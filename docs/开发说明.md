# 开发说明

本文档给零基础开发负责人阅读，用简单明了的语言说明每次开发用到的技术、实现了什么功能，以及应该如何继续学习。

每次开发结束后，都需要更新本文档。

## 2026-05-20：项目骨架与后端 MVP 1.0

### 1. 本次用到的技术

- Flask：Python 的轻量后端框架，用来写 API。
- SQLite：本地数据库，用一个文件保存数据，适合 MVP 和本地试点。
- JSON：用来保存训练卡和反馈规则，例如 `content/training_cards.json`。
- API：前端、小程序和后端之间传数据的接口。
- seed 数据：用于快速生成演示数据，方便测试。

### 2. 本次实现的功能

- 建立项目基础目录：
  - `backend`
  - `apps/miniprogram`
  - `apps/web`
  - `content`
  - `docs`
  - `shared`
- 完成 Flask + SQLite 后端 MVP。
- 建立 8 张 MVP 数据表。
- 实现这些后端功能：
  - 目标设定；
  - 情绪事件记录；
  - 非诊断规则反馈；
  - UP 训练卡读取和推荐；
  - 练习打卡；
  - 周度报告；
  - 人工督导入口；
  - 后台 CSV 导出。
- 新增 `backend/seed_data/seed.py`，可以生成演示数据。
- 新增 `backend/README.md`，说明如何安装、初始化、启动和测试后端。

### 3. 零基础如何理解

可以把这个系统理解成三层：

1. `content` 是资料库，里面放训练卡、反馈规则、知情同意和隐私文本。
2. `backend` 是服务员，负责接收小程序和网页端发来的请求，再从数据库和内容库里取数据。
3. `SQLite` 是小型资料柜，保存目标、日记、反馈、打卡等记录。

用户在小程序里写一条情绪事件记录后，流程大致是：

1. 小程序把记录发给 Flask 后端。
2. 后端把记录存进 SQLite。
3. 后端读取 `feedback_rules.json`，生成非诊断反馈。
4. 后端读取 `training_cards.json`，推荐训练卡。
5. 小程序或网页端把结果展示给用户。

### 5. 这一阶段怎么继续学习

建议学习顺序：

1. 先理解 `backend/app.py`：它是后端入口。
2. 再理解 `backend/routes`：这里是一组 API 地址。
3. 再理解 `backend/services`：这里是真正处理反馈、训练卡、周报的逻辑。
4. 再理解 `backend/database.py` 和 `backend/models.py`：这里负责数据库。
5. 最后看 `content/*.json`：理解系统为什么能生成规则反馈和训练卡推荐。

## 2026-05-20：API 文档对齐与 shared 共用结构

### 1. 本次用到的技术

- TypeScript 类型：用来说明接口数据长什么样，减少前后端字段不一致。
- 常量文件：把 API 路径、默认用户、状态值放在统一位置。
- mock 数据：假的测试数据，用来在正式页面开发前先模拟数据结构。
- API 文档：给开发者看的接口说明书。

### 2. 本次实现的功能

- 核对并更新 `docs/API接口文档.md`，让文档和真实 Flask API 对齐。
- 新增 `shared/types/api.ts`，定义前后端共用的数据类型。
- 新增 `shared/constants/api.ts`，定义 API 路径、默认用户、状态枚举和伦理边界文案。
- 新增 `shared/mock-data/mvp.ts`，提供网页端和小程序端共用 mock 数据。
- 新增 `shared/README.md`，说明 `shared` 目录的职责。

### 3. 零基础如何理解

`shared` 的作用是“统一口径”。

如果没有 `shared`，网页端可能把日记编号叫 `diary_id`，小程序端可能叫 `id`，后端又返回另一个字段名。这样联调时很容易出错。

有了 `shared` 后，大家统一参考同一套字段：

- 网页端照着它写；
- 小程序端照着它写；
- API 文档也照着它检查；
- 后端返回值也尽量和它保持一致。

### 5. 这一阶段怎么继续学习

建议先学这三个概念：

2. “请求数据”：前端发给后端的数据。
3. “响应数据”：后端返回给前端的数据。

先不用深入 TypeScript，只要知道它是在帮我们提前写清楚“数据应该长什么样”。

## 2026-05-20：网页端和小程序端最小 API 调用层

### 1. 本次用到的技术

- fetch：网页端向后端发请求的常用方式。
- wx.request：微信小程序向后端发请求的常用方式。
- Promise：表示“请求还在进行中，等后端返回结果”。
- API client：把常用请求封装成函数，页面调用时更简单。

### 2. 本次实现的功能

- 新增 `apps/web/src/services/safehomeApi.ts`。
  - 这是网页端 API client。
  - 默认后端地址是 `http://127.0.0.1:5000`。
  - 封装目标、日记、反馈、训练卡、打卡、周报、督导、导出等接口。
- 新增 `apps/miniprogram/services/api.js`。
  - 这是微信小程序端 API client。
  - 使用 `wx.request`。
  - 方法命名尽量和网页端保持一致。
- 新增 `docs/前端联调说明.md`。
  - 记录后端如何启动；
  - 记录网页端如何调用 API；
  - 记录小程序端如何调用 API；
  - 记录微信开发者工具本地联调注意事项。

### 3. 零基础如何理解

页面不要直接写一堆请求代码。更简单的做法是：

1. 先把请求后端的代码放在 `services` 文件里。
2. 页面只调用封装好的函数。
3. 后端地址或接口路径变了，只改 `services`，不用到处改页面。

可以把 API client 理解成“电话簿”：

- 页面想创建日记，就打 `createDiary`；
- 页面想生成反馈，就打 `generateFeedback`；
- 页面想拿训练卡，就打 `recommendCards`。

### 4. 如何查看这一阶段

```powershell
cd D:\codex\workspace\safehome1.0
Get-Content -LiteralPath "apps\web\src\services\safehomeApi.ts"
Get-Content -LiteralPath "apps\miniprogram\services\api.js"
Get-Content -LiteralPath "docs\前端联调说明.md"
```

### 5. 这一阶段怎么继续学习

建议先学会读懂这句话：

```text
前端通过 HTTP 请求调用后端 API。
```

学习顺序：

1. 先知道后端地址是 `http://127.0.0.1:5000`。
2. 再知道接口路径是 `/api/diaries`、`/api/feedback/generate` 等。
3. 再知道 POST 通常用于新增数据，GET 通常用于读取数据。
4. 最后再学习 fetch 和 wx.request 的具体写法。

### 2. MVP 1.1 想解决什么

MVP 1.0 已经可以完成：

```text
记录 -> 反馈 -> 训练卡
```

MVP 1.1 要把它扩展成：

```text
目标 -> 记录 -> 识别 -> 反馈 -> 练习 -> 追踪 -> 支持
```

也就是说，家长不只是记录一次事件，而是可以围绕一个本周小目标，持续记录、练习、打卡、看周报，并在需要时提交给人工督导进一步查看。

### 3. MVP 1.1 规划了哪些功能

规划了 6 个功能：

1. 目标设定页；
2. 情绪事件记录升级；
3. 情绪与互动模式识别卡；
4. UP训练卡详情与轻打卡；
5. 简版周度报告；
6. 人工督导补充入口。

### 4. 零基础如何理解这些功能

可以把 MVP 1.1 理解成一条家长练习路线：

```text
先定一个小目标 -> 记录一次事件 -> 看见当时的想法和行为 -> 得到支持性反馈 -> 选一张练习卡 -> 完成一次小练习 -> 一周后看复盘 -> 必要时请老师补充看看
```

这不是心理诊断，也不是 AI 聊天。

它更像一个温和的“亲子情绪练习记录本”。

### 5. 为什么先不改数据库

因为当前后端已经有这些表：

1. `goals`：目标；
2. `emotion_diaries`：情绪记录；
3. `feedback_results`：反馈；
4. `training_cards`：训练卡；
5. `checkins`：打卡；
6. `weekly_reports`：周报；
7. `supervision_requests`：督导请求。

第一阶段可以先复用这些表，避免新手阶段一次性改太多底层结构。
