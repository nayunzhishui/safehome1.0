# 当前项目不足与后续优化规划

更新时间：2026-07-11
适用项目：`safehome1.0 / 安心陪伴 / ReadFeedback`
代码基线：`main`，最近已推送提交 `b31604c3`
文档性质：当前事实基准 + 后续执行规划

## 1. 总体结论

当前项目已经不是“缺少基础功能”的早期原型，而是具备家长支持主闭环、学生画像、关系探索试点、研究者后台、人工复核和内容管理能力的试点平台。

下一阶段不应继续无边界增加页面和功能，应从以下五个方向收口：

```text
数据可信
模型治理
隐私完整
真实部署验收
关键页面视觉收口
```

项目不需要推倒重写。现有 Flask、SQLite/MySQL、微信小程序、React/Vite、content 内容库和 shared 契约均可继续使用；优化方式应保持小步、可回滚和一次一个明确任务。

## 3. 当前不足之处

## 3.1 P0：扩大试点前必须处理

### P0-1 通用测评输入仍不完全可信

当前 `POST /api/assessment-results` 会优先使用客户端提交的 `answer.score`。接口尚未统一拒绝：

- 未知题号；
- 重复题号；
- 不属于题目选项的 value；
- 不允许缺题的量表缺少题项；
- 客户端伪造或篡改 score。

影响：错误或恶意输入可能污染总分、维度分、画像结果、训练推荐和研究数据。

### P0-2 画像模型准入状态没有成为运行时硬规则

当前画像模型 JSON 普遍没有统一的 `admission_status`。通用加载逻辑主要排除 `manual_review_required`，不足以表达：

```text
仅内部审核
允许受控试点
正式生产批准
已停用
```

影响：文档中的开放边界可能与实际运行不一致，未签字模型可能进入自动画像链路。

### P0-3 离线模型和线上推断不完全一致

任务十二离线模型使用 GMM 权重、均值和对角协方差；线上通用画像匹配主要按标准化后的欧氏距离寻找中心。

影响：同一份填写结果可能在离线审查和线上运行时得到不同分组，现有“置信度”也不是校准后的统计概率。

### P0-4 关系试点隐私覆盖不完整

当前隐私中心已经支持研究授权撤回，但个人数据摘要没有完整覆盖关系报名、报告、任务、叙事、连续记录和假设反馈；关系研究者看板也没有统一复用撤回过滤。

影响：用户撤回后，部分研究视图和个人数据说明可能仍不完整。

### P0-5 线上版本与真机状态尚未闭环

本地测试通过不能证明云端已经运行最新登录、数据库迁移和量表内容。必须完成新版部署后再判断微信登录、手机号登录和数据链路是否真正可用。

### P0-6 Web 关键入口存在明确视觉缺陷

Web 登录、注册和家庭绑定页面使用了未定义的 `.pill` 样式。真实浏览器检查中，登录按钮退化为近似普通文本，页面存在大面积无意义空白。

影响：登录是研究者和后台用户的第一入口，该问题会直接降低专业感、可操作性和信任。

## 3.2 P1：试点质量和产品体验优化

### P1-1 学生画像仍携带逐行派生训练点

学生画像可视化仍可能返回 466 个 `training_points`。虽然不含姓名和 ID，但不符合客户端最小必要数据原则。

建议改为：簇中心、置信椭圆、密度网格或满足最小单元阈值的聚合点。

### P1-2 画像语言仍有标签化残留

部分模型内容仍存在“情绪波动型、过度确定型、外归因型、自我批判型”等名称。

应统一改为：

```text
当前线索
阶段性位置
相对接近的观察方向
待共同核对的机制假设
```

### P1-3 推荐仍偏量表级，不够个体化

同一量表不同画像之间的训练卡、问题和小步行动相似，个人维度、任务完成情况、主观帮助度和用户核对反馈尚未充分影响下一次推荐。

### P1-4 认证安全仍是试点级

- 登录令牌有效期 7 天，服务端没有撤销列表；
- 用户名密码登录尚无失败频率限制和锁定策略；
- CloudBase 可信身份头依赖真实部署入口，单元测试不能证明公网入口不会被绕过；
- 旧 `X-Admin-Token` 仍作为兼容入口存在。

### P1-5 CI 与本地总门禁范围不一致

GitHub Actions 当前主要执行内容校验、后端测试和 Web build，尚未完整执行：

- Web TypeScript `tsc --noEmit`；
- 小程序结构审计；
- 小程序 JS 与 JSON 检查；
- Playwright E2E；
- 依赖漏洞审计；
- MySQL 真实适配器集成测试；
- CloudBase 发布包验证。

### P1-6 大文件和跨层知识集中

当前部分文件较大：

| 文件 | 规模与问题 |
|---|---|
| `backend/routes/admin.py` | 约 948 行，查询、导出、脱敏、权限和审计集中 |
| `backend/database.py` | 约 806 行，连接、方言转换、迁移和内容同步集中 |
| `shared/types/api.ts` | 超过 1000 行，难以确认哪些契约真实生效 |
| `apps/miniprogram/services/api.js` | 超过 700 行，接口和请求行为集中 |
| `apps/web/src/pages/ReadFeedbackIntegrationPages.tsx` | 超过 1000 行，多页面实现集中 |
| `apps/web/src/main.tsx` | 手工判断路径、角色和页面渲染 |

这并不意味着必须按行数拆分，而是需要按高风险业务概念建立更深的模块和更小的调用界面。

## 3.3 页面美观和交互不足

### Web 端

1. Web 首页首屏较成熟，但后续连续使用相似白色卡片和三/四列网格，阅读节奏单一。
2. 首页“小程序预览”与当前真实小程序首页结构和文案不一致。
3. 登录、注册、权限和家庭绑定没有达到首页同等视觉质量。
4. 权限页暴露 `Access Control`、角色代码和 `/dashboard` 等内部词。
5. 未发现统一的 `:focus-visible` 和 `prefers-reduced-motion`。
6. 多处控件高度为 30–42px，低于 44px 建议触控尺寸。
7. `styles.css` 同时包含旧硬编码规则和新 token，仍有约 25 处内联样式。

### 小程序端

小程序已有 `app.wxss` token 和公共组件，方向正确，但页面仍大量单独声明视觉值：

| 页面 | 已观察到的视觉复杂度 |
|---|---|
| `home` | 约 30 处字号声明 |
| `assessment` | 约 36 处硬编码颜色、21 处字号声明 |
| `assessment-result` | 约 20 处字号声明，结果与画像信息密集 |
| `training` | 约 31 处字号声明 |
| `relationship-report` | 状态、四层画像、共同核对内容较多 |
| `relationship-growth` | 折线、时间轴、来源标签需要真机验证 |

主要问题：

- 全部页面累计约 20 种字号，视觉层级容易漂移；
- 暖色卡片使用较多，页面之间可能出现同质化；
- 测评结果、画像、关系报告和成长页的信息密度较高；
- 静态审计不能证明折行、安全区、Canvas 比例和真实触控体验；
- Web 模拟小程序画面与真实小程序可能继续漂移。

## 4. 后续具体优化方案

## 4.1 第一批：服务端测评答案规范化与计分

优先级：P0
预计工作量：3–5 个工作日
是否修改数据库：否
是否修改前端结构：原则上否

### 实施内容

1. 建立“测评执行模块”，统一读取 worksheet。
2. 只接受题目定义中存在的 `question_id` 和 option value。
3. 服务端重新计算原始分、反向分、维度分和总分。
4. 忽略客户端传入的 `score`，或仅作为不参与计算的审计输入。
5. 按量表配置校验是否允许缺题。
6. 在同一流程中完成风险检查、保存、画像触发和训练推荐。

### 主要文件

- `backend/routes/assessments.py`
- 新增或深化 `backend/services/assessment_*`
- `backend/tests/test_assessments_route.py`
- `backend/tests/test_training_recommendation.py`

### 验收指标

```text
未知题号：拒绝
重复题号：拒绝
非法选项：拒绝
不允许缺题：拒绝
客户端score=99：不进入真实计分
正常量表、反向计分、三份任务十二量表：全部通过
```

### 回滚方式

只回滚新模块和路由调用，不改数据库字段，不影响已有历史结果读取。

## 4.2 第二批：画像模型准入与推断一致性

优先级：P0
预计工作量：5–8 个工作日

### 实施内容

1. 建立统一准入枚举：

```text
internal_only
pilot_approved
production_approved
deprecated
```

2. 运行时只加载当前环境允许的状态。
3. 模型保存 artifact hash、训练数据摘要 hash、评分版本、推断版本、审批人和审批时间。
4. GMM 保存权重、均值和协方差；线上使用相同公式计算 posterior。
5. 用 posterior、熵和经验距离区分：可解释、低确定性、样本外。
6. 未批准、低确定性和离群结果只显示维度，不显示强画像名称和自动训练建议。
7. 删除客户端逐行 `training_points`。

### 验收指标

```text
internal_only模型自动解释数量=0
离线与线上同输入分配一致率=100%
客户端逐行训练点=0
模型artifact缺字段或hash不一致时readyz失败
标签化画像名称=0
```

## 4.3 第三批：关系试点隐私闭环

优先级：P0
预计工作量：3–5 个工作日

### 实施内容

1. 建立统一研究数据清单。
2. 关系研究者看板复用授权撤回过滤。
3. 个人数据摘要覆盖全部关系表。
4. 明确删除请求对每张关系表的处理方式。
5. 敏感查看、导出、确认和删除继续写审计日志。

### 验收指标

```text
撤回授权后研究者看板不可见
撤回授权后研究导出不可见
个人数据摘要覆盖全部关系表
删除处理清单无遗漏
敏感查看与处理均有审计记录
```

## 4.4 第四批：CloudBase 与真机发布验收

优先级：P0
预计工作量：2–3 个工作日，不含外部审核等待

### 实施顺序

1. 上传当前 CloudBase 安装包。
2. 确认 `/healthz` 版本为最新标识。
3. 确认 `/readyz` 数据库提供方、迁移号和 worksheet 数量。
4. 验证微信一键登录和手机号快捷登录。
5. 依次验证：测评 → 报名 → 报告 → 消息 → 绘画/句子 → 成长记录。
6. iOS 和 Android 各完成一次核心链路。

### 验收指标

```text
云端迁移版本=本地当前版本
云端worksheet数量不少于30
微信和手机号登录成功
不同设备Canvas不变形
断网恢复不丢草稿
高风险文本进入人工队列
```

## 4.5 第五批：Web 关键页面视觉修复

优先级：P0 产品体验 / P1 视觉体系

- 登录；
- 注册；

## 4.6 第六批：小程序视觉与体验收口

优先级：P1
预计工作量：7–10 个工作日，按页面小步执行

### 视觉方向

继续保持现有暖白、低饱和绿和克制橙色，主题建议为：

> 陪伴观察手记

界面像一份持续记录、逐步回看的家庭成长手记，不像医疗报告、考试成绩单或营销课程平台。

### 视觉 token 收敛

```text
6级字号
6个语义色
4级间距
3种surface
统一44px等效触控尺寸
```

推荐语义色：

| 名称 | 色值 | 用途 |
|---|---|---|
| 松针绿 | `#4F7C6B` | 主动作和关键路径 |
| 深林绿 | `#2F5B4D` | 标题和高对比文字 |
| 纸张暖白 | `#FFFDF8` | 主要内容 surface |
| 晨雾灰绿 | `#F2F4F0` | 页面背景和分区 |
| 陪伴橙 | `#D98243` | 提醒和进度节点 |
| 安全红 | `#C85F58` | 必须关注的风险状态 |

### 签名视觉元素

使用一条细的“陪伴路径线”连接：

```text
记录 → 理解 → 练习 → 复盘
```

只在首页核心闭环、关系试点阶段和成长报告使用，不在所有页面增加装饰。

### 页面实施顺序

1. `login` 与 `profile`：先建立信任和清晰身份状态。
2. `assessment`：减少颜色和卡片竞争，突出选择一份测评。
3. `assessment-detail`：降低问卷压力，强化进度、保存和错误定位。
4. `assessment-result`：第一屏只显示两个重要维度和一个主行动。
5. `training`：突出训练路径和今日一个练习。
6. `relationship-pilot`：维持五阶段，但只突出当前阶段。
7. `relationship-report`：区分系统计算、规则解释、研究者确认和用户核对。
8. `relationship-growth`：次数指标与1–5量尺分开，趋势至少两次才显示。
9. `home`：最后统一入口和 Web 小程序预览。

### 图表方案

- 用户端优先使用中性发散条形图和本人维度；
- 不把簇中心雷达当作用户个人轮廓；
- PC1/PC2 和散点主要留给研究者端；
- 继续复用有数据、数据不足、低确定性、离群、加载失败五态；
- 低确定性不能只靠颜色表达。

### 真机视觉矩阵

至少覆盖：

```text
微信开发者工具常用手机尺寸
iOS一台
Android一台
较窄屏幕
较大字体设置
弱网与断网恢复
Canvas横竖屏和不同像素比
```

### 验收指标

```text
页面级非白名单字号和颜色减少70%以上
每页主要实色按钮不超过1个
文字截断和底部遮挡=0
主流程页面均有截图基线
触控目标符合44px等效尺寸
Canvas不同设备不变形
```

## 4.7 第七批：可解释的个体化推荐

优先级：P1/P2
预计工作量：7–12 个工作日

不建议当前直接让大模型自由解释心理画像。先使用受控、可追溯的确定性推荐：

```text
用户目标
+ 本人维度和张力
+ 画像确定性/离群状态
+ 风险和授权
+ 最近任务完成情况
+ 主观帮助度
+ 用户“符合/不符合/不确定”反馈
→ 1个主任务 + 1个备用任务 + 明确理由
```

积累足够试点数据后，再评估离线策略学习或受约束的 contextual bandit。不得用点击率替代心理效果，不得自动强化高风险内容。

### 验收指标

```text
每次推荐理由可解释
同一量表不同维度能产生不同任务
用户不符合率可统计
研究者覆盖率可统计
高风险普通推荐数量=0
```

## 4.8 第八批：工程质量深化

优先级：P2
实施方式：分切片渐进完成，不做全项目一次性重构

### 深化模块顺序

1. 测评执行模块；
2. 画像模型运行时模块；
3. 研究数据治理模块；
4. 身份与部署运行时模块；
5. 测评、画像、认证持久化模块；
6. 跨端契约生成模块。

### 具体方案

- 以 `relationship_pilot_routes.py` 的薄 HTTP 层和深业务模块为参考；
- SQLite 和 MySQL 作为两个真实 adapter，不让方言继续泄漏到业务调用者；
- 建立顺序、可回放的迁移 runner，减少启动时正则 DDL 转换；
- 把关系试点 JSON Schema 生成方式推广到测评、画像和认证；
- Web 和小程序从同一契约生成 endpoint、状态、错误码和核心类型；
- Web 路由改为声明式路由表，避免继续扩大 `main.tsx` 手工判断。

- 模型版本、artifact hash 和解释阻断状态可追踪；
- 风险队列积压和人工处理时长可监控；
- 隐私撤回、导出、敏感查看和删除处理可审计。

## 6. 暂不建议实施

当前不建议：

- 全站重写或更换前端框架；
- 为了“智能”直接增加自由大模型心理解释；
- 未完成准入前扩大画像自动开放；
- 用更复杂算法掩盖量表版本、授权和数据质量问题；
- 删除现有后端接口、历史字段、内容库和联调页；
- 为美观大量增加通用AI插画、渐变和装饰卡片；
- 同时重构认证、数据库、画像和全部前端页面。
