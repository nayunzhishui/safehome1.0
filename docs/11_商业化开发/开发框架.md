### 1.1 技术栈

### 1.2 后端写法

```python
# backend/routes/xxx.py
from flask import Blueprint, request
from routes.auth_utils import AuthError, auth_error_response, require_login
from routes.utils import fail, ok

bp = Blueprint("xxx", __name__, url_prefix="/api/xxx")

@bp.get("")
def get_xxx():
    try:
        actor = require_login(allow_legacy_admin=False)
    except AuthError as exc:
        return auth_error_response(exc)
    return ok(xxx_service.build(actor["id"]))
```

- 注册：`backend/app.py` 顶部 `from routes.xxx import bp as xxx_bp`，`create_app` 里 `app.register_blueprint(xxx_bp)`。骨架的 5 个新蓝图已经注册。
- 连接：`with get_connection() as conn:`，写完 `conn.commit()`。
- 编号和时间：`new_id("前缀")`、`now_iso()`（都在 `database.py`）。
- 审计：`write_audit_log(conn, action, actor_id, target_type, target_id, metadata)`。审计表有哈希链，只能用这个函数写。
- 防重复：`services/idempotency_service.py` 的 `reserve_idempotency(conn, actor_id=, endpoint=, idempotency_key=, request_hash=, resource_type=, resource_id=)`。
- 产品事件：`POST /api/product-events`，要登录；允许的事件名和取值在 `routes/product_events.py` 的 `ALLOWED_EVENTS`、`ALLOWED_METADATA_VALUES`；事件写进 `audit_logs`，action 是 `product_event_<事件名>`。

### 1.3 数据库变更

- 开发和测试环境：`init_db()` 按 `models.SCHEMA_SQL` 建表，加列用 `ensure_column`。
- 生产环境：**启动时不改表**（`app.py` 里有注释说明）。新表、新列都要写成显式迁移：在 `services/schema_migration_service.py` 加 `_apply_2026_11_xx_079` 和对应的 `Migration(...)`（现在最新的是 `2026_08_26_078`），由负责人执行 `python backend/scripts/apply_explicit_migrations.py --apply`。
- 生产健康检查只看 `database.REQUIRED_HEALTH_TABLES`。新表在功能正式启用前不要加进去，否则没有执行迁移的环境会启动失败。
- 索引列在 MySQL 里要用 VARCHAR(191)，写法参照 `ensure_mysql_index_columns`；迁移函数里用 `_provider(conn)` 分 SQLite 和 MySQL 两种语句，参照现有迁移。
- 本期只新建 `orders`、`entitlements` 两张表（B5）。其余都复用 `records`、`checkins`、`audit_logs`。

### 1.4 时间

- 库里的 `created_at` 是 UTC 时间（`now_iso()`）。现有周报用 `substr(created_at, 1, 10)` 切日期，所以北京时间 0–8 点写的记录会算到前一天。
- 新代码一律按北京时间切日期和时段：`zoneinfo.ZoneInfo("Asia/Shanghai")`（tzdata 已在依赖里）。
- 旧代码先不改，免得周报的数字突然变化。要不要顺手修，负责人定（见 B3 意见第 4 条）。

## 2. A3 渠道标记

**目标**：知道人从哪个渠道进来，哪个渠道来的人留得住。

**现状**：产品事件接口要登录，事件里没有渠道字段。

**做法**

- 入口参数 `ch`，取值 `gzh`（公众号）、`sph`（视频号）、`group`（小组）、`interview`（访谈）、`other`。
  - 文章里的路径：`pages/home/index?ch=gzh`。
  - 小程序码：服务端调 `getUnlimited`，scene 写 `ch=sph`（scene 最长 32 个字符，以官方文档为准）。
- 前端：`app.js` 的 `onLaunch` / `onShow` 从 `options.query.ch` 或 `decodeURIComponent(options.query.scene)` 里解析渠道，存进本地 `safehome.channel`（只记首次渠道和时间）。登录后补报一次 `app_entry`，`client_event_id` 用 `app_entry:<ch>:<北京日期>`，避免重复。
- 后端：`ALLOWED_EVENTS` 加 `app_entry`；`ALLOWED_METADATA_VALUES` 加 `"channel": {"gzh", "sph", "group", "interview", "other"}`。
- 统计：`backend/scripts/channel_summary.py` 只输出各渠道的人数和 7 日留存，不输出个人记录；生产上由负责人自己跑。
- 局限：没登录的人进来，事件先存在手机上，登录后才补报；从没登录过的人不计入。这一点要写进指标说明。微信的 We 分析自定义事件（`wx.reportEvent`）能统计没登录的人，但数据给到微信平台，要写进隐私政策；用不用由负责人定。

## 3. B1 急救卡

**目标**：气头上或刚吵完，两次点击内开始一段能听着做的短练习，做完马上看到前后分数。没登录也能用。

**现状**

- 6 张卡都在 `content/training_cards.json`，状态都是 production_approved：
  - 气头上：`three_second_pause` 开口前停三秒（1 分钟）、`parent_body_signal_check` 身体信号检查（2 分钟）、`parent_body_grounding` 先让身体落地（3 分钟）、`emotion_naming` 先命名情绪（3 分钟）。
  - 刚吵完：`parent_after_conflict_repair` 冲突后一句修复（2 分钟）、`parent_repair_question` 先听最难受的那句（4 分钟）。
- 真正做练习的页面是 `pages/checkin`。行动方案里写的 `pages/training-card` 是选卡列表，这里更正。练习页的前后分数是 0–10 的滑块，默认都是 5。
- `GET /api/cards` 不要求登录；保存练习 `POST /api/checkins` 要登录。
- 云托管最小实例 10-20 改成了 0，服务空闲后第一次请求要冷启动，可能要等几秒到十几秒（以实测为准）。在气头上的人等不了这么久。

**意见（和行动方案不同的三处）**

1. **语音先走，文字后到。** 卡片正文不能写死在前端（第 1.6 节），所以正文从接口取，拿到后存进本地缓存。语音放在云存储，用文件 ID 直接播放，不经过后端，冷启动时也能马上开始。第一次打开如果网络很差，就先放语音，文字晚几秒出来。
2. **不改 `training_cards.json` 的标签。** 这份文件有负责人的发布批准记录（`release_approval`），改标签要重走批准。改用单独的 `content/quick_cards.json`（骨架已建），里面写分组、顺序和音频文件 ID。
3. **练习前的分数不给默认值。** 必须先点选一个分数才能开始，避免没拖滑块也被记成 5 分。现有练习页默认 5 分也有同样的问题，负责人 11-05 定一起改：没拖滑块就不记分。

## 5. B3 看见变化

**目标**：每次练完看到前后分数；本周复盘能看到练习前后和最高的几次；用满两周后看到自己的基线。

**现状**

- 练习前后分在 `checkins.emotion_before / emotion_after`（0–10），或者通过 `before_thermometer_id / after_thermometer_id` 关联温度计记录。

**意见**

1. 单次前后分：练习页提交成功后，直接用页面上的两个分数显示，不需要新接口。

3. 个人基线只用温度计记录：近 28 天 `intensity_level` 的中位数和四分位距。条件是第一条记录距今满 14 天，并且 28 天内至少 6 条；不够时告诉她还差几天、几条。

   - 周报里高风险时的建议是“下周优先安排人工关注和现实支持确认，暂不把高风险个案推入普通自动训练”。这是写给工作人员看的话，却会显示在家长的本周复盘页上，建议改成面向家长的话，并附上求助入口。

## 6. B4 深度报告：现状和意见

### 6.1 现有的几种报告

| 报告 | 代码 | 时间范围 | 内容 | 问题 |
|---|---|---|---|---|
| 本周复盘 | `report_service.build_weekly_report` → `pages/weekly-report` | 7 天 | 场景和情绪词计数、测评摘要、温度计均值和趋势、30 天练习效果、一句建议 | 趋势只比首尾两条；高风险建议是工作人员口吻；按 UTC 切日期 |
| 阶段进展 | `progress_summary_service.build_progress_summary` | 7 天或 30 天 | 测评变化、练习、温度计、阶段状态文字 | 和深度报告的 30 天对比部分重叠 |
| 练习效果 | `build_training_effectiveness` | 30 天 | 每张卡的平均变化和样本量提示 | 用平均数，一次极端值影响大；不分场景 |
| 家长测评报告 | `parent_assessment_service.build_parent_report` | 单次 | 画像、建议、推荐“课” | 推荐的 4 门“微课”在课程里不存在（C4） |
| 关系报告 | `relationship_report_service` + `pages/relationship-report` | 一次活动 | 假设、反馈、长图导出 | 长图导出（`drawLongImage`、`exportLongImage`）可以抽出来复用 |

### 6.2 意见

1. **深度报告卖的是“跨时间、跨场景的关联”，不是更多的分数。** 现有数据能可靠做出四节：场景和时段的分布、每个场景常见的情绪词、每个场景下哪张卡练完降得多、同一份问卷前后两次的对比。不做“情绪模式画像”，也不对日记文字做自动归类，日记原句只按场景列出来给她回看。理由：一个人 30 天的样本很小，解释的风险高，容易被读成诊断。
2. **不说“最有效”，只说“练完平均降了几分（几次）”。** 人往往在情绪最高的时候去练，练完分数本来就会回落一些（回归均值），降幅不全是卡的作用。报告里写一句：“这是你自己的记录，帮你找规律，不是疗效证明。”
3. **每一节有自己的门槛。** 总门槛“30 天内至少 8 条记录”只决定能不能买。各节再设门槛：
   - 场景 × 时段：日记至少 8 条；
   - 场景 × 练习：同一场景下同一张卡至少 3 次；
   - 问卷对比：同一份问卷 2 次、间隔至少 14 天，用现有的 `assessments_comparable` 判断能不能比；
   - 和前 30 天比：前 30 天也至少 8 条。

   不够门槛的节不显示。购买前的预览列出“你的数据能生成哪几节”，让她知道买的是什么。
4. **生成一次就存一份快照。** 存进 `records`（`module_type = "deep_report"`），`data_json` 里记版本号、时间窗和每一节的结果；同一天重复请求直接返回快照。这样她买到的内容是固定的，以后数字变了也说得清原因。
5. **统计用中位数，不用平均数。** 和前 30 天比只看中位数差和记录条数差；差值不超过 1 分写“变化不大”，因为温度计是整数刻度，1 分以内的差别不可靠。
6. **时段按北京时间切**：早晨 6–9 点、白天 9–17 点、傍晚 17–20 点、晚上 20–23 点、深夜 23–6 点。用日记的 `event_time`（她自己选的事发时间），没有时再用 `created_at`。
7. **4 周方案复用现成的。** 用 `pages/personalized-plan` 和 `training_schedule_service`（现有排期 `next_three_per_week` 就是每周 3 次）。第 1 周从“场景 × 练习”里降幅最大的两张卡开始；数据不够时用家长测评的推荐。提醒沿用 `WECHAT_TRAINING_DUE_TEMPLATE_ID` 的一次性订阅，每次练完重新请求授权（`pages/personalized-plan` 已有请求授权的代码）。
8. **风险优先。** 报告顶部固定放风险提示和求助入口。30 天内有高风险记录时，第一节换成“先照顾好自己”的支持信息和求助入口，整份报告不出现购买引导。中风险怎么处理，按负责人此前对“中风险对用户不可见”的决定执行。
9. **测试期间谁能看到。** 开发和验证环境里所有人都能生成。生产环境在 `COMMERCE_ENABLED` 打开之前，深度报告的接口返回 404。如果想在实际测试里免费给测试用户看，需要负责人单独决定，再加一个开关。

## 7. B5 付费功能（测试环境）

**现状**：没有任何订单和支付代码。幂等、审计哈希链、开关写法、显式迁移这几样现成的都能直接用。

**一个要先解决的问题**：按官方文档的描述，虚拟支付的用户态签名 `signature` 要用用户的 `session_key` 计算（开通时以官方文档核对）。`session_key` 只能通过 `wx.login` 加 `code2Session` 拿到。10-15 的记录显示，开放接口服务挡住了 `code2Session`，现在登录走的是手机号和云托管身份头。不解决这一条，安卓端也调不起支付。主体迁移完成后，第一件事就是核对这一点。

### 7.1 设计

- **支付方式做成可替换的。** `services/payment_provider.py` 定义 `PaymentProvider`（建单、验签通知、查询、退款）。先实现 `MockPaymentProvider`，在测试环境走通全流程；`WechatVirtualPaymentProvider` 先留空，主体和虚拟支付开通后再实现。订单逻辑只依赖这个接口，换支付方式不用改订单代码。
- **订单状态只允许这几种转换**：created → paid → delivered；paid 或 delivered → refunded；created → closed（30 分钟没付）。每次转换写一条审计（action `commerce_order_<状态>`）。
- **防重复发货**：支付通知按商户订单号 `out_trade_no` 调 `reserve_idempotency`（endpoint 用 `commerce_notify`）。重复通知直接回成功，不再发货。
- **发货就是写权益**：发货写 `entitlements`；退款把对应权益改成 revoked。
- **金额只认服务端**：下单时按 `commerce_skus.json` 的价格计算，前端传来的金额一律忽略。
- **平台判断**：前端用 `wx.getDeviceInfo().platform`，只有 android 显示购买按钮；iOS 和电脑端显示“暂不支持在这台设备上购买”，不写引导去别处付款的话。

### 7.2 虚拟支付流程（开通时逐项以官方文档为准）

1. 前端 `POST /api/commerce/orders {sku_id}`。后端建单（created），生成 `signData`（offerId、buyQuantity、env、currencyType、productId、goodsPrice、outTradeNo、attach）、`paySig`（AppKey 对 `requestVirtualPayment&` 加 signData 做 HMAC-SHA256）和 `signature`（session_key 签名），返回给前端。
2. 前端调 `wx.requestVirtualPayment({signData, paySig, signature, mode: "short_series_goods"})`。
3. 微信服务器通过消息推送通知后端发货。后端验签、防重复、改成 paid、写权益、改成 delivered，再回成功。
4. 前端支付成功后轮询 `GET /api/commerce/orders/<id>`，最多 5 次，确认 delivered 后刷新权益。
5. 道具（productId）要先在虚拟支付后台配置好，价格和 `commerce_skus.json` 一致。

### 7.3 表结构（显式迁移 079，只在测试环境执行；不加进 `REQUIRED_HEALTH_TABLES`）

```sql
CREATE TABLE IF NOT EXISTS orders (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    sku_id TEXT NOT NULL,
    amount_fen INTEGER NOT NULL,
    currency TEXT NOT NULL DEFAULT 'CNY',
    provider TEXT NOT NULL,              -- mock / wechat_virtual
    platform TEXT,                       -- android / ios / pc
    status TEXT NOT NULL,                -- created / paid / delivered / refunded / closed
    out_trade_no TEXT NOT NULL,          -- 唯一索引；MySQL 用 VARCHAR(191)
    provider_txn_id TEXT,
    sku_snapshot_json TEXT NOT NULL DEFAULT '{}',
    created_at TEXT NOT NULL,
    paid_at TEXT,
    delivered_at TEXT,
    closed_at TEXT,
    refunded_at TEXT,
    updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_orders_out_trade_no ON orders(out_trade_no);
CREATE INDEX IF NOT EXISTS idx_orders_user ON orders(user_id, created_at);

CREATE TABLE IF NOT EXISTS entitlements (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    entitlement_type TEXT NOT NULL,      -- deep_report / four_week_plan / full_courses
    source_order_id TEXT,
    starts_at TEXT NOT NULL,
    ends_at TEXT,
    status TEXT NOT NULL,                -- active / revoked / expired
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_entitlements_user ON entitlements(user_id, entitlement_type, status);
```

## 8. B6 内容分流：现状和意见

### 8.1 现有的分流规则（都是规则，没有 AI）

| 从哪来 | 规则和代码 | 推荐到 | 说明 |
|---|---|---|---|
| 日记 | `content/feedback_rules.json` → `feedback_service.generate_feedback`；`content/diary_training_map.json` | 训练卡 | 触发条件是反馈规则（如 judgmental_language）和风险等级，不看日记的场景 |
| 测一测 | `content/assessment_training_map.json` → `training_recommendation_service` | 训练卡 | 按问卷维度阈值或画像；有两种策略：`legacy_rule_order_v1`，以及会按她对卡的评价调整顺序的 `feedback_adaptive_v2`；结果记在 `recommendation_snapshots` |
| 家长测评 | `content/readfeedback/parent_report_rules.json` → `parent_assessment_service.build_parent_report` | 课程名（纯文字） | 推荐的 4 个名字在课程里不存在 |
| 卡片库 | `GET /api/cards/recommend?tags=` | 训练卡 | 按标签 |
| 本周复盘 | `report_service` 里写死的几句话 | 一句建议 | 不带链接 |

### 8.2 意见

1. **不另做分流引擎。** 训练卡继续用现有的两套规则，包括按评价自适应的 v2。内容地图只补训练卡以外的内容（文章、视频、短课、故事）和它们的“下一步”。
2. **统一内容编号，格式是“类型:id”**，例如 `card:three_second_pause`、`course:repair_after_conflict_course`、`video:v001`、`story:s001`、`worksheet:<问卷 id>`。课程推荐、文章里的链接、故事的下一步都用这个编号；前端由 `utils/contentRoute.js`（骨架已建）统一决定跳到哪个页面。
3. **运行时只按“台阶 + 场景”分流。** 场景用日记现有的 5 个（作业拖延、睡前冲突、手机使用、出门准备、亲子沟通），另加“其他”。生态层（家庭内、家校之间、父母工作、更大的环境）只在盘点时用，检查内容有没有偏科，先不进运行时规则。理由：多一个维度，要维护的规则就多一倍，现在的内容量还撑不起来。
4. **日记加一条按场景的兜底规则。** 现在日记按反馈规则推荐，不看场景。建议在 `diary_training_map.json` 里加按场景的兜底：反馈规则没有命中时，按场景推荐 1 到 2 张卡；现有规则的优先级不变。
5. **风险优先。** 分流之前先看风险。高风险时只出求助入口，不出“下一步内容”，也不出付费入口。`diary_training_map.json` 的边界说明已经是这个意思，内容地图照此执行。
6. **家长报告改成按编号推荐。** `parent_report_rules.json` 的 `course` 字段改为 `course_id`，原来的文字保留成 `course_label`，方便回退；先指向现有的 5 门课（C4）。
7. **加一个校验。** 检查内容地图里所有编号都存在、每条内容都有下一步、没有绕圈（A 指向 B，B 又指回 A）。

```json
      "type": "video",
      "title": "作业为什么越催越慢",

```

- `access`：free 或 paid（只有完整短课是 paid）。
