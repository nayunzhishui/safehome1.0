# SafeHome 1.0 非权限项产品信息密度与工程收敛执行计划

> 执行状态（2026-08-13）：R00、R01 已完成；下一唯一入口为 R02 首页呈现收敛。基线证据见 `artifacts/convergence/R00-baseline/`、`artifacts/convergence/R01-information-baseline/`、`artifacts/convergence/function-baseline/` 与 `artifacts/information-density/`。R00/R01 未修改参与者 UI、权限、后端、数据库、API、shared、心理计分或风险规则。

**版本：Final 1.0**
**日期：2026-08-13**
**适用项目：SafeHome 1.0**
**执行对象：Codex / Claude / 人工开发者**
**任务性质：产品与工程收敛，不新增业务能力**

---

# 1. 本轮任务目标

SafeHome 当前阶段的主要问题已经不是“功能不足”，而是：

1. 部分参与者页面功能和信息同时暴露过多。
2. 首页存在多个信息区块和行动入口竞争注意力。
3. 测评结果页同时承担结果解释、画像、图表、研究信息、推荐等过多职责。
4. 部分文案存在重复解释、重复免责声明、专业术语负担较高的问题。
5. 项目文档持续 append，形成数百 KB 的超大“当前文档”。
6. Web、小程序和后端存在大型高耦合文件。
7. CI 检查已经很多，但信号集中、可维护性下降。
8. 小程序源码、生成文件、页面和资源规模持续扩大，需要包体和加载治理。
9. 缺少“功能不丢失 + 信息密度下降”的自动化检查体系。

因此，本轮目标从：

> 继续增加功能

切换为：

> **完整保留现有能力，对产品呈现、信息层级、代码结构、文档结构和工程质量进行收敛。**

---

# 2. 最高级原则：功能零损失

这是本计划中优先级最高的约束。

任何其他条款与本条冲突时，以本条为准。

## 2.1 不允许通过删功能实现简化

所谓：首页减负、测评页减负、信息密度优化、页面收敛、代码重构、包体优化，均不代表删除已有能力。

必须满足：

```text
现有页面保持存在
现有功能保持存在
现有业务能力保持存在
现有数据保持存在
现有主要入口保持可访问
现有按钮行为保持可用
现有API能力保持不变
现有业务路径保持完整
现有异常处理保持有效
现有历史数据保持兼容
```

# 3. 呈现减法 ≠ 功能减法

允许做的是：

```text
调整排序
调整视觉层级
调整卡片大小
调整信息默认展开状态
使用折叠/展开
增加“查看详情”
增加二级页面承载详细信息
调整次要入口视觉权重
缩短重复文案
合并重复说明
优化标题
优化段落
延迟加载非关键数据
拆分组件
拆分代码文件
拆分CSS
拆分CI
```

禁止做的是：

```text
删除现有业务功能
删除页面
直接删除入口
删除数据能力
关闭原有API
改变已有业务流程
减少原有用户可执行操作
```

核心公式：

> **功能完整度保持不变，默认暴露复杂度下降。**

- 增加新的首页主入口。

# 12. SafeHome UI 信息结构原则

参与者核心页面默认使用三级结构：

1. **我现在是什么状态？**
2. **这意味着什么？**
3. **我现在可以做什么？**

不要在第一屏同时解释统计模型、研究方法、画像、算法、限制、样本、训练、风险、维度和研究任务。

文案不是越短越好，目标是每一句话承担明确功能：说明状态、解释意义、提供行动、说明边界、提供安全支持。

---

# 13. 文案建议范围

以下属于内部设计目标，不是绝对限制：

- 页面标题：4–12 个中文字符。
- 副标题：12–30 字。
- 卡片解释：20–60 字。
- 普通连续段落：尽量 ≤80 字，超过时优先拆段、列表、折叠或详情。

风险相关文案不机械压缩，包括高风险反馈、危机处理、未成年人保护、紧急求助、医疗边界、重要隐私说明。要求是清楚、准确、能行动。

重复免责声明优先治理为“全页统一边界区 + 必要场景即时安全提示”，避免每个卡片重复完整说明。

# 14. R02：首页优化目标

首页当前功能必须全部保留。改造重点是让用户更容易识别“现在该做什么”，而不是减少首页业务能力。

推荐信息架构：

```text
顶部状态
├─ 问候
└─ 情绪天气

今日行动
└─ 今天的一小步

快捷功能
├─ 测一测
├─ 情绪日记
└─ 三步开始

我的进展
├─ 最近记录
└─ 阶段性反馈

更多支持
├─ 支持性反馈
├─ 训练中心
└─ 人工支持
```

视觉层级可调整，但所有功能必须仍然可达。“三步开始”不得删除；若主要用于 onboarding，已完成用户可降低视觉优先级，但仍必须可再次进入。

首页验收：所有原功能仍存在、所有入口仍可达、首屏层级更清楚、主要行动更明确、重复说明下降、业务路径不变。

# 15. R03：测评结果页重点治理

问题不是功能多本身，而是多种专业信息同时默认展开。

现有结果摘要、风险状态、画像、维度、雷达图、散点信息、匹配说明、优势、建议、训练推荐、讨论问题、详细说明、边界信息和研究数据等底层能力全部保留。

改成分层展示：

## Level 1：核心结果

默认展开：测评名称、核心结论、1–3 个重点结果、一个当前建议。

## Level 2：详细分析

通过“查看详细结果”进入：所有维度、画像、图表、更详细解释、优势、推荐。

## Level 3：专业说明

通过“了解结果如何生成”承载：样本信息、模型说明、算法说明、统计边界、研究说明。

图表治理原则：一个图必须回答一个用户问题。参与者首层建议最多一个主图，其他图进入详细结果，能力保留。

内部研究信息如 modelId、clusterId、PCA、feature 名称、内部研究任务线索、工程字段，不直接删除；如果参与者不需要，则退出默认视图，进入专业详情、研究后台或开发模式。

# 18. R06：项目文档治理

核心问题：很多“当前文件”同时承担历史日志、计划、交接、证据和状态，长期 append 导致读取成本、Token 消耗、旧事实污染、任务漂移和事实冲突增加。

建议结构：

```text
docs/
├── 00_当前事实基准/
├── 01_当前执行入口/
├── 10_产品/
├── 20_技术架构/
├── 30_心理学/
├── 40_测试与质量/
├── 50_运维/
└── 99_历史归档/
```

建立：

```text
docs/00_当前事实基准/当前事实摘要.md
```

只写当前 HEAD、版本、已完成、执行阶段、阻塞、风险、下一步、关键链接，不再写完整历史。

`docs/01_当前执行入口/` 只保留仍有效计划。历史日志按月或按日拆入 `docs/99_历史归档/开发日志/`。

机器可读取状态优先进入：

```text
content/project_state.json
content/release_state.json
artifacts/
```

Markdown 只负责人类可读摘要。

Agent 默认阅读顺序：

```text
1. AGENTS.md
2. 当前事实摘要.md
3. 当前执行计划
4. 与具体任务直接相关的文档
5. 相关代码
```

不要默认读取全部开发日志、全部历史计划、全部旧交接、全部 Registry。

历史内容不删除、不覆盖、不丢失，只归档、索引、标记 superseded。

# 19. R07：前端高耦合治理

优先关注：

```text
ResearchDashboard.tsx
styles.css
apps/miniprogram/services/api.js
assessment-result/index.js
```

重构前后必须保证：路由不变、功能不变、API 行为不变、业务输出不变、用户路径不变、数据不变。只改变职责划分、文件组织、组件边界、函数边界和样式组织。

`ResearchDashboard` 按业务域拆 `hooks/components/services/utils`。不允许“为了拆而拆”；成功标准是职责明确、共享状态减少、可测试性提高、修改影响范围降低。

CSS 先审计重复 selector、重复规则、spacing、颜色、media query、unused class，再按领域拆分。

小程序 API Service 可按领域拆为 `client/assessment/diary/training/reports/program/relationship` 等，但外部接口尽量继续通过 `createSafeHomeApi()`，避免页面大面积改造。

生成代码禁止人工编辑，只能修改 source、generator、build pipeline，生成结果必须可复现。

# 20. R08：后端非权限模块治理

权限相关暂缓。可以优先审查 `models.py`、`database.py`、`profile.py`、`admin.py` 中的纯业务部分。

# 23. R11：功能回归

每一个 UI 改造后必须执行 Function Preservation Gate：

```text
原页面存在？
原入口存在？
原按钮可用？
原API仍调用？
原数据仍显示？
原业务流程完整？
原异常状态有效？
原空状态有效？
原加载状态有效？
```

任一失败即 FAIL。

至少回归七类用户旅程：第一次进入、已使用一段时间、完成测评、写情绪日记、完成训练、查看阶段反馈、需要人工支持。

---

# 24. R12：认知负荷复审

功能测试通过后，再评估：页面目的、首要信息、主要行动、重复文案、术语负担和视觉竞争。

每个页面至少回答五问：

1. 这个页面主要干什么？
2. 我现在最应该看什么？
3. 我现在最应该做什么？
4. 如果我要找其他原有功能，能否找到？
5. 有没有明显重复或看不懂的信息？

如果 UI 更干净了，但旧功能找不到，改造失败。

# 25. Harness

每一个子任务严格执行：

```text
PRECHECK
↓
FUNCTION BASELINE
↓
SCOPE FREEZE
↓
INFORMATION BASELINE
↓
IMPLEMENT
↓
FUNCTION PRESERVATION TEST
↓
STATIC TEST
↓
FUNCTION TEST
↓
UI REVIEW
↓
REGRESSION
↓
INDEPENDENT REVIEW
↓

↓

```

Scope Freeze 每轮明确本轮目标、允许修改文件、禁止修改文件、预计修改量、已有功能清单。如果实际变更范围明显扩张，停止并重新 Scope。

# 26. Commit 原则

一个 Commit 解决一个明确问题。例如：

```text
refactor(ui): reorganize home information hierarchy
refactor(assessment): layer participant result details
refactor(web): split research dashboard modules
docs: introduce compact current-state entrypoint
ci: separate quality jobs
```

不要使用 `optimize everything`、`big update`、`fix project` 等模糊提交。
