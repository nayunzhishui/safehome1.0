## 五A、第一性原理与对抗性发布模型

本节是 F00—F26 的上位约束。计划不以“代码已实现”或“测试变绿”代替真实可发布性，所有整改最终必须回答五个问题：

1. 当前运行的是不是唯一、可追溯、未经替换的批准制品；
2. 每个身份是否只能操作其被授权的对象与动作；
3. 数据、服务、心理内容或外部依赖出错后是否可以发现、停止、恢复和核对；
4. 真实用户是否能理解、完成、退出，并在错误、弱网和旧客户端下安全失败；
5. 平台规则、专业边界、成本和值守能力是否足以持续支持本轮发布规模。

### 5A.1 四类发布结论

| Gate | 核心问题 | 最低证据 | 失败结论 |
|---|---|---|---|
| Product GO | 目标用户能否完成核心闭环且理解边界 | 核心旅程、错误恢复、可用性与支持性文案证据 | NO-GO 或缩小灰度范围 |
| Platform GO | 微信类目、备案、隐私声明、接口权限与审核材料是否匹配实际功能 | 微信后台、备案/类目/隐私和审核记录 | NO-GO，不得以工程绿灯替代 |
| Engineering GO | 制品、权限、数据、迁移、恢复、安全与观测是否可靠 | 唯一 RC、CI、迁移恢复、安全扫描、SBOM、回滚演练 | NO-GO |
| Professional GO | 心理内容、风险升级、人工容量和禁止解释是否可被专业责任链支持 | 内容版本、专业审核、风险流程、值守/关闭策略 | NO-GO 或关闭相应能力 |

正式结论使用：`Release GO = Product GO ∧ Platform GO ∧ Engineering GO ∧ Professional GO`。任何一项未通过，只能输出 NO-GO、受限灰度建议或 `blocked_external`；自动化不得代替负责人、平台或专业人员签字。

### 5A.2 对抗者与故障来源

Threat model 至少覆盖：恶意参与者、被盗研究者账号、内部人员或运维误操作、旧客户端、依赖/CI 供应链、CloudBase 控制面凭据、外部 AI/消息供应商、过期或错绑证据、费用/配额耗尽，以及发布后已经发生的不可逆外部副作用。每个 Fxx 必须说明其覆盖哪些威胁、如何检测、怎样停止、由谁恢复。

### 5A.3 发布人群与能力清单

F01 必须生成版本化 `release_population_manifest`，至少冻结：年龄与风险范围、邀请/自愿条件、单人或多方资料、最大用户数与机构数、地区、开放能力、排除条件和退出路径。未成年人、伴侣/多方数据、个体风险预测等能力若无独立门禁，必须显式关闭；扩大人群或能力会使相应验收证据失效。

### 5A.4 控制面与业务面分离

研究者业务权限不得等同于基础设施权限。Secret、数据库迁移、production 开关、制品发布和回滚由独立控制面管理；研究者页面和业务 API 不得提供这些能力。紧急 `break-glass` 必须限时、说明理由、双人确认或等效控制并完整审计，不能成为常规写路径。

### 5A.5 可信时间、来源与不可逆副作用

- 构建、证据、审计和 SLA 使用明确时区、可信时钟与漂移检查；定时任务同时考虑墙钟与单调时间。
- RC 必须绑定 commit、source tree、lockfile、SBOM、镜像/ZIP hash、构建身份和可验证 provenance/attestation。
- 站内消息、微信订阅消息、AI 外部请求、风险任务、导出和审计属于不可逆或半不可逆副作用；代码回滚不能宣称撤销这些事实，必须有 ledger、对账、补偿、停止和人工核对规则。

## 七B、十一项横向强制门禁

这些门禁适用于所有相关 Fxx。它们不新增业务功能，只防止整改破坏现有用户、跨层合同、性能、UI、数据和发布安全。

| Gate ID | 适用任务 | 强制内容 | 失败处理 |
|---|---|---|---|
| COMPAT-GATE | F01、F06—F09、F11、F20、F26 | 旧账号、旧Token、旧客户端、旧字段、历史结果和历史Consent兼容 | 保持父任务 incomplete，生成兼容性修复工单 |
| CONTRACT-GATE | 所有涉及接口/字段的任务 | 数据库、迁移、后端、API文档、shared、Web、小程序、旧客户端一致 | 禁止只修单端后提交 |
| MIGRATION-GATE | F07、F09、F11、F13、F14、F16—F20 | 合成历史数据迁移、ID/数量/状态/归属比较、回滚与恢复 | 迁移结果不一致即停止后续任务 |

## 八、单任务标准执行 Loop

每个 Fxx 必须严格执行以下顺序：

1. Preflight：读取本计划对应 Fxx、当前事实基准、直接相关模块和 Git 状态。
2. Scope Freeze：登记本轮允许修改文件、禁止修改文件、依赖和回滚点。
3. Failing Contract：先建立能重现差距的失败测试或机器断言。
4. Minimal Implementation：只修改本任务范围，禁止顺手扩展。
5. Targeted Verify：运行专项、权限、异常、并发、迁移和回滚测试。
6. Cross-layer Verify：涉及字段或状态时同步 backend、database、shared、Web、小程序和文档。
7. Plan Backfill：先把修改、原因、文件、测试、风险、回滚和 PR 编号写回本计划 Fxx 执行记录。
8. Independent Review：审查者只读取冻结验收标准、实际 diff、测试证据和回填后的计划，不直接改代码。
9. Review Decision：输出 pass、fix_required 或 blocked_external。
10. Fix Loop：fix_required 时只修审查报告列出的缺陷，然后回到步骤 5；不得跳过重新审查。
11. Commit：只有 review=pass 且必需测试通过后才能单独提交。
12. Push：提交成功后推送远端，并记录 commit、remote branch 和 push 结果。
13. Fact Sync：同步三份事实文档；阶段节点再补完整交接。

### 8.1 Loop 终止规则

- pass：进入下一 Fxx。
- blocked_external：保存证据包和继续条件，不伪造通过；工程任务可继续处理无依赖项。
- fix_required：自动进入下一轮修复。
- 同一根因连续五轮仍失败：停止自动扩大改动，标记 root_cause_unresolved，记录最小复现、已尝试方案和建议；不得用跳过测试、删除断言或放宽权限结束 Loop。
- 发现目标漂移：立即停止实现，重新读取本计划、PR #8 和当前事实基准，修正 scope 后继续。
- 发现与现有核心闭环冲突：优先保持目标→记录→反馈→训练→追踪→支持链路，登记 feature_conflict。
