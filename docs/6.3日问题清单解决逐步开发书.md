## 0. 文档定位

本文件不是普通建议书，而是**开发施工文档**。Codex 执行时应把本文档作为任务来源，按阶段、按任务编号逐个处理。

本轮开发的核心不是继续堆新功能，而是完成以下五类加固：

```text
1. 风险安全：所有自由文本入口先做风险预检，高风险不进入普通反馈和训练卡。
2. 权限与审计：后台导出、敏感查看、风险复核必须有权限和日志。
3. 数据治理：正式试用不能继续依赖 demo-parent，必须使用匿名 user_id。
4. 内容质量：训练卡、反馈规则、风险词库必须可校验、可审核、可追踪版本。
5. 工程验证：风险、反馈、画像、导出必须有自动化测试和提交前检查。
```

## 1. Codex 执行总原则

Codex 每次执行任务前，必须先阅读本节，并严格遵守。

### 1.1 一次只做一个任务

每次只执行一个明确编号的任务，例如：

```text
P0-01 反馈接口统一接入风险预检
```

禁止一次性同时处理：

```text
风险预检 + UI 重构 + 数据库迁移 + 文档同步 + 大模型接入
```

如果发现当前任务需要修改其他模块，应先写入“阻塞说明”，等待人工确认。

### 1.2 不做大重构

除非任务明确要求，否则不要：

```text
- 重构整个 Flask 后端；
- 把 Flask 换成 FastAPI；
- 把 SQLite 换成 PostgreSQL；
- 把 React 手动路由一次性改成 React Router；
- 重写整个小程序；
- 删除已有页面、API、内容库或历史文档。
```

当前阶段优先采用**最小、最稳、最容易解释**的实现方式。

### 1.3 不越过心理伦理边界

所有用户端文案必须符合：

```text
非诊断、非标签化、支持性、非评判、聚焦具体事件和可练习动作。
```

禁止出现或强化以下表达：

```text
AI诊断
心理治疗
危机干预
系统判断你有问题
人格异常
家庭病态
孩子有心理疾病
本系统能处理自杀/自伤/家暴等危机
沙盘潜意识诊断
```

允许使用：

```text
可能
看起来
这次记录中可以看到
可以尝试
支持性反馈
阶段性画像
压力反应观察
练习位置
需要时寻求现实支持或专业帮助
```

### 1.4 内容扩展优先改 content，不优先改代码

如果只是新增训练卡、反馈规则、伦理文案、隐私文本，应优先修改：

```text
content/training_cards.json
content/feedback_rules.json
content/risk_keywords.json
content/assessment_worksheets.json
content/consent.md
content/privacy.md
```

不要为了简单内容扩展就修改后端、数据库或小程序页面。

### 1.5 不提交运行产物和敏感配置

禁止提交：

```text
node_modules
dist
*.db
*.sqlite
venv
.venv
__pycache__
*.pyc
.pytest_cache
.env.local
.env.production
```

## P0-01 反馈接口统一接入风险预检

执行状态：已完成，见 `docs/当前进度交接.md` 第 84 节。

### 任务目标

在家长端反馈生成前统一调用 `services.risk_service.check_text_risk()`，确保 high 风险文本不会进入普通反馈生成流程。

### 任务等级

```text
P0 阻断问题
```

### 涉及文件

```text
backend/routes/feedback.py
backend/services/risk_service.py
backend/services/feedback_service.py
backend/tests/test_risk_service.py
backend/tests/test_feedback_route.py 或 backend/tests/test_feedback_service.py
```

### 不得修改

```text
- 不改小程序页面；
- 不改 Web 页面；
- 不接入大模型；
- 不删除 generate_feedback；
- 不改变 low 风险原有反馈流程；
- 不重构整个后端。
```

### 具体修改步骤

1. 在 `backend/routes/feedback.py` 中导入：

```python
from services.risk_service import check_text_risk
```

2. 在调用 `generate_feedback(source_payload)` 前，提取以下字段：

```python
risk_text = [
    source_payload.get("event_description"),
    source_payload.get("automatic_thought"),
    source_payload.get("behavior"),
    source_payload.get("free_text"),
]
```

3. 调用：

```python
risk_result = check_text_risk(risk_text, source="feedback")
```

4. 如果：

```python
risk_result["allow_auto_feedback"] is False
```

则：

```text
- 不调用 generate_feedback；
- tags 返回 []；
- recommended_card_ids 返回 []；
- supportive_feedback 使用 risk_result["safe_response"]；
- alternative_response 使用 risk_result["boundary_notice"]；
- risk_level 保存为 risk_result["risk_level"]；
- 返回 ok=true，status=201；
- 为后续 create_risk_review_record 预留 TODO。
```

5. 如果 `risk_level=medium`：

```text
- 可以继续生成支持性反馈；
- 返回 risk 字段；
- 后续页面可提示现实支持；
- 不要用恐吓式表达。
```

6. 如果 `risk_level=low`：

```text
- 保持原有 generate_feedback 流程；
- 不影响训练卡推荐。
```

### 验收标准

```text
1. 输入“我不想活了”时，recommended_card_ids=[]。
2. high 风险时不返回普通训练卡。
3. high 风险时 supportive_feedback 来自 safe_response。
4. high 风险时 alternative_response 来自 boundary_notice。
5. low 风险时原反馈规则仍正常。
6. feedback_results 中 risk_level 保存正确。
7. pytest 通过。
```

### 推荐测试用例

```python
def test_feedback_high_risk_blocks_training_cards(client):
    response = client.post("/api/feedback/generate", json={
        "user_id": "parent_test_001",
        "event_description": "我不想活了",
        "automatic_thought": "撑不下去了",
        "behavior": "一直哭"
    })
    data = response.get_json()["data"]
    assert data["risk_level"] == "high"
    assert data["recommended_card_ids"] == []
    assert data["risk"]["allow_auto_feedback"] is False
```

### 目标

把学生画像从 `assessment_results` 中拆出独立表，支持画像版本、置信度、复测变化和风险状态追踪。

### 禁止

```text
不要在 P0/P1 未完成前执行。
```

### 目标

建立统一研究导出视图或表，把业务数据转成脱敏、结构化、可分析的数据。

### 目标

## P3-06 GitHub Actions

### 目标

# 8. 禁止上线条件

如果存在以下任一问题，不允许进入真实用户试用：

```text
1. high 风险文本仍返回普通训练卡。
2. 后台导出无需权限。
3. 导出无审计日志。
4. 用户数据仍统一写入 demo-parent。
5. 用户端出现诊断化、人格化、病理化表达。
6. 小程序主流程无法走通。
7. Web 后台无法查看基本数据。
8. 隐私政策、用户协议、非诊断声明完全缺失。
9. 风险测试无法通过。
10. 仓库中出现真实 token、数据库文件或生产密钥。
```

# 11. 结论

当前 safehome1.0 的核心开发策略不是“大换血”，而是**在现有技术栈上做安全、工程、内容和体验加固**。

最重要的顺序是：

```text
先修风险安全 -> 再修权限审计 -> 再修内容校验 -> 再修自动测试 -> 再修用户体验 -> 最后考虑长期架构升级
```

Codex 必须严格按任务编号推进，不允许一次性扩展范围。每一步都要保证项目仍然可运行、可解释、可回滚、可验收。
