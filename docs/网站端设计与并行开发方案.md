# 网站端设计与并行开发方案

更新时间：2026-05-21

本文档用于指导 `safehome1.0 / 安心陪伴 / ReadFeedback` MVP 1.1 阶段的网站端设计和小程序端、网站端并行开发。本文档只做规划，不包含业务代码实现。

进度说明：截至 2026-06-01，网站端第一版已经实现 `/`、`/dashboard`、`/goals`、`/diaries`、`/feedback`、`/checkins`、`/reports`、`/supervision`、`/content/cards`、`/content/rules`、`/export` 和 `/integration-test`。当前最新进度以 `docs/项目进度统一口径.md` 为准，本文更多作为网站端设计依据和后续优化参考。

## 一、网站端定位

### 1. 网站前台

网站前台面向试点合作方、家长、研究人员、督导老师和项目介绍场景，主要承担：

1. 项目展示：说明安心陪伴是什么、解决什么问题、如何支持家长练习非评判陪伴。
2. 试点招募：介绍适合参与试点的家庭、合作学校或机构、参与方式和联系方式。
3. 使用说明：解释小程序端如何记录、反馈、练习、打卡和查看周报。
4. 伦理边界：明确系统不是诊断工具，不替代心理咨询、医学诊断、危机干预或法律判断。

### 2. 网站后台

网站后台面向项目管理员、研究人员和督导老师，主要承担：

1. 数据管理；
2. 情绪记录查看；
3. 训练卡管理；
4. 反馈规则查看；
5. 周报查看；
6. 督导请求查看与处理；
7. 数据导出。

网站后台不是家长日常使用入口，而是研究管理、内容管理和试点评估工具。

### 3. 与小程序端的关系

网站端不复制小程序端的日常使用流程。

小程序端仍然是家长主要使用入口，负责：

1. 目标设定；
2. 情绪事件记录；
3. 即时反馈查看；
4. 训练卡练习；
5. 练习打卡；
6. 简版周报查看；
7. 人工督导请求提交。

网站端负责展示、管理、查看、评估和导出，不应把家长每天要完成的记录和练习流程搬到网页端重新做一遍。

## 二、网站前台页面设计

### 1. 首页 Hero 区

目标：第一屏清楚传达项目定位，让访问者知道这是一个面向家长的非诊断陪伴训练系统。

建议内容：

1. 主标题：安心陪伴，帮助家长练习更稳定的亲子回应。
2. 副标题：基于 UP 跨诊断情绪调节思路，支持家长记录情绪事件、识别互动模式、获得非评判反馈和练习建议。
3. 主按钮：了解试点计划。
4. 次按钮：查看使用方式。
5. 边界提示：本系统不提供诊断，不替代心理咨询、医学诊断、危机干预或法律判断。

视觉建议：

1. 绿色为主色；
2. 大面积留白；
3. 温和插图或真实场景图片；
4. 避免医疗化、治疗化、诊断化视觉。

### 2. 核心闭环展示区

目标：展示 MVP 1.1 核心链路。

闭环：

```text
目标设定 -> 情绪记录 -> 模式识别 -> 支持性反馈 -> 训练卡练习 -> 打卡追踪 -> 周度复盘 -> 必要时督导补充
```

展示方式：

1. 使用横向或纵向步骤卡片；
2. 每一步配一个线性图标；
3. 每张卡只写一句支持性说明；
4. 强调练习和复盘，不强调评估或诊断。

### 3. 理论基础区

目标：用普通用户能理解的语言介绍理论来源。

建议内容：

1. UP 跨诊断情绪调节框架；
2. 情绪、想法、身体感觉和行为之间的相互影响；
3. 非评判觉察；
4. 家长回应方式的练习；
5. 小步练习和持续复盘。

文案边界：

1. 不宣称治疗效果；
2. 不承诺改善诊断症状；
3. 不使用“治疗儿童问题”“矫正人格”等表达；
4. 使用“支持练习”“帮助观察”“提供参考”。

### 4. 使用场景区

目标：说明系统适合哪些普通家庭练习场景。

建议场景：

1. 作业拖延；
2. 起床、睡前、出门等日常冲突；
3. 情绪爆发后的复盘；
4. 家长希望减少催促、指责、争吵；
5. 家长希望练习暂停、倾听、描述期待和共同解决。

不建议写成：

1. 适用于焦虑症；
2. 适用于抑郁症；
3. 适用于行为障碍；
4. 适用于家庭病理问题。

### 5. 功能介绍区

目标：介绍小程序和后台各自能力。

前台功能介绍应分成两组：

1. 家长小程序：
   - 设定本周小目标；
   - 记录一次具体情绪事件；
   - 查看支持性反馈；
   - 获取训练卡建议；
   - 完成轻打卡；
   - 查看周度复盘；
   - 必要时提交督导请求。
2. 研究与管理后台：
   - 查看目标、记录、反馈、打卡和周报；
   - 管理训练卡内容；
   - 查看反馈规则；
   - 查看督导请求；
   - 导出脱敏数据。

### 6. 伦理边界区

目标：把伦理边界作为网站前台的固定内容，而不是藏在底部小字。

必须明确：

1. 所有反馈都是非诊断、非标签化、支持性、非评判的练习建议；
2. 系统不会判断孩子、家长或家庭是否存在某种疾病或人格问题；
3. 高风险内容只提示风险和督导入口；
4. 系统不替代心理咨询、医学诊断、危机干预或法律判断；
5. 研究或试点数据使用必须经过知情同意；
6. 导出数据必须考虑脱敏。

### 7. 试点招募区

目标：承接项目试点报名和合作咨询。

建议内容：

1. 适合参与者：
   - 希望练习亲子沟通的家长；
   - 愿意进行一段时间记录和练习的家庭；
   - 愿意参与匿名化研究反馈的试点对象。
2. 不适合仅依赖本系统处理的情况：
   - 急性危机；
   - 自伤、自杀或伤害他人风险；
   - 严重暴力、虐待、忽视；
   - 需要医学诊断、心理治疗或法律介入的情况。
3. 试点流程：
   - 了解项目；
   - 完成知情同意；
   - 使用小程序记录和练习；
   - 后台进行研究和督导管理；
   - 结束后收集反馈。

## 三、网站后台页面设计

### 后台整体原则

后台偏研究管理，不做家长日常练习入口。后台页面应优先服务：

1. 数据能否看清；
2. 小程序提交的数据是否完整；
3. 规则反馈是否符合非诊断边界；
4. 训练卡是否能复用；
5. 周报和督导请求是否便于试点评估；
6. 导出是否便于脱敏分析。

### 1. `/dashboard` 总览页

页面目标：

展示项目运行概况，帮助管理员快速判断当前试点是否正常运行。

核心字段：

1. 目标数量；
2. 情绪记录数量；
3. 已生成反馈数量；
4. 训练卡数量；
5. 打卡数量；
6. 周报数量；
7. 待处理督导请求数量；
8. 最近记录和最近督导请求。

需要调用的 API：

1. `GET /api/goals`
2. `GET /api/diaries`
3. `GET /api/checkins`
4. `GET /api/cards`
5. `GET /api/weekly-report`
6. `GET /api/admin/export?type=feedback`
7. `GET /api/admin/export?type=supervision`

是否需要新增 API：

建议新增 `GET /api/admin/summary`，用于一次性返回后台总览指标。MVP 1.1 第一阶段也可以先用现有列表和导出接口拼出总览。

是否需要改数据库：

第一阶段不需要。

与小程序端哪个功能对应：

对应小程序端完整核心链路：目标、记录、反馈、训练、打卡、周报、督导。

用户研究或试点评估中的用途：

用于观察试点活跃度、数据完整度、练习完成情况和督导需求规模。

### 2. `/goals` 目标管理页

页面目标：

查看家长在小程序端设定的本周目标，判断目标是否具体、可练习、可追踪。

核心字段：

1. `id`
2. `user_id`
3. `scene`
4. `smart_goal`
5. `motivation`
6. `status`
7. `created_at`
8. 关联情绪记录数量

需要调用的 API：

1. `GET /api/goals`
2. 后续可选：`GET /api/diaries?user_id=...`

是否需要新增 API：

第一阶段不需要。后续如需按目标查看记录，可新增 `GET /api/diaries?goal_id=...`。

是否需要改数据库：

第一阶段不需要。

与小程序端哪个功能对应：

对应小程序 `pages/goal-setting/index`。

用户研究或试点评估中的用途：

用于评估家长目标设定质量、常见冲突场景、练习意愿和目标完成基础。

### 3. `/diaries` 情绪记录列表页

页面目标：

集中查看小程序端提交的情绪事件记录，支持筛选、查看详情和追踪记录质量。

核心字段：

1. `id`
2. `user_id`
3. `goal_id`
4. `event_text`
5. `emotion`
6. `intensity`
7. `thought`
8. `body_signal`
9. `behavior`
10. `child_reaction`
11. `short_term_result`
12. `long_term_effect`
13. `created_at`

需要调用的 API：

1. `GET /api/diaries`
2. 可选：`GET /api/goals`

是否需要新增 API：

第一阶段不需要。后续建议新增筛选参数：`goal_id`、`emotion`、`date_from`、`date_to`。

是否需要改数据库：

如果现有 `emotion_diaries` 表已经能承载上述字段，则不需要。若缺少 `body_signal`、`child_reaction`、`short_term_result`、`long_term_effect`，应先在小程序记录升级阶段统一规划，不由网站端单独改。

与小程序端哪个功能对应：

对应小程序 `pages/diary-form/index`。

用户研究或试点评估中的用途：

用于分析家长记录是否围绕具体事件、情绪强度是否可追踪、亲子互动模式是否逐渐清晰。

### 4. `/diaries/:id` 情绪记录详情页

页面目标：

查看单条情绪记录的完整上下文，以及其目标、反馈、训练卡推荐和打卡关联。

核心字段：

1. 记录基础字段；
2. 关联目标；
3. 生成的反馈；
4. 命中的规则标签；
5. 推荐训练卡；
6. 后续打卡记录；
7. 是否产生督导请求。

需要调用的 API：

1. `GET /api/diaries`
2. `POST /api/feedback/generate`
3. `GET /api/cards/recommend`
4. `GET /api/checkins`
5. `GET /api/goals`

是否需要新增 API：

建议新增 `GET /api/diaries/:id`，避免详情页依赖列表数据。后续可新增 `GET /api/diaries/:id/related` 返回关联目标、反馈、训练卡和打卡。

是否需要改数据库：

第一阶段不需要。只有在需要保存更多关联状态时再评估。

与小程序端哪个功能对应：

对应小程序情绪记录提交后的反馈查看和训练卡推荐流程。

用户研究或试点评估中的用途：

用于人工检查规则反馈是否合适、训练卡推荐是否贴合事件、记录质量是否足以支持后续分析。

### 5. `/feedback` 反馈结果查看页

页面目标：

集中查看规则生成的反馈结果，检查文案是否非诊断、非标签化、支持性、非评判。

核心字段：

1. `id`
2. `diary_id`
3. `user_id`
4. `matched_tags`
5. `pattern_summary`
6. `supportive_feedback`
7. `recommended_card_ids`
8. `created_at`

需要调用的 API：

1. `GET /api/admin/export?type=feedback`
2. `POST /api/feedback/generate`
3. `GET /api/diaries`

是否需要新增 API：

建议新增 `GET /api/feedback` 和 `GET /api/feedback/:id`，让后台不依赖 CSV 导出查看反馈。

是否需要改数据库：

第一阶段不需要。

与小程序端哪个功能对应：

对应小程序 `pages/feedback-result/index`。

用户研究或试点评估中的用途：

用于抽查反馈边界、统计常见模式标签、评估训练卡推荐规则是否稳定。

### 6. `/checkins` 练习打卡记录页

页面目标：

查看家长是否完成训练卡练习，以及练习后的自我观察。

核心字段：

1. `id`
2. `user_id`
3. `card_id`
4. `diary_id`
5. `done`
6. `note`
7. `created_at`
8. 训练卡标题

需要调用的 API：

1. `GET /api/checkins`
2. `GET /api/cards`
3. 可选：`GET /api/diaries`

是否需要新增 API：

第一阶段不需要。后续可增加 `card_id`、`diary_id`、`date_from`、`date_to` 筛选参数。

是否需要改数据库：

第一阶段不需要。

与小程序端哪个功能对应：

对应小程序 `pages/checkin/index` 和训练卡练习完成流程。

用户研究或试点评估中的用途：

用于评估训练卡是否被使用、哪些卡更容易完成、练习后的备注是否显示出可持续练习价值。

### 7. `/reports` 周度报告页

页面目标：

查看每个用户或试点家庭的周度复盘，帮助研究人员观察练习趋势。

核心字段：

1. `user_id`
2. `week_start`
3. `diary_count`
4. `checkin_count`
5. `common_emotions`
6. `common_tags`
7. `completed_cards`
8. `summary`
9. `created_at`

需要调用的 API：

1. `GET /api/weekly-report`
2. `GET /api/diaries`
3. `GET /api/checkins`

是否需要新增 API：

建议新增 `GET /api/reports` 用于后台列表。现有 `GET /api/weekly-report` 更适合生成或查看单个用户单周报告。

是否需要改数据库：

第一阶段不需要。

与小程序端哪个功能对应：

对应小程序 `pages/weekly-report/index`。

用户研究或试点评估中的用途：

用于观察一周内记录频率、练习频率、常见情绪和常见互动模式。

### 8. `/supervision` 人工督导请求页

页面目标：

查看家长提交的人工督导请求，支持研究人员或督导老师判断是否需要进一步回应。

核心字段：

1. `id`
2. `user_id`
3. `diary_id`
4. `reason`
5. `message`
6. `status`
7. `created_at`
8. 关联记录摘要

需要调用的 API：

1. `POST /api/supervision`
2. `GET /api/admin/export?type=supervision`
3. 可选：`GET /api/diaries`

是否需要新增 API：

建议新增 `GET /api/supervision` 和 `PATCH /api/supervision/:id`，用于后台查看和更新处理状态。

是否需要改数据库：

如果现有 `supervision_requests` 表已有 `status`，第一阶段不需要。若缺少处理备注、处理人、处理时间，可在后续督导流程成熟后再新增字段。

与小程序端哪个功能对应：

对应小程序人工督导入口。

用户研究或试点评估中的用途：

用于识别哪些场景更容易触发人工支持需求，并记录督导响应流程。

### 9. `/content/cards` 训练卡管理页

页面目标：

查看和管理训练卡内容，保证训练卡和小程序推荐逻辑一致。

核心字段：

1. `id`
2. `title`
3. `category`
4. `tags`
5. `goal`
6. `steps`
7. `practice_tip`
8. `is_active`

需要调用的 API：

1. `GET /api/cards`
2. `GET /api/cards/recommend`

是否需要新增 API：

第一阶段可只读，不新增。若要后台编辑，需要新增 `POST /api/cards`、`PATCH /api/cards/:id`，并决定是否仍以 `content/training_cards.json` 为主数据源。

是否需要改数据库：

第一阶段不需要。训练卡优先复用 `content/training_cards.json`。

与小程序端哪个功能对应：

对应小程序 `pages/training-card/index` 和训练卡推荐流程。

用户研究或试点评估中的用途：

用于检查训练卡是否覆盖常见场景，统计哪些卡更常被推荐或完成。

### 10. `/content/rules` 反馈规则查看页

页面目标：

查看反馈规则和标签，保证规则文案符合非诊断边界。

核心字段：

1. `id`
2. `tag`
3. `keywords`
4. `pattern_summary`
5. `supportive_feedback`
6. `recommended_card_ids`
7. `risk_hint`

需要调用的 API：

1. 当前可直接由前端构建时读取或后端间接使用 `content/feedback_rules.json`
2. `POST /api/feedback/generate`

是否需要新增 API：

建议新增 `GET /api/content/rules`，让网站后台以只读方式查看规则。编辑规则应后置。

是否需要改数据库：

第一阶段不需要。反馈规则优先复用 `content/feedback_rules.json`。

与小程序端哪个功能对应：

对应小程序反馈生成和模式识别卡。

用户研究或试点评估中的用途：

用于伦理审查、规则质量抽查、模式标签统计和训练卡推荐逻辑复核。

### 11. `/export` 数据导出页

页面目标：

提供研究和试点评估所需的脱敏数据导出入口。

核心字段：

1. 导出类型：`goals`、`diaries`、`feedback`、`checkins`、`reports`、`supervision`、`cards`
2. `user_id` 筛选；
3. 日期范围；
4. 脱敏选项；
5. 导出说明；
6. 管理员令牌输入。

需要调用的 API：

1. `GET /api/admin/export`

是否需要新增 API：

## 五、UI / 美术规范

### 1. 色彩

1. 主色使用绿色；
2. 推荐主色方向：柔和深绿、薄荷绿、浅灰绿；
3. 背景可使用白色、浅灰、极浅绿色；
4. 少用红色，红色只用于高风险提示、错误状态或必须注意的信息；
5. 不使用高饱和大面积警示色。

### 2. 风格

整体风格应温和、专业、低压力、可信。

前台偏项目展示：

1. 留白更多；
2. 结构清楚；
3. 文案温和；
4. 展示项目价值和边界。

后台偏研究管理：

1. 信息密度更高；
2. 表格、筛选、详情页清晰；
3. 卡片式分组；
4. 便于快速查看数据状态。

### 3. 布局

1. 使用卡片式布局；
2. 卡片用于单条数据、统计指标、页面分区和详情模块；
3. 列表页优先使用表格加筛选区；
4. 详情页优先使用左侧记录内容、右侧关联信息或规则结果；
5. 移动端前台要清晰，后台以桌面端优先。

### 4. 图标

1. 使用线性图标；
2. 图标含义要具体，例如目标、记录、反馈、训练、周报、督导、导出；
3. 不使用医疗诊断类图标强化“治疗”暗示。

### 5. 按钮文案

按钮文案避免命令式，保持支持性。

推荐：

1. 查看记录；
2. 了解详情；
3. 查看反馈；
4. 查看练习卡；
5. 继续查看；
6. 导出数据；
7. 标记为已查看。

避免：

1. 立即纠正；
2. 诊断问题；
3. 判定风险；
4. 处理异常儿童；
5. 强制完成。

## 六、心理学与伦理要求

### 1. 反馈边界

所有反馈都必须满足：

1. 非诊断；
2. 非标签化；
3. 支持性；
4. 非评判；
5. 聚焦具体事件、情绪、想法、身体感觉、行为和可练习动作。

### 2. 后台展示边界

网站后台也不得展示诊断性标签。

后台可以展示：

1. 情绪词；
2. 互动模式提示；
3. 规则标签；
4. 训练卡标签；
5. 风险提示；
6. 督导状态。

后台不得展示：

1. 疾病诊断；
2. 人格标签；
3. 对孩子或家长的病理化判断；
4. 对家庭关系的定性判断。

### 3. 高风险内容

高风险内容只做风险提示和督导入口。

高风险内容包括但不限于：

1. 自伤、自杀；
2. 伤害他人；
3. 严重暴力；
4. 虐待或忽视；
5. 急性精神危机；
6. 需要法律或医学介入的情况。

系统不应自动给出危机干预指令，不应替代专业人员判断。

### 4. 系统边界

系统不替代：

1. 心理咨询；
2. 医学诊断；
3. 危机干预；
4. 法律判断；
5. 学校或机构正式处置流程。

### 5. 数据导出脱敏

导出数据必须考虑脱敏。

导出前应检查：

1. 是否包含真实姓名、电话、地址、学校、班级等直接身份信息；
2. 是否包含可识别具体儿童或家庭的长文本；
3. `user_id` 是否需要匿名化；
4. 时间字段是否需要按研究需要降精度；
5. 督导请求中是否包含高敏感描述；
6. 导出文件是否只给授权人员使用。

## 九、回滚方案

网站端开发出错时，必须保证不影响小程序端核心流程。

### 1. 路由隔离

网站端页面只修改 `apps/web`，不应为了后台展示随意改小程序页面。

如果网站端某个页面出错：

1. 先隐藏该页面导航入口；
2. 保留已稳定的小程序入口；
3. 保留后端核心 API。

### 2. API 兼容

新增后台 API 时必须保持兼容：

1. 不删除已有 API；
2. 不重命名已有字段；
3. 不改变已有响应结构；
4. 新增字段应为可选字段；
5. 小程序端仍能调用 `POST /api/diaries`、`POST /api/feedback/generate`、`GET /api/cards/recommend`、`POST /api/checkins`。

### 3. 数据库变更谨慎

网站端不应单独推动破坏性数据库变更。

如果必须改数据库：

1. 先写文档；
2. 明确旧字段如何兼容；
3. 确认小程序端不受影响；
4. 保留旧数据读取能力；
5. 优先新增字段，不删除字段。

### 4. 内容规则回滚

训练卡和反馈规则优先通过 `content` 文件维护。

如果规则更新导致反馈不稳定：

1. 回退 `content/feedback_rules.json` 到上一版；
2. 回退 `content/training_cards.json` 到上一版；
3. 保持小程序核心链路可继续运行。

### 5. 最小可用保底链路

无论网站端开发是否完成，都必须保留：

```text
小程序情绪事件记录 -> 后端创建记录 -> 生成非诊断反馈 -> 推荐训练卡
```

同时保留：

1. `pages/integration-test/index`；
2. `POST /api/diaries`；
3. `POST /api/feedback/generate`；
4. `GET /api/cards/recommend`；
5. `GET /api/admin/export`。
