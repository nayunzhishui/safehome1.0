# 任务十二后前端优化计划

更新时间：2026-07-10

## 1. 当前后端已经提供什么

前端不需要再自行拼接业务数据。后端现已统一提供：三份关系测评、精确维度计分、三份题项级画像模型、画像落点、第二阶段报名、初筛报告、报告人工确认与消息发送、关系绘画、句子补全、研究者备注、探索手记、每周补充测量、关键事件、变化曲线、时间轴、成长报告和四层画像。

前端的下一阶段重点应从“补入口”转为“把复杂状态解释清楚、把敏感材料操作做稳、把研究者工作流做快”。

## 2. 优化原则

1. 保持小程序是学生/家长日常入口，Web是研究者复核入口，不复制两套字段和业务规则。
2. 一个页面只保留一个主动作；报告状态、复核状态、风险状态用清楚的文字，不靠颜色单独表达。
3. 使用安静、可信、有人味的视觉语言：暖白底、低饱和绿、克制橙色提示，避免医院感、AI渐变、营销大卡片和过多阴影。
4. 画像始终写“阶段性位置”“探索线索”，不使用人格类型、病理模式或关系能力排名。
5. 绘画、句子补全和开放叙事默认按高敏感材料设计：授权先于编辑、保存状态可见、退出前提示、原文不出现在列表摘要。

## 3. P0：试点前必须完成

### P0-1 角色与入口状态

- 小程序“训练”页的关系试点入口根据账号角色展示；非学生账号显示“当前仅向学生试点账号开放”，不进入报名失败页。
- “我的”页研究者入口区分：未登录、普通账号、研究者账号、令牌过期四种状态。
- Web研究平台在管理员令牌/研究者登录缺失时显示明确登录或令牌修复动作，避免整页通用错误。

验收：普通用户不能看到研究档案；研究者可以稳定进入；403/401文案不同。

### P0-2 报告状态机

- 报告页顶部固定显示：待人工复核、可查看、研究者已确认、已发送。
- `pending_review`时保留维度和边界，但弱化明确画像名，并解释“为什么暂不做明确解释”。
- 研究者端把“生成→复核→确认→发送”做成四步状态条；发送前二次确认收件人匿名信息和报告版本。
- 用户下载从当前JSON本地保存升级为排版稳定的PDF/长图；下载文件不含内部字段、模型中心或研究备注。

验收：未确认报告无法发送；用户与研究者看到同一版本；下载不泄漏内部字段。

### P0-3 敏感材料编辑与恢复

- 绘画画布保存画布宽高和坐标比例，研究者预览按比例缩放，避免不同设备变形。
- 增加撤销、重做、保存中、已保存和退出前确认；弱网失败时保留本地草稿。
- 句子补全支持逐题折叠和“只答愿意回答的题”；不在页面列表展示原文摘要。
- 高风险预检后显示现实支持提示，不生成普通自动解释。

验收：真机横竖屏、不同尺寸画布不变形；断网恢复不丢内容；高风险进入人工队列。

### P0-4 人工可用性与无障碍验收

- 微信开发者工具和至少一台iOS/Android真机完成报名、测评、报告、消息、绘画、句子、成长记录全链路。
- 触控目标不小于44px等效尺寸；文字对比达到WCAG 2.1 AA；Canvas提供文字替代说明。
- 所有表单有字段标签、错误定位、字符上限和提交成功反馈。

## 4. P1：提升理解与复核效率

### P1-1 关系试点信息架构

把当前入口整理为五个稳定阶段：

```text
1 起点测评 -> 2 阶段性报告 -> 3 线上探索任务 -> 4 研究者反馈 -> 5 连续记录
```

首页显示“当前步骤”和一个主动作；其它入口放在次级列表，避免五个并列按钮造成选择负担。

### P1-2 画像和四层逻辑可视化

- 基础画像：保留落点和维度雷达。
- 矛盾画像：用两列或连接线呈现“意愿—行动”“靠近—保护”张力，不用红绿好坏色。
- 机制画像：显示为“待核对假设”卡片，并提供“符合/不符合/不确定”的共同修订控件。
- 动态画像：用真实时间轴和折线展示多次记录；只有两次以上才显示趋势箭头。

### P1-3 成长仪表盘

- 当前文本点位升级为轻量折线图，允许选择维度；次数指标和1-5量尺分开坐标，不混在一张图。
- 时间轴按测评、任务、关键事件、报告、研究者反馈分组，并可筛选。
- 成长报告明确区分“用户原话”“系统汇总”“研究者确认”，防止来源混淆。

### P1-4 研究者工作台

- Web使用三栏结构：左侧待办/档案列表，中间用户时间轴与材料，右侧报告复核和备注。
- 提供待复核、待确认、待发送、高风险优先四个筛选器。
- 画像、维度、评估问题、任务材料、备注和报告版本在同一档案中，不要求研究者跨页面来回跳转。
- 所有敏感材料默认折叠，点击查看时再次记录审计。

## 5. P2：性能与长期维护

1. Web当前构建主包约1.63MB、gzip约489KB。按路由拆分ECharts、研究者平台、内容后台和ReadFeedback集成页面，目标首屏JS gzip低于250KB。
2. 抽出关系试点共享类型和状态标签组件，继续以 `shared/types/api.ts` 为唯一契约，不在小程序和Web各写一套状态映射。
3. 将雷达、散点、折线图统一为“有数据/数据不足/低置信度/离群/加载失败”五态组件。
4. 增加不含敏感原文的产品事件：入口点击、步骤完成、报告确认、下载成功、任务保存失败；不采集绘画、句子或开放叙事正文。
5. 后续如做站内提醒，只发送中性提醒，不在系统通知预览中暴露“亲密关系”“风险”等敏感主题。

## 6. 推荐实施顺序

| 批次 | 范围 | 主要文件 | 自动验收 |
|---|---|---|---|
| 1 | 角色入口、报告状态、错误态 | `pages/profile`、`relationship-pilot`、`relationship-report`、Web `ResearchDashboard` | JS/JSON检查、Web build、权限测试 |
| 2 | 绘画坐标、草稿恢复、句子体验 | `relationship-task`、任务API | 真机画布矩阵、弱网恢复测试、风险测试 |
| 3 | 五阶段信息架构、四层画像 | `relationship-pilot`、`assessment-result`、报告组件 | 截图对比、可读性与边界文案审查 |
| 4 | 成长曲线和时间轴 | `relationship-growth`、Web研究档案 | 两次/多次/缺失数据状态测试 |
| 5 | Web拆包和共享组件 | Vite路由、图表组件、shared类型 | bundle分析、首屏性能、回归build |

每批只做一个清晰目标，先复用当前API和表，不为视觉优化新增第二套数据结构。
