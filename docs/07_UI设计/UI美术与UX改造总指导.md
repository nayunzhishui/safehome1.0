# UI 美术与 UX 改造总指导

本文件是安心陪伴项目 UI、UX、美术设计、Figma 复现和前端视觉实现的唯一通用规则。每次开始用户研究、UI/UX 设计、视觉审查、可用性测试、Figma 或前端视觉改造前，必须完整阅读本文件。

本文件解决一个问题：让产品需求、ImageGen、Figma 和真实页面形成可审核的同一条链路，同时保护后端、数据结构和业务逻辑。

## 1. 文档地位与适用范围

本文件适用于：

- 微信小程序全部正式页面；
- 网站前台与网站后台；
- 公共组件、Design Tokens、插画、图标和动效；
- ImageGen 概念图、Figma 设计系统与前端真实实现；
- 真机检查、无障碍检查、Loop 审核和 Harness 验收。

规则冲突时按以下优先级处理：

1. 用户在当前任务中的明确要求；
2. `AGENTS.md` 和当前事实基准；
3. 本文件；
4. 当前页面的需求冻结版；
5. 网站或专项页面的独立方案；
6. 历史日志、旧任务卡和旧效果图。

历史设计不能自动覆盖当前真实页面。页面数量、路由、组件和 token 必须从代码重新读取，不能沿用旧文档中的静态数字。

## 2. 产品目标与伦理边界

安心陪伴是家长非评判陪伴训练系统。界面应帮助用户记录具体事件、理解互动线索、获得支持性反馈并完成可练习的行动，不承担诊断、治疗或人格判断。

所有用户可见内容必须：

- 使用“支持性测评”“阶段性观察”“自我了解线索”“压力管理线索”等表达；
- 聚焦具体场景、感受、行为和下一步行动；
- 使用“可能”“看起来”“这次记录中可以看到”等保守措辞；
- 高风险内容只提供明确的人工支持、督导或转介入口；
- 明确系统不能替代临床诊断、治疗和危机干预。

禁止使用诊断、筛查、病理化、人格定性、责备、恐吓或治疗承诺。不得将不同量尺合并成虚假的“健康分”“成长分”或精确概率。

## 3. 当前改造总目标

全部页面都要审查和改造，但严格一次只处理一个页面。每个页面独立完成需求冻结、设计确认、Figma、前端实现、本地 Loop 1–4 与四类 Harness 后，才能进入下一页。真机验收按 2026-08-10 用户冻结要求统一延期到全部页面本地完成之后，不再作为逐页推进的阻断门禁。

改造的共同目标是：

- 降低模板化和 AI 生成感；
- 提升中文阅读舒适度和信息辨识度；
- 用克制的创意建立品牌识别，而不是堆装饰；
- 减少卡片、胶囊、渐变、光斑和无效说明；
- 让一个页面只突出一个主任务；
- 保持现有功能、数据绑定、跳转和接口语义不变。

## 4. 冻结的视觉方向

当前总方向为“温润编辑感”。它不是儿童化、医疗化或互联网营销风，而是安静、可信、有人写作与整理痕迹的陪伴工具。

视觉关键词：

- 温暖但不甜腻；
- 专业但不临床；
- 有编辑感但不杂志化；
- 有呼吸感但不空洞；
- 有细节但不炫技。

推荐语言：

- 温暖象牙白作为大面积背景；
- 森林绿作为主行动和稳定锚点；
- 克制的陶土橙只承担提醒或少量强调；
- 细线、轻纹理、自然留白和不完全对称的编辑式构图；
- 清晰的中文字体层级优先于容器装饰。

禁止语言：

- 大面积渐变、发光光斑和玻璃拟态；
- 通用 AI 家庭照、拥抱照、治愈系库存人物插画；
- emoji 充当正式图标；
- 每个模块都使用相同圆角卡片；
- 多个按钮同时使用实心主色；
- 为“高级感”增加无意义英文、编号或抽象术语；
- 没有功能目的的漂浮、呼吸、闪烁和粒子动效。

## 5. 当前真实 UI 审查基线

2026-08-09 真机录屏审查显示，当前页面功能基础可用，但存在以下共性问题：

- 卡片数量过多，部分页面出现卡片套卡片；
- 小字号、辅助说明和标签过密，真实手机上阅读费力；
- 胶囊标签承担了标题、状态、说明和按钮等过多角色；
- 页面用多个框表达层级，缺少标题、字重和留白形成的自然层级；
- 一屏内解释过多，主任务被背景知识和提醒淹没；
- 多页套用相似的“标题 + 说明 + 卡片列表”模板，缺少页面性格；
- 部分图片与内容关系弱，容易形成库存图或 AI 图观感。

所有页面默认执行以下收敛规则：

- 每屏只保留一个实心主行动；
- 每屏最多两个强视觉卡片；
- 禁止嵌套卡片；
- 正文基准为 `28rpx`，可在 `26–28rpx` 内调整；
- 辅助说明不低于 `24rpx`，每段尽量不超过两行；
- 标签只表示状态、分类或可操作筛选；
- 优先使用标题、留白、分隔线和列表，不为每段文字加框；
- 长解释采用渐进披露，默认展示完成任务所需的最少内容；
- 没有数据时不展示空图表骨架，改为明确空状态和下一步；
- 不增加纯装饰动效。

## 6. 每个页面的强制执行顺序

任何页面都不得跳过以下关卡：

1. 读取现有实现；
2. 建立页面功能真值表，理解功能和业务边界；
3. 审查真实页面；
4. 与用户沟通需求；
5. 形成并确认需求冻结版；
6. 使用 ImageGen 生成视觉方案；
7. 用户确认视觉方案；
8. 在 Figma 中组件化复现；
9. 完成 ImageGen 到 Figma 的视觉审核；
10. 修改真实前端；
11. 在微信开发者工具完成编译、预览和可获得的模拟器检查；
12. 执行本地 Loop 1–4 修正；
13. 执行四类 Harness 工程验收；
14. 将本页登记为“本地完成、真机统一待验收”；
15. 进入下一页；
16. 全部页面本地完成后，由用户统一执行 Android/iOS 真机验收；
17. 对真机发现的问题逐页修正并回归，最后完成全量验收。

需求未冻结时，不得调用 ImageGen 生成正式方案。视觉方案未确认时，不得进入 Figma。Figma 未确认时，不得修改前端视觉实现。延期只改变真机验收时点，不允许跳过真机验收，也不降低逐页本地设计、实现、Loop 和 Harness 标准。

### 功能真值门禁

视觉服务于真实功能。每页在需求沟通前必须在 `design/function-truth-table.md` 建立“页面元素 → 事件处理 → 前端路由/API → 后端能力或本地状态 → 用户任务”的功能真值表。

功能真值表必须满足：

- 页面名称以实际业务能力为准，不能只沿用可能误导的现有文案；
- ImageGen 和 Figma 不得新增代码中不存在的选择器、数据、入口、状态、图表或结论；
- 后端返回的标题、状态和边界说明不得被效果图擅自改写成营销文案；
- 只存在跳转功能的入口，不得画成可以在首页直接完成的交互；
- 页面文案与点击结果不一致时，先标记为产品或导航问题并等待确认，不能用视觉包装掩盖；
- 无法从代码、接口或用户确认中找到依据的内容，一律视为假设，不得进入正式设计。

ImageGen 若改变功能语义，即使画面美观也必须淘汰。正式设计提示词应直接引用功能真值表，而不是只描述页面氛围。

`design/function-truth-table.md` 是所有小程序页面的统一功能入口。首页为第一个已核对页面，其余页面按“一次一页”补全。调用 ImageGen 前、进入 Figma 前和修改前端前都必须重读目标页表格，并与当前代码再次比对；代码发生变化时先更新真值表，不能沿用旧快照。

## 7. 开始一页前必须读取的内容

每页开始前至少读取：

- `AGENTS.md`；
- `docs/00_当前事实基准/项目进度统一口径.md`；
- `docs/00_当前事实基准/当前进度交接.md`；
- 本文件；
- `shared/design/experience-tokens.json`；
- `design/function-truth-table.md` 中目标页对应章节；
- `apps/miniprogram/app.json` 和 `apps/miniprogram/app.wxss`；
- 目标页的 WXML、WXSS、JS、JSON；
- 目标页使用的组件；
- 目标页上游和下游页面；
- 直接相关的业务、接口和字段文档，只读核对；
- 最新真机截图或录屏（已有则必须读取；当前批次没有新证据时不阻断逐页本地流程，并明确登记为统一待验收）。

同时列出目标页面的点击事件、数据绑定、接口调用、权限判断、状态分支和页面跳转。只有确认这些行为后，才能讨论视觉结构。

## 8. UI skills 强制路由

每个页面都必须使用与当前阶段匹配的 UI skills。使用前应告知用户“正在使用什么 skill，以及它如何影响本阶段”。不要为了凑数量同时加载全部技能，应选择能覆盖当前阶段的最小组合。

| 阶段 | 必用或优先 skill | 产出 |
|---|---|---|
| 需求澄清 | `design-get-context` | 页面目标、用户任务、保留与禁改项 |
| 现状审查 | `design-audit`、`safehome-ui-motion-audit` | 可读性、层级、伦理、动效和工程问题 |
| 方案发散 | `design-ideate` | 至少两个有实质差异的方向 |
| 视觉概念 | `imagegen` | 经冻结需求约束的页面效果图 |
| Figma | `figma:figma-use`、`figma:figma-generate-design`，按需使用 library skill | tokens、组件、页面和变体 |
| 前端实现 | `frontend-design`，按需使用 `design-image-to-code` | 与 Figma 对齐的真实页面 |
| 可访问性 | `accessibility` 或 `a11y-audit` | 字号、对比度、触控、读屏与状态检查 |
| 视觉验收 | `design-qa` | ImageGen、Figma、真机差异清单 |

若某个 skill 缺失或不可用，应说明原因并使用最接近的可用流程，不能静默跳过阶段。

## 9. 需求沟通与冻结模板

每页需求沟通必须覆盖以下内容：

- 页面名称和路由；
- 页面目标；
- 核心用户与使用场景；
- 唯一主任务；
- 页面内容及优先级；
- 保留内容；
- 修改内容；
- 禁止修改内容；
- 布局和导航方式；
- 色彩、卡片、图标、插画和动效倾向；
- Default、Loading、Empty、Error、Disabled、Active、Selected、Long Content、Network Failure 状态；
- 与上游、下游页面的关系；
- 后端能力是否足以支撑方案；
- 验收方式和回滚点；
- 仍待用户决定的问题。

冻结版应写明版本、日期和用户确认结论。后续重大变化必须重新冻结；不得用实现便利替代产品决策。

## 10. 信息架构与可读性

每个页面先回答“用户现在最需要完成什么”。页面结构围绕这个答案组织。

推荐层级：

1. 当前情境或页面标题；
2. 用户需要理解的一个关键结论；
3. 完成任务所需的主要内容；
4. 一个主行动；
5. 次要帮助、边界说明或历史信息。

中文文案应直接、具体、短句优先。标题表达任务或结论，不用空泛口号。正文每段保持单一主题，辅助说明能删则删，必须保留时放在最靠近相关操作的位置。

不要使用以下 AI 文案特征：

- 连续堆叠“温暖、专业、智能、贴心”等形容词；
- 每个区块都用“让我们一起……”开头；
- 对简单操作写长篇背景解释；
- 模糊承诺“全方位赋能”“深度洞察”“精准识别”；
- 使用相同句式重复安慰；
- 将系统生成内容伪装为确定事实。

## 11. Design Tokens

`shared/design/experience-tokens.json` 是跨端体验 token 的当前事实源。小程序全局变量、Figma Variables 和页面实现应与它对应；调整全局 token 前必须说明影响面，并经用户确认。

当前核心 token：

| 类别 | 名称 | 当前值 | 用途 |
|---|---|---|---|
| Color | Canvas | `#F7F8F5` | 页面背景 |
| Color | Surface | `#FFFFFF` | 必要容器 |
| Color | Ink | `#202622` | 主要文字 |
| Color | Muted | `#68736D` | 次级文字 |
| Color | Primary | `#4F7C6B` | 主行动 |
| Color | Primary Deep | `#2F5B4D` | 强调与按下态 |
| Color | Warning | `#B86A24` | 克制提醒 |
| Color | Danger | `#A5453F` | 风险和错误 |
| Color | Line | `#DFE5DC` | 分隔线与边界 |
| Color | Focus | `#1F6F54` | 焦点状态 |
| Type | Caption | `24rpx` | 辅助说明下限 |
| Type | Body | `28rpx` | 正文基准 |
| Type | Title | `40rpx` | 主要标题参考 |
| Touch | Minimum | `88rpx` | 小程序最小触控目标 |

颜色值是当前工程基准，不代表永久冻结。页面概念阶段可以提出优化方案，但只有用户确认并完成全局影响审查后才能改 token。

间距使用稳定节奏，优先 `8rpx` 的倍数。常用层级为 `8 / 16 / 24 / 32 / 48 / 64rpx`。同级间距一致，区块间距明显大于区块内部间距。

圆角用于表达组件类型，不用来制造“亲和感”。小元素可用小圆角，普通容器使用中圆角，主卡片谨慎使用大圆角，pill 只用于标签、开关或明确的胶囊控件。

阴影只在需要表达层级或浮层时使用。普通列表和内容区优先边框、底色或留白。

## 12. 组件规则

Figma 与代码都应建立可维护的组件体系。相同语义和状态的元素优先复用，不因单页视觉微调复制新组件。

核心组件至少覆盖：

- Button：Primary、Secondary、Text、Danger、Disabled、Loading；
- Card：只保留必要的内容卡、行动卡和风险卡；
- Input：默认、聚焦、已填、错误、禁用；
- Navigation 与 Tab；
- Tag：状态、分类、筛选；
- List Item；
- Modal、Toast 和 Inline Feedback；
- Loading、Empty、Error 和 Network Failure；
- Skeleton：只在确有等待价值时使用；
- 风险提示与人工支持入口。

组件必须定义尺寸、内边距、字体、图标、点击态、禁用态、长文案和错误态。若页面需要与现有组件不同的视觉，应先判断这是新语义、合法变体还是样式分叉。

## 13. 图标、插画和图片

图标应来自统一线性或面性体系，同一页面不混用不同粗细、端点和透视。图标必须帮助识别操作，不代替关键文字。

插画只在以下情况使用：

- 解释复杂关系比文字更清楚；
- 建立页面情境；
- 空状态需要方向提示；
- 品牌识别确实需要视觉锚点。

插画风格优先克制线描、纸张肌理、自然物象和抽象关系图。禁止使用与真实内容无关的家庭合照、万能拥抱、医生白大褂、脑科学光效或带诊断暗示的图形。

图片进入代码前必须检查授权、尺寸、压缩、暗色背景表现和不同屏幕裁切。ImageGen 产物是概念和资产候选，不应作为整页截图直接嵌入前端。

## 14. 动效规则

动效必须服务于状态变化、层级关系、方向感或操作反馈。每项动效都要写明：

- 目的；
- 触发条件；
- 持续时间与 easing；
- 是否可中断；
- 错误和网络失败时如何结束；
- reduced motion 的降级方式；
- 对性能和敏感内容的风险。

默认使用短、轻、可被打断的过渡。风险提示、危机入口、长文阅读和输入页面禁止使用循环装饰动效。动效不能延迟主要操作、隐藏错误或制造虚假进度。

## 15. Figma 组件化复现

Figma 不是静态效果图存档。视觉方案确认后应建立：

- Colors、Typography、Spacing、Radius、Shadows、Borders、Icon Size、Layout Grid；
- 与代码语义一致的组件名称；
- 必要的组件变体和状态；
- 目标设备 Frame、安全区域和滚动边界；
- Default、Loading、Empty、Error、Disabled、Long Content 等关键页面状态。

Figma 复现完成后，逐项比较 ImageGen 与 Figma 的布局、比例、字号、行高、间距、圆角、阴影、色彩、图标、插画、尺寸、对齐和层级。平台字体差异应记录，不伪造“像素完全一致”。

## 16. 小程序前端实现

Figma 通过后才能修改小程序。实现时优先调整目标页 WXML、WXSS 和现有组件配置；只有 UI 必须且不改变业务语义时，才谨慎调整目标页 JS。

必须保留：

- 点击事件和事件参数；
- 数据绑定和状态判断；
- 页面跳转及返回路径；
- 表单校验和提交行为；
- API 调用、错误处理和权限逻辑；
- 埋点和用户状态；
- `pages/integration-test/index` 与 `pages/debug/index` 源码。

不得修改：

- `backend`；
- 数据库和迁移；
- API 路径、请求字段和返回结构；
- 云函数、CloudBase 服务、认证和权限体系；
- `content` 与 `shared` 的业务语义，除非用户另行明确授权。

如果设计需要后端尚未提供的数据，应停止该部分实现，记录差距并询问用户。不得用前端伪造正式业务能力。

## 17. 页面状态与真机适配

每页至少检查：

- Default；
- Loading；
- Empty；
- Error；
- Disabled；
- Active；
- Selected；
- Long Content；
- Network Failure。

涉及敏感或高风险内容时，还要检查：

- 普通内容与风险内容的视觉区分是否克制明确；
- 风险操作是否有清晰人工支持入口；
- 失败时是否仍能找到恢复或求助路径；
- 隐私内容是否默认最小暴露。

逐页本地阶段先通过微信开发者工具、静态检查和可获得的模拟器覆盖不同屏幕、安全区域、状态栏、导航栏、刘海屏、长文本、大字体、键盘弹起与弱网。触控目标不小于 `88rpx`；不能只靠颜色表达状态。

Android 和 iOS 真机检查统一放在全部页面本地完成后的最终批次。届时按页面建立证据矩阵；任一页发现问题即标记 `fix_required`，完成修正及相关页面回归后重新验收，不得将“延期”写成“通过”。

## 18. Loop 审核

实现后完成两阶段 Loop。逐页阶段必须完成 Loop 1–4；全部页面本地完成后统一执行 Loop 5。发现问题必须修改并重新检查，不能只写问题清单。

### Loop 1：三级视觉一致性

逐页阶段比较 ImageGen、Figma 与微信开发者工具预览或代码实现证据；最终真机批次再加入小程序真机截图，完成三级视觉一致性复核。记录允许差异、实现偏差和修正结果。

### Loop 2：UI 细节

检查像素对齐、间距、字体、行高、圆角、阴影、边框、图标、图片、对齐和视觉层级。

### Loop 3：UX

模拟首次用户和回访用户完成主任务。检查是否易懂、路径是否清晰、是否易误触、是否信息过载、是否存在多余步骤和无法恢复的失败。

### Loop 4：页面状态

覆盖所有定义状态、极端数据、长文案和弱网。检查状态切换是否稳定，反馈是否出现在正确位置。

### Loop 5：真机适配

此 Loop 是全量延期门禁：只有全部页面的本地阶段均为 `complete` 后才启动。在至少一个真实 Android 或 iOS 环境及可获得的不同屏幕尺寸中逐页复查；未完成项明确标记为待人工验收，发现问题标记为 `fix_required`，不能写成已通过。

## 19. Harness 工程验收

每页交付前执行四类 Harness。

### 视觉 Harness

- 逐页本地阶段的 ImageGen、Figma 和前端实现证据均可追溯；
- 关键尺寸和 token 有对应关系；
- 视觉偏差有记录和处理结论。

全量真机阶段追加真机截图或录屏证据；逐页本地 Harness 不因真机统一延期而失败。

### 组件 Harness

- 无无意义重复组件；
- 无同语义样式分叉；
- 页面硬编码已控制在合理范围；
- 新变体已回到 Figma 和代码组件定义。

### UX Harness

- 一个页面一个主行动；
- 触控区域、状态反馈、可读性、信息层级和可访问性达标；
- 错误提供恢复动作；
- 敏感内容按需展开。

### 工程 Harness

- `git diff --name-only` 未出现未经授权的后端、数据库、API 或业务文件；
- 没有无关重构、新增依赖和重复 WXSS；
- 页面 JS 语法和 JSON 可解析；
- 核心跳转、表单和数据加载未破坏；

### UIproduct 分支与统一合并门禁

- 逐页 UI 生产只在 `safehome1.0-UIproduct` worktree 的 `UIproduct` 分支进行，不切换或修改主 worktree 的 `main`，禁止 reset/clean。
- 按 2026-08-10 用户冻结决定，全部页面本地完成前固定使用注册表 `main_sha_baseline` 作为工程范围基线；外部 main 后续推进只登记为待集成，不得将 main 新增的后端、内容或配置文件误判为本轮 UI 改动。
- 逐页范围检查必须比较“核准基线 → UIproduct 当前状态”，仍严格禁止 UI 分支新增或修改后端、API、数据库、content 和 shared 文件。
- 全部页面本地完成后，才在 UIproduct worktree 一次性合并当时的 main；文档冲突同时保留 UI 记录和 main 记录，不得覆盖任一侧事实。
- 合并完成后更新 `main_sha_baseline` 与 `baseline_history`，重新生成 53 页功能真值，执行全量工程 Harness 和已完成页面最小回归；通过后才进入统一真机验收。
- `git diff --check` 通过；
- 本轮文档已按项目规则更新。

## 21. 页面推进顺序

页面总量以 `apps/miniprogram/app.json` 为准。2026-08-09 当前登记 52 个页面，后续不得把该数字当成永久常量。

推荐顺序如下：

1. 首页 `pages/home/index`，建立首个视觉基准；
2. 登录、注册和首次使用；
3. 情绪温度计、情绪记录、反馈、训练卡、打卡、周报和督导核心闭环；
4. 训练、课程、计划和历史记录；

6. 关系试点、关系报告、关系任务和关系成长；

8. 成长仪表盘、研究者工作台和治疗性评估相关页面；
9. 个人页与设置；
10. `debug` 和 `integration-test` 只做可用性与发布卫生检查，保留源码。

顺序可由用户调整，但“一页冻结、一页设计、一页本地闭环”不能改变。跨页公共组件修改必须明确列出影响页面，并在本页本地 Harness 后做最小回归；全量真机验收统一后置。

## 22. 当前页面的优先改进提示

以下提示来自真机审查，是后续沟通的起点，不自动等于冻结需求：

- 首页：减少入口卡片堆叠，以一个今日主行动建立节奏；
