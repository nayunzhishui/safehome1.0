# 6-9 月自动化开发总计划：对照修改说明

版本：v1.0  
更新时间：2026-06-26  
对应文件：`6-9月自动化开发第一轮总计划修订版.md`

---

## 1. 修改目的

本次修订不是重新制定研发方向，而是把原有 `6-9月微信小程序自动化开发总计划.md` 的阶段框架和已完成记录，收口到 `6-9月自动化开发第一轮总计划修订版.md`。自 2026-06-27 起，修订版是唯一总计划；旧文件已按用户要求删除。

核心目标：

1. 保留原计划中 P0-P8 的阶段框架；
2. 明确本地工作区是当前开发事实源，GitHub main 只是远程对照；
3. 收紧自动化权限，允许 Chrome / CloudBase / 小程序后台检查，但保护账号、密钥和发布操作；
4. 把“家长优先”写入 P2/P3/P4 的产品主线；
5. 将 P3 聚焦为“家长测评优先阶段”；
6. 将 P4 明确为“测一测 + 情绪日记双来源训练推荐”；
7. 将 P7 升级为“Web 内容审核后台”；
8. 将 P8 明确为“正式发布前准备完成，不提交审核、不正式发布”；
9. 只保留一份主计划，不额外拆出新的主文档。

---

## 2. 总体结构变化

| 原计划结构 | 修订后结构 | 修改原因 |
|---|---|---|
| 直接从目标、权限、阶段总览开始 | 先写“当前需求确认” | 把用户已确认口径前置，避免 Codex 按旧假设执行。 |
| GitHub 与本地状态混用 | 新增“当前事实源说明” | 用户说明很多改动还在本地未提交，因此必须以本地工作区为事实源。 |
| 自动化权限较宽泛 | 新增“自动化权限与暂停条件” | 允许自动检查，但禁止密钥、发布、删除、开放量表等高风险自动操作。 |
| P0-P8 阶段存在，但部分目标不够聚焦 | 保留 P0-P8，并重命名 P3/P4/P7/P8 | 让阶段名直接体现当前开发重点。 |
| 任务记录较多，主线容易被历史记录淹没 | 新增“历史记录处理原则” | 旧记录不删除，但不再干扰当前执行流。 |

## 3. 已确认需求如何写入文档

### 3.1 文档用途

原计划主要像 Codex 自动化开发计划。修订后明确：

```text
本文档同时服务 Codex 自动执行和用户本人进度管理；导师版后续另出。
```

这样避免自动化执行细节和导师汇报混在一起。

### 3.2 Codex 执行方式

用户明确说明 Codex 与用户不需要每个任务都问答确认。因此修订后写为：

```text
Codex 可按计划自动推进；只有遇到扫码、验证码、密钥、发布、删除、开放真实量表、数据库结构变更、新依赖安装等事项时暂停。
```

### 3.3 本地未提交内容

原计划中曾把 GitHub 状态作为重要参考，但用户说明很多内容目前还在本地没有提交。修订后明确：

```text
以 D:\codex\workspace\safehome1.0 本地工作区为当前开发事实源。
GitHub main 用于远程备份、对照和提交后的状态确认。
```

Codex 每次启动只列出未提交文件后继续开发，不再每次等待用户确认，但必须避免覆盖已有改动。

### 3.4 Git / push 规则

修订后明确：

1. Codex 不自动 commit；
2. 修改后先汇报，用户确认后 commit；
3. push 前必须单独询问；
4. 不允许 force push；
5. 不允许 `git add .`。

## 4. P3 阶段修改说明

### 4.1 原计划问题

原计划把 P3 写成“测一测真实量表阶段”，方向是对的，但范围较宽，容易同时展开家长、大学生、成人自助、学生画像等多条线。

### 4.2 修订后定位

修订后 P3 改为：

```text
P3 家长测评优先阶段
```

第一批主题明确为：

1. 家长养育压力；
2. 亲子沟通；
3. 家长反思功能 / 心理化能力；
4. 家长自主支持；
5. 家长情绪调节。

### 4.3 完成标准变化

用户确认 P3 目标为 4-5 个家长测评包可在小程序试用填写。修订版将其拆成：

1. 扫描本地家长量表文件；
2. 建立 4-5 个测评包目录；
3. 抽取题项；
4. 核验计分和维度；
5. 小程序测一测分组；
6. 结果页短报告；
7. 试用标识；
8. 正式开放前暂停确认。

### 4.4 量表状态变化

修订版采用代码英文、页面中文的审核状态：

```text
draft / pending_review / reviewed / trial_enabled / enabled / disabled
```

其中 `enabled` 或 `enabled_for_user=true` 前必须暂停并向用户确认；`trial_enabled` 可用于小范围试用，但必须显示“试用版 / 非诊断 / 小范围测试”。

### 4.5 结果页变化

修订版明确结果页不显示“风险等级”，只显示：

1. 当前状态概括；
2. 维度说明；
3. 支持性解释；
4. 今日建议；
5. 推荐训练卡；
6. 非诊断边界；
7. 必要时提示人工支持。

## 5. P4 阶段修改说明

### 5.1 原计划问题

原计划写了训练推荐，但未完全区分推荐来源，也未明确“今日建议”和“长期建议”的关系。

### 5.2 修订后定位

P4 改为：

```text
P4 测一测 + 情绪日记双来源训练推荐阶段
```

推荐逻辑：

1. 情绪日记生成“今日建议”；
2. 测一测生成“长期建议”和“3 天轻量计划”；
3. 每次最多推荐 3 张训练卡；
4. 三张卡角色固定为：今日练习 / 备用练习 / 长期练习；
5. 每张训练卡必须显示推荐理由。

### 5.3 数据结构边界

用户确认 3 天轻量计划不新增数据库，先用小程序本地缓存。因此修订版明确：

```text
不新增 training_plans 表；不改数据库结构；如未来需要数据库保存，必须单独确认。
```

## 6. P7 阶段修改说明

### 6.1 原计划问题

原计划中 P7 是“Web 后台必要验收阶段”，偏验收，不足以支撑量表、训练卡、反馈规则的审核工作。

### 6.2 修订后定位

P7 改为：

```text
P7 Web 内容审核后台阶段
```

第一版目标：

1. 内容审核总览页；
2. 量表目录审核；
3. 训练卡审核状态；
4. 反馈规则审核状态；
5. 管理员可修改 `review_status` 和 `enabled_for_user`；
6. 研究者只读；
7. 审核操作至少写入开发日志。

### 6.3 修改方式

用户确认本地开发阶段可以直接修改 content JSON，因此修订版写为：

```text
本地开发阶段可以直接修改 content JSON；正式发布前必须复核。
```

## 7. P8 阶段修改说明

### 7.1 原计划问题

原计划目标为“小程序真机可验收”，但用户确认 6-9 月目标为“正式发布前准备完成，但不提交审核”。

### 7.2 修订后定位

P8 改为：

```text
P8 发布前总验收与交接阶段
```

完成标准包括：

1. 本地测试全部通过；
2. 微信开发者工具编译通过；
3. 真机主链路验收通过；
4. CloudBase 健康检查通过；
5. Web 后台内容审核、导出、复核可用；
6. 文档和交接完成；
7. 完成一次发布前人工风险复核会；
8. 体验版上传预案已写，但明确禁止自动上传。

### 7.3 体验版预案

修订版保留体验版预案，但明确：

```text
禁止 Codex 自动上传体验版。
禁止 Codex 自动提交审核。
禁止 Codex 自动正式发布。
```

## 8. 文档更新规则变化

用户确认每个小任务都更新四份文档，并且四份都详细写。修订版为避免文档乱写，增加固定位置要求：

| 文档 | 固定更新位置 |
|---|---|
| 总计划 | 对应任务卡 + 阶段总览 |
| 开发日志 | 最新日期追加区 |
| 当前进度交接 | 当前阶段摘要区 |
| 开发说明 | 对应模块说明区 |

这样既满足“每个小任务都详细更新”，又避免 Codex 到处新增零散段落。

## 9. 自动化验收证据变化

原计划已经有“自动化验收过程记录”路径。修订版进一步明确：

1. 证据保存到仓库外；
2. 按日期分文件夹；
3. 截图、CloudBase 记录、真机记录、CSV 抽查记录都放入该目录；
4. 测试数据统一前缀 `SAFEHOME_TEST_`；
5. 测试数据不自动清理，清理必须用户确认。

## 10. 连续执行模式变化

用户允许在明确要求时持续执行直到所有开发任务完成。修订版加入两个启动语：

1. 普通单任务启动语；
2. 连续执行启动语。

连续执行时：

1. 不需要每个小任务都在聊天里询问；
2. 每个小任务仍要更新四份文档；
3. 只有遇到阻塞或必须人工确认事项才汇报；
4. 阶段结束后统一汇总；
5. 不自动 commit；
6. 不自动 push。
