## 3. BLOCKER

### BLOCKER-01：当前展示全权限模式仍处于开启状态

证据：

- `content/showcase_access.json`
  - `enabled: true`
  - `read_only_role_bypass: true`
  - `researcher_platform_full_access: true`
  - `allow_program_participation: true`
  - 文件自身明确写明“正式发布前必须关闭”。
- `backend/services/showcase_access_service.py`
  - `allow_showcase_researcher_platform_full_access()` 在开关开启时返回 true。
- `backend/routes/auth_utils.py`
  - 已登录用户携带 `X-SafeHome-Researcher-Workspace: 1` 且进入指定研究平台接口时，可被开发例外临时提升为 `admin` 角色。
- `apps/miniprogram/pages/researcher-dashboard/index.js`
  - 研究者工作台客户端主动携带该 Header。

判断：

这是项目明确设计的开发验证能力，不等于普通权限逻辑写错；但在当前配置下，它与“正式角色权限验收”互斥。只要该开关继续开启，就不能把研究者/督导/管理员权限测试结果作为正式发布证据。

**等级：BLOCKER。**

## 4. P0

### P0-01：debug / integration-test 开发页面仍属于正式小程序注册面，并存在参与者可达路径

证据：

- `apps/miniprogram/app.json` 注册：
  - `pages/debug/index`
  - `pages/integration-test/index`
- `pages/debug/index.js`
  - 可查看当前 env/service/base URL；
  - 可切换本地/云端后端配置；
  - 可运行接口检查；
  - `testProfile()` 会调用画像创建接口。
- `pages/integration-test/index.js`
  - 按钮触发后执行：`healthz → createDiary → generateFeedback → recommendCards`；
  - 对已登录用户会产生真实测试日记/反馈链路写入。
- `pages/assessment/index.wxml`
  - 当测评加载失败时，参与者界面直接显示“打开联调测试页”按钮。

补充：首页的开发入口由 `showDevEntry` 控制，当前没有找到 JS 中主动置 true 的证据，因此首页入口通常应隐藏；但测评错误页到 integration-test 的路径是明确存在的。

判断：正式参与者遇到测评服务错误时，不应被导向能够产生测试数据的工程联调页面。

**等级：P0（正式发布阻断）。**

### P0-02：研究者账号 bootstrap 安全契约发生实质漂移

`backend/scripts/bootstrap_researcher.py` 当前：

```python
ALLOWED_BOOTSTRAP_ROLES = {"parent", "student", "researcher", "supervisor", "admin"}
```

因此 `prepare(... role="parent")` / `role="student"` 已被脚本接受，而既有安全测试明确要求该研究者 bootstrap 工具不得创建公众参与者角色。

这不是单纯行号或文档漂移，而是工具权限边界实际改变。

在确认这是经过设计批准的“统一账号 bootstrap”改造之前，应按安全契约回归处理。

**等级：P0。**

## 5. P1

### P1-01：参与者 AI 的“产品策略”和“治理冻结状态”互相矛盾

`content/ai_participant_use_case_policy.json` 当前声明：

```text
stage = controlled_participant_support
allowed_roles = parent, student
allowed_use_cases = 支持性自由问答
required_consent_type = ai_assistance
write_actions_allowed = false
```

但 `content/ai_qa_governance.json` 同时声明：

```text
status = blocked_human_review
participant_feature_enabled = false
sandbox_scope = synthetic_only
provider = owner_security_review_required
participant_enabled = false
```

`apps/miniprogram/services/api.js` 已存在 `sendAiQaMessage`，因此旧 Task28 安全契约测试失败；而 `backend/config.py` 已改成可通过受控生产总开关启用 `AI_QA_ENABLED`，旧 Task31 文本冻结测试也失败。

前端 `support-assistant` 本身有登录、同意、边界提示和 `participant_enabled` UI 门禁，代码防护并非完全缺失。真正的问题是：**当前到底属于“仍禁止参与者 AI”还是“已进入受控参与者支持阶段”，项目事实口径尚未统一。**

**等级：P1；在正式开放 AI 前升级为发布阻断项。**

---

### P1-02：首页部分接口失败会被伪装成“没有数据”

`apps/miniprogram/pages/home/index.js` 对多项请求使用 `.catch(() => ({ items: [] }))` 或 `.catch(() => null)`。

例如今日日记、最近日记读取失败后，UI 可能进入：

```text
还没有记录
可以先写下一件刚发生的小事
```

而不是明确提示“服务器/网络暂时无法读取”。

这会把“服务故障”与“用户确实没有数据”混在一起，属于数据可信度问题，也与项目既有“错误不能伪装成空数据”的可靠性原则冲突。

相比之下，`messages`、`weekly-report` 已能区分错误态并提供重试，说明该问题主要集中在首页聚合逻辑。

**等级：P1。**

---

### P1-03：训练中心存在双份 hardcoded 内容，和正式内容库/API 存在漂移风险

证据：

- `apps/miniprogram/pages/training/index.js` 内部直接维护大量 `trainingStages/tasks`；
- `apps/miniprogram/pages/task-detail/index.js` 仍存在明确 TODO，说明 TASKS 为 hardcoded、未与 API 接通；
- 训练中心实际会导航到 `/pages/task-detail/index?id=...`。

这意味着正式 `content/training_cards.json` / 后端推荐规则更新后，训练列表或任务详情可能继续展示旧内容。

心理支持类产品尤其不适合长期维护两套互不绑定的训练文案，因为会削弱内容审核、版本冻结和发布追溯。

**等级：P1。**

---

### P1-04：Task35 冻结证据校验失败

`config/task35_registry.json` 明确规定：

- `production_replacement_allowed: false`
- 多项外部数据权利、人审、生产演练仍 pending/blocking。

`scripts/run_task35.py verify` 会校验登记证据文件及 `offline_baseline_manifest.json` 中冻结 SHA256；当前 CI 的 `test_task35_verifier_binds_frozen_artifact_hashes` 失败。

因此 Task35 的冻结证据目前不能被视为完整可重复验证。

**等级：P1（研究/模型发布治理）。**

## 7. 已通过的关键模拟验收

### 7.1 登录与用户数据归属：PASS

- 小程序 `authGuard` 对需登录流程进行拦截；
- 后端 Token 有 7 天签名过期校验；
- 用户被停用后旧 Token 不再正常使用；
- `auth_epoch` 改变可使旧会话失效；
- 首次临时密码未修改时，除必要认证接口外默认拒绝；
- 后端 `resolve_actor_user_id` 优先使用认证 Actor，普通参与者不能通过请求参数切换到别人的 `user_id`；
- development fallback 被限制在 development 环境。

结论：代码层面的会话与对象归属设计较完整。

### 7.2 日记填写：PASS

`pages/diary-form/index.js` 已具备：

- 强制登录；
- 本地草稿恢复；
- 提交中防重复；
- 慢请求提示；
- `client_submission_id` 幂等标识；
- 失败后保留输入。

### 7.3 训练打卡：PASS

`pages/checkin/index.js` 已具备：

- 强制登录；
- resilient draft；
- `submitting + submitted` 双层重复提交保护；
- client submission ID；
- 网络失败保留可重试状态。

### 7.4 高风险反馈路由：PASS（代码层）

前端 `feedback-result` 在高风险或后端禁止推荐时，不显示训练推荐；后端 `risk_service.py`：

- 明确不把信号当诊断/自杀概率；
- 支持否定、历史、假设、即时性上下文；
- immediate high-risk → `urgent_human_review`；
- urgent 时强制 `allow_auto_feedback = false`、`allow_recommended_training_cards = false`。

该部分符合“高风险优先现实支持/人工复核，而不是自动训练建议”的项目原则。

### 7.5 消息与周报错误处理：PASS

- 消息页区分登录失败与一般网络失败；
- 周报页保留明确错误状态和重试；
- 可复制诊断信息只包含 request ID、客户端/服务版本、build ID、时间，不包含 token 或自由文本。

### 7.6 未成年人保护：PASS（代码层）

设置页已覆盖：

- 只记录年龄范围而非精确生日；
- 未满 14 周岁要求监护关系；
- 监护人同意与学生本人意愿分开；
- 学生可拒绝/撤回；
- 状态失败时不直接开放受保护功能。

### 7.7 隐私删除流程：PASS（代码层）

参与者可：

- 查看自己的删除申请；
- 新建删除申请；
- 取消 pending 申请；
- 对 rejected 申请补充说明后申诉；
- 取消/申诉请求存在幂等 key。

### 7.8 内容/API 基础校验：PASS

既有 CI 中已通过：

- release artifact hash inspection；
- content validation；
- API contract drift check；
- API query boundary scan（0 blocker）；
- 136 个冻结 API operation compatibility replay。

## 8. 52 页面静态覆盖说明

当前 `app.json` 共注册 52 个页面。此前建立的纯验收 Harness 静态门禁已能做到 52/52 页面进入验收矩阵，且其静态一致性门禁为绿色。

但“页面存在并可被静态登记”不等价于：

- 微信开发者工具真实编译成功；
- WXML/WXSS 在不同设备无视觉错误；
- 页面上的每个按钮都真实可点击；
- 微信授权 API 真正成功；
- Android/iOS 表现一致。

因此本报告将其记为“静态覆盖完成”，不写成“52 页面真机通过”。
