# 2. 方法：六轮核心审查 + 攻击链交叉验证

## Round A — Semgrep 式语义规则审查

重点寻找 production bypass、客户端可控权限标记、debug/test 正式入口、真实写调试路径、hardcoded 心理干预内容、高权限 feature flags、敏感 `SELECT *`、无界列表、动态执行和凭据模式。

## Round B — CodeQL 式跨文件数据流与权限流审查

追踪：

```text
用户身份 → Token → Header/body/query → actor → role/capability → target object → side effect
```

## Round C — Trivy / Gitleaks 式供应链、配置与 Secrets 审查

检查 Secret 覆盖、生产默认值、Docker、Python/npm 依赖证据、明显凭据与 scanner 自身盲区。

## Round D — Schemathesis 式 API 属性与状态机审查

按角色 × 对象 × 状态 × 输入边界检查跨用户、disabled/expired token、重复提交、高风险下游、异常/空数据、分页和高权限管理动作。

## Round E — Mutation Testing 式测试有效性审查

检查 role、showcase、owner、risk threshold、auth_epoch、AI gate、idempotency 被削弱时测试是否真正失败。

## Round F — CI / PR Gate 审查

检查 fail-fast、门禁独立性、冻结契约与当前策略漂移。

## Round G — Adversarial Chain Correlation

只把能形成可达路径、权限变化或真实副作用的问题提升为 CRITICAL/HIGH。

# 29. CRITICAL-02：研究者可伪造参与者同意并覆盖撤回，审计主体同时错误归因

**类别：CWE-639 / CWE-862 / Consent Integrity / Audit Integrity**  
**严重度：CRITICAL**  
**置信度：高**  
**发布影响：阻断**

## 29.1 根因

`resolve_actor_user_id()` 对已认证的 `admin/supervisor/researcher` 采用如下语义：

```text
如果请求显式提供 user_id
→ 直接把该 user_id 当作目标对象
```

该 helper 本身没有检查 researcher 是否被分配给该参与者、route 是否允许代写、capability 是否允许当前操作、consent 是否只能由参与者本人表达。

## 29.2 `/api/consent` 直接继承该语义

`POST /api/consent` 调用 `resolve_actor_user_id(...)`，允许 consent type 包括 `research_authorization`、`anonymous_research`、`model_training`、`ai_assistance`、`relationship_analysis`、`secondary_research` 等。因此合法 researcher 可向 participant B 的 `user_id` 写入 `agreed=true`，无需 B 本人重新确认。

## 29.3 可以逆转参与者撤回

隐私中心撤回追加 `agreed=false` 记录，而研究授权读取以“最新一条记录”为准。于是：

```text
participant revoke
→ researcher 向该 user_id POST 新的 agreed=true
→ 新记录时间更晚
→ 系统重新认为授权有效
```

## 29.4 审计还会把动作记录成参与者本人

consent route 当前把 `actor_id = user_id`，这里的 user_id 是目标参与者而非实际 Bearer actor，形成 researcher 实际发起但 audit 看起来像 participant 自己操作的归因错误。

## 29.5 修复方案

### P0-A：participant consent endpoint self-only

```text
actor = require_login(allow_legacy_admin=False)
actor.role ∈ {parent, student}
user_id = actor.id
payload.user_id != actor.id → 403
```

更推荐直接从 participant consent schema 删除 `user_id`。

### P0-B：后台更正单独建受控 endpoint

若确有行政更正，必须独立 endpoint + reason code + supervisor/admin 审批 + 实际 actor 审计；不得伪造成 participant 行为，也不得直接把 revoke 改回 agreed。

### P0-C：敏感撤回单调化

participant revoke 后，后台 actor 无权恢复；只有 participant 新一次认证后的明确 reconfirm 才可恢复。保存 `consent_text_hash / version / recorded_by / source / supersedes_id / reconfirmed_at`。

### P0-D：审计分离 actor 与 target

```text
actor_id = 实际认证操作者
target_user_id = 被影响参与者
```

### 必须增加的回归测试

- researcher/supervisor 代 participant 写 consent → 403；
- participant 只能写自己；
- revoke 后后台无法恢复；
- participant 自己重新确认才可恢复；
- audit actor 等于真实操作者；
- target participant 单独记录；
- revoke→forged consent 的 mutation 必须被测试杀死。

# 30. HIGH-06：关闭 Showcase 后仍存在系统性 researcher 横向对象越权

**类别：BOLA / IDOR / CWE-639**  
**严重度：HIGH**

## 30.1 项目已有正确对象范围模型

`research_access_service.py` 已有 `has_object_scope()/require_object_scope()`，researcher 需 assigned enrollment 或 active assignment；supervisor 也通过 scope assignment。这说明目标架构并不是 researcher 默认看所有人。

## 30.2 participant routes 绕过该模型

`resolve_actor_user_id()` 对 researcher/supervisor/admin 直接接受显式 `user_id`，而多类 participant route 没有 `require_object_scope()`。

已逐文件确认：

- `/api/diaries`：可横向读目标日记，也可代目标创建；
- `/api/checkins`：可读/写目标 checkin；
- `/api/assessment-results`：可在目标 participant 下提交测评并污染 score/risk/profile/recommendation；
- `/api/feedback`：`require_admin_or_owner()` 把 researcher/supervisor 视作通用 owner-equivalent，可对任意 participant diary 生成反馈和下游 risk review；
- `/api/goals`：生产匿名 fallback 被阻断，因此本轮**未确认未登录 production 冒充**，但 researcher 任意 target 语义仍存在。

## 30.3 修复方案

### P0-A：self-service route 只允许 self

新增统一 `resolve_self_user_id()`：parent/student 永远 actor.id；researcher/supervisor 不通过 participant self-service API 跨用户；admin 全局能力走显式 admin route。

### P0-B：研究跨对象操作显式 capability + object scope

```text
require_login
→ assert_capability
→ enrollment lookup
→ require_object_scope
→ target
```

优先使用 enrollment/scoped reference，而非裸 user_id。

### P0-C：`require_admin_or_owner()` 移除 researcher universal bypass

researcher/supervisor 必须有 scope context；admin 只在显式 admin contract 全局。

### P1-D：全仓迁移

系统审计 `resolve_actor_user_id / require_user_id / resolve_user_id_for_query / require_admin_or_owner` 的所有调用；不能只修已确认的六个 route。

### 回归测试

researcher A 对 assigned X 按策略允许，对 unassigned Y 的 diary/checkin/assessment/feedback/profile/consent 等全部 403。

# 31. HIGH-07：Participant 写接口的幂等设计缺少数据库并发唯一性

**类别：Race Condition / Data Integrity**  
**严重度：HIGH**

日记、打卡、目标、测评采用 `SELECT(user_id,client_submission_id) → none → INSERT` 的 check-then-insert；schema 中这些字段未发现 `UNIQUE(user_id, client_submission_id)`。

并发 A/B 都可能先读到 none 后各自 INSERT，产生重复 diary/checkin/assessment/goal，测评还会重复风险/画像/推荐派生。

## 修复方案

1. 核心表加数据库 `UNIQUE(user_id, client_submission_id)`；
2. 先清理历史重复并重连下游引用；
3. 原子 insert + duplicate-key handling；
4. 同 key 保存 canonical request hash；
5. 同 key 同 payload 返回同 ID，同 key 不同 payload → 409；
6. 高价值写逐步强制 Idempotency-Key；
7. SQLite/MySQL 做双实现并发测试。

并发验收必须达到：N 个相同请求只产生 exactly one durable business record。

# 32. HIGH-08：家庭绑定码防爆破控制实际无效，并存在并发抢占窗口

**类别：Authentication/Binding Abuse / CWE-330 / Race**  
**严重度：HIGH**

## 32.1 错误尝试不计数

`MAX_BIND_ATTEMPTS=5`，但错误 6 位码查不到 row 后立即 404，不增加任何 student/IP/global attempt budget。`attempt_count` 只有猜中真实 link 后才参与逻辑，所以“5 次限制”不能阻止遍历不同 code。

## 32.2 使用非密码学随机数

6 位码来自 `random.randint(0,999999)`，空间 1,000,000 且有效 24h。

## 32.3 并发兑换缺少原子条件

最终 UPDATE 仅 `WHERE id=?`，未把 pending/student_user_id/expiry/version 放入原子条件，两个 student 并发读 pending 后可能产生 last-write-wins。

## 修复方案

- 使用 `secrets`，人工码增加熵；扫码/深链优先 80–128 bit token；
- 错误 code 不存在也消耗 account/device/IP/global abuse budget；
- 响应统一，不泄露 code existence；
- 原子单次兑换，UPDATE 条件包含 pending、unused、expiry，并要求 rowcount=1；
- 对未成年人监护关系建议二阶段 parent confirmation；
- 测试第6次错误、nonexistent code、并发双兑换、过期、单次使用、响应一致性。

# 33. HIGH-09：隐私删除“verified”存在白名单覆盖盲区

**类别：Privacy Erasure Completeness / Data Lineage Drift**  
**严重度：HIGH（发布门禁）**

## 33.1 删除执行器依赖手工白名单

`privacy_request_service.py` 的 `SCOPE_TABLES/DIRECT_USER_TABLES` 同时决定 preview、delete 和 verification；`research_outputs` 当前只含 `records/profile_reviews`。

## 33.2 新研究分析数据不在该范围

数据库已有 `research_analysis_snapshots(participant_user_id)`、snapshot_links、jobs、artifacts、events；research analysis 服务有独立 freeze 与手动 `delete_artifact()`，但本轮未发现这些资源被 privacy delete transaction 纳入。

## 33.3 verifier 与 executor 共享同一个可能漏项的列表

`_verify_deleted_scope()` 同样只遍历 `SCOPE_TABLES`。因此未登记的新 participant-linked table 会同时从 preview、delete 和 verification 消失，最终仍可能返回 `verified`。

## 33.4 缓解控制

当前 privacy policy 仍是 `owner_confirmation_required / not_approved`，production gate 要求 approved，因此不声称该问题已造成真实生产删除欺骗；但一旦只审批现有 policy 而不修血缘覆盖，该缺陷就会进入正式执行。

## 修复方案

- 建 Participant Data Registry：每张表声明 participant relation、privacy scope、retention、delete/anonymize/retain、cascade、verification；
- Schema-to-Privacy CI Gate：新增 participant-linked entity 未分类即 BLOCKER；
- executor 与 verifier 使用独立事实源，避免共同模式失效；
- research analysis 明确 delete/anonymize/legally-retained 策略；
- 删除完成后按 `user_id / participant_user_id / enrollment lineage / source links` 全残留扫描，未批准 residual 必须为 0。

# 34. MEDIUM-08：密码失败锁号可被用于账户拒绝服务与渐进枚举（第三轮已修正事实基础）

**类别：Authentication Abuse / Account Lockout DoS**  
**严重度：MEDIUM**

第二轮曾写“未发现独立登录限速”。第三轮继续追踪 WSGI/runtime bootstrap 后确认：**生产运行路径实际上存在基于 Redis 的分布式登录限速**，`/api/auth/login` 默认有独立请求额度。因此“完全没有限速”这一表述不准确，本报告在此正式更正。

真正剩余的问题是：Redis 限速服务不可用或抛错时，`redis_service.rate_limit()` 返回 `allowed=true`，认证入口会 fail-open。与此同时账号自身仍有连续失败锁定机制，因此攻击源可在 Redis 故障窗口继续制造锁号压力。

## 修复方案

- API Gateway/WAF 保留与应用内 Redis 相互独立的登录限速；
- Redis limiter 失败时进入本地低配额 fallback，或对认证等关键入口 fail-closed/受控降级；
- limiter degraded 必须进入监控与告警；
- 外部错误尽量减少 existing/unknown username oracle；
- 测试 Redis 正常、超时、断连、返回异常时的登录攻击流量。

# 35. 第二轮架构级解决方案：不要逐 endpoint 打补丁

## 35.1 Identity Boundary

只回答“真实 actor 是谁”，输出 id/role/auth_epoch/source，不根据 request.user_id 自动授权目标。

# 40. 第三轮：第一性原理全域代码审查（2026-08-09）

## 40.1 审查目标

前两轮主要回答“当前代码哪里可能被绕过”。第三轮改为从更底层的问题出发：

> 如果完全忘掉现有实现，从 SafeHome 的真实目标重新推导，一个心理支持、未成年人保护、研究分析、AI 辅助与人工治理系统必须永远满足哪些条件？当前每一个代码域是否真正证明了这些条件？

因此本轮不以“有没有某个 CWE”为起点，而以**系统不可违反的不变量**为起点。

## 40.2 第一性原理公理

### FP-01 身份真实性

客户端、Header、Query、Body 都不可信。服务端必须能回答“谁在操作”，且请求参数不能改变真实 actor。

### FP-02 授权三元组

合法访问不是 `role == researcher`，而应至少是：

```text
actor capability
AND target object scope
AND purpose/consent allowed
```

### FP-03 状态变化必须原子

任何可能产生研究数据、风险事件、账号状态、绑定关系、发布状态的写入，都必须由数据库/事务保证单一事实，而不能依赖“先查再写”的时间窗口。

### FP-04 安全必须由时间和状态主动触发

“15 分钟内人工复核”“超时暂停”“撤回立即停止研究处理”只有在时间/状态变化本身会触发系统行为时才算保障。依赖人工打开页面或轮询不构成安全保证。

### FP-05 研究结论必须可追溯、可重放

研究数据来源、量表、算法、参数、授权和结果必须形成服务器可验证的 provenance；调用者提交一个 `source_hash` 或 `resource_hash` 不能自动成为证据。

### FP-06 发布批准必须由真实证据驱动

任何叫 gate/approval/review 的机制都不能把 `true` 当证据。Gate 应自己读取可信记录并验证：谁批准、批准了什么、基于什么版本、证据哈希是什么、证据是否仍有效。

### FP-07 内容与行为在副本/重启后必须一致

同一个 release/version 对所有运行实例必须代表同一内容。只改某个容器的本地文件不能构成正式发布。

### FP-08 隐私删除必须覆盖完整数据血缘

系统不能只删除“记得列出来的表”，而必须能证明所有 participant-linked 原始数据、派生数据、缓存、研究快照、索引、导出和备份都被分类并按策略处理。

### FP-09 退出即撤销会话能力

官方客户端的“退出登录”不能只是把 Token 从本地界面藏起来；服务端已经签发的能力必须按产品语义失效。

### FP-10 错误不能伪装成事实

网络/数据库/API 错误不能被 UI 表达为“没有记录”；健康检查也不能为了诊断方便把内部状态全部公开。

### FP-11 心理安全边界高于自动化便利

任何高风险、自伤/他伤、未成年人敏感处理、治疗性评估安全事件都必须优先进入人工/安全路径；无法判断时默认不能自动推进普通干预。

### FP-12 测试必须能证伪不变量

“测试通过”只有在测试能在安全条件被削弱时失败才有意义。保护开发后门的测试不是安全证据。

# 42. HIGH-10：官方 Logout 没有保证服务端 Token 撤销

**不变量：FP-09**  
**严重度：HIGH**  
**类别：Session Lifecycle / Capability Revocation**

## 42.1 服务端其实已经有正确撤销机制

`POST /api/auth/logout` 在收到有效 Bearer actor 时会对该账号 `auth_epoch + 1`。旧 Token 随后无法通过服务端 epoch 校验。

## 42.2 小程序官方 API 的调用顺序反了

`apps/miniprogram/services/api.js::logout()` 先：

```text
remove auth_token/auth_user
```

再调用 `/api/auth/logout`。

请求函数发送 Authorization 时从 Storage 读取 Token，因此真正发出 logout 请求时已经没有 Bearer Token，服务端只看到匿名请求，无法递增 `auth_epoch`。

实际 Profile 页更直接：使用 `authGuard.logout()`，只清本地 Storage/globalData，不调用服务端撤销。

Web `authState.logout()` 也只是清 `sessionStorage`，未发现服务端 logout 调用。

## 42.3 影响

官方 UI 看起来“已退出”，但此前复制/泄露的 Token 仍可继续工作直至自然过期或其他动作递增 epoch。

## 42.4 修复

```text
capture current token
→ POST /api/auth/logout with Bearer token
→ server increments auth_epoch
→ finally clear local token/user
```

同时明确产品语义：当前 epoch 方案是“退出当前设备还是退出所有设备”。如果需要 current-session logout，应使用 session/jti registry；如果产品定义为 logout-all，则 UI 要明确。

## 42.5 回归测试

- login 得到 T1；
- 官方小程序点击退出；
- 使用原始 T1 访问 `/api/auth/me` → 401；
- Web 同样验证；
- 服务端 revoke 失败时客户端不能静默声称“所有会话已安全退出”。

# 43. HIGH-11：数据库没有把核心业务关系提升为存储层不变量

**不变量：FP-03 / FP-08**  
**严重度：HIGH（结构性）**

SQLite `get_connection()` 当前建立连接后设置 `row_factory`，但未显式执行 `PRAGMA foreign_keys=ON`；仓库 schema 中也未确认广泛存在 `FOREIGN KEY` 关系约束。

SafeHome 的核心数据却高度关系化：

```text
user
→ diary
→ feedback
→ risk review
→ training recommendation
→ checkin

user
→ enrollment
→ assignment
→ research snapshot
→ job
→ artifact

case
→ safety event / evidence / review / publication
```

如果关系正确性只靠应用代码，则任意迁移、删除、并发、脚本或未来新路由都可能生成 orphan，进一步破坏隐私删除、研究 provenance、账号合并和审计。

## 修复

1. 为稳定主外键关系建立真实 FK；
2. 明确每条关系的 `CASCADE / RESTRICT / SET NULL`；
3. SQLite 每个连接 `PRAGMA foreign_keys=ON`；
4. MySQL 使用 InnoDB FK；
5. 迁移前先跑 orphan inventory；
6. 如果某些研究/审计表有意不用 FK，则必须进入 Schema Lineage Registry 并由 CI 做 orphan auditor。

## 验收

- 写入不存在 parent 的 child row → DB 层失败；
- delete/revoke/merge 后无未分类 orphan；
- SQLite 与 MySQL 行为一致。

# 44. HIGH-12：Research Snapshot 的来源证明是“研究者声明”，不是服务器事实

**不变量：FP-05**  
**严重度：HIGH / 研究完整性发布阻断**

`create_snapshot()` 对 `source_refs` 当前只检查：

- `source_type` 在允许枚举；
- `source_id` 非空；
- `source_hash` 长度为 64；
- participant/enrollment/object scope/consent 合法。

它没有：

- 到真实业务表中加载 source；
- 验证 source 属于 participant；
- 验证 source 当前版本；
- 服务器重新计算 canonical hash；
- 验证该 source 对当前 research purpose 可使用。

现有测试甚至在没有插入 `diary-f13` 的情况下传：

```text
source_id = diary-f13
source_hash = aaaaaaaaa...（64位）
```

并期望快照成功。

这说明当前 snapshot 的“来源证明”在语义上是 caller assertion。

## 修复

客户端只提交：

```text
source_type + source_id
```

服务端建立 `ResearchSourceResolver`：

```text
source_type
→ allowlisted resolver
→ load row
→ assert participant ownership
→ assert consent/purpose
→ canonicalize exact source version
→ server hash
→ immutable source descriptor
```

快照只保存服务器生成的 descriptor/hash。

## 验收

- 不存在 source → 404/422；
- 其他 participant source → 403；
- caller 不能自带 hash 影响结果；
- source 被改变后新 snapshot hash 必须变化；
- 老 snapshot 保留创建时的不可变 source version。

# 45. HIGH-13：Research Artifact 还不能证明“由声明算法对声明输入真实计算得到”

**不变量：FP-05 / FP-06**  
**严重度：HIGH（研究可重复性）**

`enqueue_job()` 中：

- `analysis_version` 只要求非空；
- `resource_hash` 只检查 64 位长度；
- job 绑定 snapshot 与参数。

`complete_job()` 则由具有 operate capability 的执行者提交 metrics，系统把 metrics、snapshot hash、analysis version 组合成 artifact hash。

这能证明“系统保存了谁提交的什么结果”，但还不能证明：

> 某个服务器登记的、不可变算法制品，确实对该已验证 snapshot 和参数执行，并产生了该结果。

## 修复

建立 `ResearchAlgorithmArtifactRegistry`：

- artifact_id；
- code/model/container digest；
- algorithm_version；
- dependency lock/SBOM hash；
- input schema；
- approved purpose；
- validated_by/evidence；
- immutable status。

Job 只能引用 registry artifact_id。Worker 完成时提交由服务端核对的 execution manifest：

```text
snapshot_hash
algorithm_artifact_digest
parameters_hash
runtime_image_digest
started_at/completed_at
worker identity
result_hash
```

## 验收

相同 snapshot + artifact + params 应可重放；未知 resource hash 不得排队；人工提交任意 metrics 不能伪装成“算法执行证据”。

# 46. HIGH-14：Participant Real-AI 模式下，外部数据处理的知情同意与去标识强度不足

**不变量：FP-08 / FP-11**  
**严重度：HIGH（真实外部 Provider 开启时）**

当前 AI service 的顺序是正确方向：

```text
participant consent
→ input security / de-identification
→ safety gate
→ RAG
→ provider
```

RAG 只检索 approved/published 内容也是重要正面控制。

但去标识规则目前主要覆盖手机号、邮箱、身份证、IP、微信号等显式标识。心理健康自由文本仍可能包含：

- 姓名；
- 学校/单位；
- 详细住址；
- 家庭成员姓名与关系；
- 精确时间地点；
- 小众事件组合；
- 可被上下文重新识别的连续叙事。

小程序 consent UI 的核心表述是“我已阅读并同意AI辅助处理”，当前界面没有把真实外部 Provider、第三方处理、地区/保留策略等关键信息清晰绑定到本次授权。

因此“有一个 ai_assistance consent”不能自动推出“外部真实 Provider 处理心理自由文本已经获得充分、具体的知情同意”。

## 修复

- 把 `local_ai_support` 与 `external_ai_processing` 分成不同 consent purpose；
- consent 固化 provider category、purpose、data categories、retention/region notice、version/hash；
- 增加更强 DLP/实体识别与 re-identification risk score；
- 高可识别文本不发送外部 Provider，退回固定安全响应或本地能力；
- participant raw text 默认不走外部 embedding；
- Provider 合同、no-training/no-retention/region evidence 成为 release gate 的真实证据；
- 只保存 provider/version/consent-version/DLP-version/request hash 等 provenance，不保存外发原文日志。

## 测试

构造姓名、学校、医院、公司、孩子姓名、详细地址、精确日期地点、组合身份叙事，验证高识别风险时不发生外发。

# 47. HIGH-15：统一 Publication Gate 仍在信任调用者传入的“事实布尔值”

**不变量：FP-06**  
**严重度：HIGH（架构性）**

`publication_gate_service._gate_results()` 看起来有五道服务端门，但许多关键事实来自调用方 context：

```text
permission_granted = true
consent_active = true
recipient_matches_scope = true
source_authorized = true
language_checked = true
human_reviewed = true/false
high_risk_reviewed = true/false
reviewer_id = ...
author_id = ...
```

Gate 自己没有统一从 capability、consent_records、assignment、review events、source registry 中重算这些事实。

当前调用者很多确实先做了自己的检查，但这意味着安全性依赖：

> 每一个现在和未来的调用者都永远正确构造这些 bool。

这不符合“Gate 是信任根”的设计目的。

## 修复

把 Gate 输入改成：

```text
actor
target/recipient ID
subject/source IDs
content
review evidence IDs
```

Gate 内部通过权威 resolver 得到：

```text
permission_granted
consent_active
scope_match
source_authorized
reviewer identity
human review validity
```

也就是说：**bool 应该是 Gate 的输出，不是输入。**

## 验收

测试构造一个恶意/错误内部调用者，即便传 `permission_granted=true`，只要 DB 没有授权事实，Gate 仍必须 block。

# 48. HIGH-16：内容治理逻辑很强，但运行时发布模型与容器/多副本架构冲突

**不变量：FP-07**  
**严重度：HIGH**

内容治理层本身已有很多正确控制：

- payload SHA256；
- research / psychology / ethics / content 四学科审核；
- 同一 reviewer 不能代表多个学科批准；
- dependency impact；
- manual confirmation；
- active content hash 一致性检查；
- rollback。

问题出在最终发布动作：

```text
publish_version
→ _replace_active_item()
→ temp file
→ os.replace(content/*.json|md)
→ DB 记录 active release
```

锁也是 `/app/content/.content-governance.lock` 的本地文件锁。

### 多实例问题

实例 A 改了本地文件，实例 B 不会自动获得该内容；DB 却可能已经显示 release active。

### 重启问题

新实例由 Docker image 的 `COPY content /app/content` 启动，运行时修改不会天然成为下一实例的不可变制品。

### 文件权限问题

Dockerfile 切换到非 root `safehome`，只显式 `chown -R safehome:safehome /app/data`，没有对 `/app/content` 做同等赋权，却又打开 `CONTENT_GOVERNANCE_PUBLISH_ENABLED=1`。因此在线文件发布在容器中还可能直接遇到写权限失败。

## 正确修复不是 `chmod 777`

正式内容发布应迁移为：

```text
immutable governed content artifact
→ shared durable storage / DB / object store
→ atomic active_version pointer
→ all replicas read same pointer/version
→ startup/readiness verify digest
```

或者使用“发布新 immutable image”的 GitOps 路径。

### 验收

- 两副本并发存在时发布一次，两副本读取相同 hash；
- 任意副本重启后仍是相同 active release；
- DB active release 与实际 served payload hash 永远一致；
- 发布锁为分布式 CAS/DB transaction，而非单机文件锁。

# 49. HIGH-17：普通 Risk Review 的 SLA 目前是“时间戳”，不是主动时间保证

**不变量：FP-04 / FP-11**  
**严重度：HIGH（安全运营）**

`risk_review_service` 对 urgent/priority review 记录 `due_at`，例如紧急路径 15 分钟，且 reviewer 身份、版本锁、审计都比较完整。

但本轮没有找到一个独立 scheduler/worker 根据 `risk_review_records.due_at` 自动完成：

- overdue detection；
- escalation；
- backup assignee；
- pager/notification；
- supervisor fallback。

如果 `due_at` 只被 UI 展示或人工查询，那么“15 分钟”不是系统保证，只是数据字段。

## 修复

- durable scheduler 每分钟扫描 due/overdue；
- escalation event 与原 review record 同一事务/Outbox；
- primary reviewer 未处理 → supervisor/backup escalation；
- 关键高风险可进入 pager/值守通知；
- SLA breach 进入不可忽略监控；
- 不把微信普通训练提醒当危机通知渠道。

## 验收

冻结系统时钟创建 urgent event，不进行任何 GET/人工页面操作，推进 16 分钟后系统必须自动产生 escalation 证据。

# 50. HIGH-18：治疗性评估的 Queue Timeout Kill 是读取触发，而非时钟触发

**不变量：FP-04 / FP-11**  
**严重度：HIGH**

治疗性评估安全控制总体比普通 risk queue 更强：

- safety signal 立即切 `safety_path`；
- 责任链缺失/失效可 global kill；
- resolver 必须是 supervisor/admin；
- 恢复要求 evidence；
- stop/recovery 还有 self-verification forbidden。

但 `evaluate_runtime()` 中的：

```text
if open_event age > queue_timeout_minutes:
    _kill("human_queue_timeout")
```

本轮全仓搜索只确认在安全状态读取路径调用 evaluator，没有找到独立时钟 worker。

因此：

```text
事件创建
→ 超过 timeout
→ 如果没人读取 status
→ kill 可能尚未发生
```

## 修复

- scheduled safety evaluator；
- 所有 therapeutic mutation 前统一 `assert_runtime_safe()`，并实时检查 overdue；
- DB/outbox 记录 timeout transition；
- 监控/Pager 由独立 worker 驱动；
- clock-driven tests 不能先调用 status endpoint。

# 55. MEDIUM-13：匿名试用数据认领仍带有“客户端生成所有权标识”的历史风险

# 56. MEDIUM-14：审计表是业务审计，不是强防篡改证据账本

**不变量：FP-06 / AUDIT-INV**  
**严重度：MEDIUM（治理证据强度）**

SafeHome 大量高价值动作都会写 `audit_logs`，这是很好的工程基础。

但当前审计主要仍是同一业务数据库中的普通记录；隐私删除流程为了合规去标识，还会主动：

- 改写 `audit_logs.actor_id`；
- 改写 target/metadata 为 privacy-redacted 状态。

这说明当前 audit 的语义是：

> 可按隐私策略修改的业务审计记录。

它不等于独立、不可篡改、可用于强非抵赖的审计证据。

## 修复

对 release/privacy/account-security/consent override 等高影响动作增加第二层 tamper-evident ledger：

- canonical event hash；
- previous hash / Merkle checkpoint；
- 定期签名 checkpoint；
- 外部 WORM/object-lock/log sink；
- privacy deletion 只去标识业务副本，不破坏最小合规 proof hash；
- DB admin 无法无痕改写历史。

注意：这不是要求保留被删除的心理原文，而是保留**不可逆的最小事件证明**。

# 57. 第一性原理下的安全/心理学外部门禁

## 57.1 Risk classifier 不能因为代码复杂就叫“已临床验证”

当前 risk engine 已经有：

- 否定语境；
- 历史/假设语境；
- immediacy；
- self/other harm routing；
- high risk 固定安全响应；
- 禁止普通自动训练。

这是优秀的 engineering safety boundary。

但 `risk_keywords.json` 本身明确仍为工程增强、等待临床专家审核，并提出 precision/recall/F1/Kappa 等验证计划。

因此正式发布文档必须区分：

```text
engineering fail-safe implemented
≠ clinical detection performance validated
```

正式危机检测能力仍需要双专家标注样本、漏报专项、方言/隐喻/青少年表达、false-positive burden、值守链路共同验收。

## 57.2 年龄目前更准确应称“年龄自我声明”

未成年人机制已有 guardian consent + child assent + sensitive capability gate，并禁止已记录 under-14 用户自己升级成 14+，这是正面控制。

但首次 `age_band` 仍由 participant 自己提交。如果产品/伦理/法律要求真正的年龄核验，当前机制不能被描述成强 identity-proofed age verification。

需要产品层明确：

- pilot 接受 self-declaration；还是
- 需要 guardian/school/admin/第三方 age assurance。

# 58. 第一性原理下确认的 Positive Controls

第三轮刻意寻找“哪些东西已经符合正确方向”，避免修复时误删成熟机制。

### PC-09 生产配置已有大量 fail-closed validator

SECRET_KEY、DB provider、CORS、privacy production gate、fault injection 等已经具备明确生产拒绝条件。

### PC-10 CloudBase Identity Header 默认不可信

只有显式开启 trust，且 openid 格式、source、appid 通过检查才采用 CloudBase Header；标准微信登录在 production 缺配置会失败，而不是使用 dev fallback。

### PC-11 WeChat transport 日志避免打印凭据和 response body

认证 transport failure 只记录 operation/error 类型等元数据。

### PC-12 Agent Runtime 当前没有通用写工具

planner/tool allowlist、synthetic-only、tool budget、无 shell/SQL/browser/write tool，是合理的 Agent 安全基线。

### PC-13 RAG 不直接把参与者数据建立成知识库

检索对象是 governed/published 内容，缓存 key 使用 hash；这是正确的数据边界。

### PC-14 Assessment 是服务端计分而不是信任客户端 score

题号、选项、必答、维度与转换均在服务端处理。

### PC-15 高风险反馈会阻断普通自动训练

risk result 能关闭 auto feedback / training cards，避免高风险内容落入普通干预路径。

### PC-16 Therapeutic Stop/Recovery 有独立人责链

恢复证据带 SHA、reviewer 不能核验自己提交的 evidence、global kill/recovery 都有明确状态机。

### PC-17 Notification 使用固定最小内容

训练提醒需要明确订阅授权，外发模板不包含日记/测评自由文本，并有 idempotency、retry、dead-letter。

### PC-18 Admin export 做了数据最小化与 CSV 防护

导出使用匿名化 ID，很多自由文本只导长度/计数，研究撤回有 filter，并防 spreadsheet formula injection，limit 有上限。

### PC-19 Web Token 从长期 localStorage 降为 sessionStorage

旧式 X-Admin-Token 也只在显式 dev flag 下启用并驻留内存；本轮未检出 `dangerouslySetInnerHTML/innerHTML` 直接注入模式。

### PC-20 MySQL/Redis 有真实 CI infrastructure smoke

工程基础设施 workflow 会实际启动 MySQL 8.4 + Redis，而不是所有测试都只在 mock 层。

### PC-21 Schema migration 有 MySQL advisory lock

startup migration 虽建议长期迁到 deploy job，但现有 migration 对 MySQL 已有 named advisory lock、锁内重检与幂等设计。

### PC-22 Identity merge 有版本化、迁移账本与回滚窗口

合并流程不是直接批量 UPDATE；有 candidate/confirm/execute/verify/rollback 结构和 record links。

# 59. CI / 测试从第一性原理重构建议

当前 `SafeHome Checks` 是单 Job 顺序执行：

```text
content/contract
→ backend pytest
→ AI quality
→ npm install/audit
→ typecheck/build
→ mini-program audits
```

后端测试失败会使后续证据消失。

另一个 Engineering Infrastructure workflow 已经有真实 MySQL/Redis smoke，但完整行为/安全回归大多仍在 SQLite。

## 推荐结构

```text
PR
├─ backend-sqlite-full
├─ backend-mysql-critical-contracts
```

### 供应链进一步要求

- Web 有 package-lock 与 npm audit，但 audit 不能被 backend fail-fast 跳过；
- GitHub Actions `actions/checkout@v6` / `setup-*` 最终可考虑 pin 到 immutable commit SHA；
- container base image 也应有 digest/SBOM/provenance。

# 60. 第三轮新增不可违反不变量

- **SESSION-INV-01**：官方 logout 后，退出前 Token 立即不能继续访问受保护 API。
- **DB-INV-01**：任何 child record 都不能指向不存在的 parent entity，除非 schema registry 明确声明为软引用。
- **RESEARCH-INV-01**：snapshot source 必须由服务器从真实数据解析、验证 owner 并计算 hash。
- **RESEARCH-INV-02**：research artifact 必须绑定已登记算法制品和 execution manifest，且可重放。
- **AI-PRIVACY-INV-01**：未经明确 external-processing consent 的 participant raw/free text 不得离开 SafeHome trust boundary。
- **GATE-INV-01**：release/publication gate 的 permission/consent/review 事实必须由权威 evidence resolver 得出，不接受调用者自报 true。
- **CONTENT-INV-01**：任意两个 production replica 对同一 active release 必须返回相同 payload hash。
- **TIME-SAFETY-INV-01**：安全 SLA 到期必须在没有任何人工 GET/poll 的条件下自动触发 escalation/pause。
- **ASSESSMENT-INV-01**：历史 assessment 必须能从不可变 worksheet hash + engine version 精确重放。
- **AUDIT-INV-02**：高影响安全/发布/隐私动作必须存在独立 tamper-evident 最小证明。
- **HEALTH-INV-01**：匿名健康接口不得暴露 participant/risk backlog/internal operational details。
- **CONFIG-INV-01**：同一进程中所有组件必须读取同一 resolved settings truth。

# 64. 第一性原理最终结论

第三轮对全域代码的结论不是“SafeHome 架构很差”。相反，项目已经有很多明显超出普通 MVP 的成熟控制：

- capability registry；
- object scope 模型；
- auth_epoch；
- 多层 privacy workflow；
- risk fail-safe；
- therapeutic stop/recovery；
- content multi-discipline governance；
- idempotency；
- MySQL/Redis runtime；
- RAG content boundary；
- Agent tool allowlist；
- CI contract；
- 大规模测试。

真正的问题是这些控制还没有全部落到**统一信任根**上。

当前系统仍存在几类重复模式：

```text
客户端/调用者声明一个事实
→ 服务端把它当作已证明事实

配置写着 enabled/approved
→ 运行时把它当作治理批准

数据库写着 due_at
→ 但时间不会主动驱动状态变化

容器本地文件被替换
→ 数据库把它当作全局发布

测试断言功能可达
→ 但没有验证安全不变量是否不可破坏
```

因此后续最重要的架构目标应当是：

```text
Identity Truth
→ Authorization Truth
→ Consent Truth
→ Data Lineage Truth
→ Safety Time Truth
→ Evidence/Release Truth
→ Immutable Runtime Truth
```

每一层都只能由更低层、不可伪造的事实推导，而不能由调用者提交 `true`、任意 SHA、Header、`user_id` 或当前容器文件状态来决定。

在第 60–61 节的不变量和回归矩阵成为自动化门禁之前，第三轮继续维持：

```text
RELEASE STATUS = NOT READY
```

本第三轮仍只更新同一份审查报告；**没有修改任何业务代码、配置、Workflow、Dockerfile、数据库、CloudBase 或真实账号。**
