### 总体判定

**当前 `main` 不满足正式发布安全门禁。**

最严重问题不是单个文件中的普通漏洞，而是一条已经被代码、配置和测试共同确认的**认证后权限提升攻击链**：

```text
普通 parent / student 已登录账号
        ↓
可访问/构造 researcher workspace 请求
        ↓
客户端请求头：X-SafeHome-Researcher-Workspace: 1
        ↓
content/showcase_access.json

        ↓

        ↓
/api/research/*、/api/security/*、/api/ai-qa/*、

        ↓

        ↓
PATCH /api/security/accounts/<user_id>/status
        ↓
```

这条链已经超过“开发开关忘记关闭”的层级，应按 **CRITICAL / Release Blocker** 处理。

# 2. 方法：六轮核心审查 + 一轮攻击链交叉验证

## Round A — Semgrep 式语义规则审查

目标：寻找“一旦这种代码模式出现，就应当自动报警”的危险结构。

重点规则模型：

- 生产环境开启 development/showcase bypass
- participant 页面调用 researcher/admin 能力
- 客户端可控 Header 参与服务端角色提升
- 正式 `app.json` 注册 debug / integration-test 页面
- 调试页面执行真实写请求
- hardcoded 心理训练内容绕开受治理内容源
- 生产镜像直接开启高风险 Feature Flags
- 默认生产端点与调试写入入口组合
- `SELECT *` 出现在敏感 HTTP adapter
- 列表接口缺少明确上限
- Shell / eval / 动态执行危险模式
- 私钥 / API Key / Token 硬编码模式

## Round B — CodeQL 式跨文件数据流与权限流审查

目标：不只看函数内部，而是追踪：

```text
用户身份 → Token → Header → actor → role → capability → target object → side effect
```

重点数据流：

1. participant Token 到 researcher/admin 权限的传播；
2. `X-SafeHome-Researcher-Workspace` 从客户端到服务端权限决策；
3. researcher participant matrix 暴露的 `user_id` 到安全管理接口；
4. participant 传入 `user_id` 到对象归属解析；
5. 高风险状态到训练/AI/反馈下游动作；
6. AI participant 请求到真实 Provider；
7. production Feature Flag 到高权限执行面。

## Round C — Trivy / Gitleaks 式供应链、配置与 Secrets 审查

目标：检查：

- Secret 检测覆盖范围；
- 默认密钥与生产保护；
- Docker 生产镜像配置；
- Python/npm 依赖安全证据；
- 是否存在真实私钥、AKID、`sk-*` 等明显凭据；
- 安全扫描器自身是否存在漏检目录/模式。

## Round D — Schemathesis 式 API 属性与状态机审查

目标：按“角色 × 对象 × 状态 × 输入边界”检查 API，而不是只验证 Happy Path。

重点属性：

- parent/student 永远不能取得 researcher/admin 权限；
- A 用户永远不能通过 user_id 读取 B 用户私有数据；
- disabled/expired token 不得继续写入；
- 高风险状态不得自动下发普通训练建议；
- 重复提交不得制造重复副作用；
- API 失败不得伪装成“没有数据”；
- 列表、分页、文本、ID、枚举必须有上限和无效值行为；
- 生产发布/安全账户操作必须拒绝非管理员身份。

## Round E — Mutation Testing 式测试有效性审查

目标：不看“测试有多少”，而看：

> 如果把安全条件翻转，测试究竟会失败，还是反而保护了错误行为？

重点突变点：

- `role == admin` ↔ `role != admin`
- showcase full access true ↔ false
- participant → researcher elevation 删除/保留
- `>= risk threshold` ↔ `> risk threshold`
- owner ID ↔ request user_id
- disabled account auth_epoch 是否更新
- AI participant gate true ↔ false
- idempotency required true ↔ false

## Round F — CI / PR Gate 审查

目标：检查：

- 一个 Job 失败后是否导致其他审查证据消失；
- 安全扫描、前端构建、npm audit、小程序结构审计是否相互独立；
- 旧冻结测试是否与当前产品策略冲突；
- PR 绿色是否等价于发布可用；
- 静态门禁是否覆盖真正的权限攻击链。

## Round G — Adversarial Chain Correlation

最终把前六轮发现进行攻击链串联，只把有完整可达路径和实际副作用证据的问题提升为 CRITICAL/HIGH。

# 3. CRITICAL-01：认证后 Showcase Workspace 权限提升到 Admin

**类别：CWE-269 Improper Privilege Management / CWE-284 Improper Access Control**  
**严重度：CRITICAL**  
**置信度：高**  
**发布影响：阻断**

## 3.1 前置条件

攻击者只需要：

- 一个正常的、已登录的 `parent` 或 `student` 账号；
- 能向 SafeHome API 发起带 Bearer Token 的请求。

不需要：

- admin 密码；
- researcher 账号；
- `X-Admin-Token`；
- 数据库权限；
- 服务器 Shell；
- CloudBase 控制台权限。

## 3.2 入口 1：小程序正式清单包含 researcher-dashboard

`apps/miniprogram/app.json` 当前正式页面表包含：

- `pages/researcher-dashboard/index`
- `pages/debug/index`
- `pages/integration-test/index`

因此这些不是仓库外的开发草稿，而是当前小程序路由清单的一部分。

## 3.3 入口 2：researcher-dashboard 自动增加高权限 Header

`apps/miniprogram/pages/researcher-dashboard/index.js` 创建 API 时默认加入：

```js
"X-SafeHome-Researcher-Workspace": "1"
```

同时页面角色判断逻辑在 showcase 开启时，不再要求当前用户必须属于 `researcher/admin/supervisor`。

因此：

```text
showcase.enabled = true
```

时，普通已登录账号可以进入这套 Workspace 逻辑。

## 3.4 服务端权限提升

`backend/routes/auth_utils.py` 中：

```python
elevate_actor_for_showcase_researcher_platform(...)
```

在以下条件同时满足时：

1. Showcase researcher platform full access 开启；
2. Header 为 `X-SafeHome-Researcher-Workspace: 1`；
3. URL 命中研究平台命名空间；

会返回：

```python
{
    ...actor,
    "original_role": 原角色,
    "role": "admin",
    "showcase_access": True,
    "showcase_full_access": True,
}
```

受影响前缀包括：

- `/api/research/`
- `/api/therapeutic-assessment/`
- `/api/ai-qa/`
- `/api/relationship-pilot/`
- `/api/text-analysis/`
- `/api/operations-governance/`
- `/api/reliability/`
- `/api/content-review/`
- `/api/security/`
- `/api/ux-governance/`
- `/api/risk-review/`
- `/api/supervision/`
- 以及特定 `/api/messages` 写入路径

这不是“展示 UI”，而是服务端角色对象发生实际变化。

## 3.5 当前配置明确打开该能力

`content/showcase_access.json` 当前为：

```json
{
  "enabled": true,
  "researcher_platform_full_access": true,
  "allow_program_participation": true,
  "open_programs": true,
  "open_training_cards": true,
  "open_courses": true
}
```

文件 Notice 自己也写明：

> 正式发布前必须关闭。

## 3.6 Public Status 还会公开暴露开关状态

`GET /api/showcase-access` 无需登录即可返回：

- `enabled`
- `researcher_platform_full_access`
- `read_only_role_bypass`
- programs/cards/courses 开放状态

这本身不是根因，但降低了攻击者确认开发越权窗口是否开启的成本。

## 3.7 可枚举参与者 ID

`backend/routes/research_workspace.py` 的 `/api/research/participants`：

- 仅允许 researcher/supervisor/admin；
- 但经过 Showcase elevation 后普通 parent 会成为 admin；
- admin 不受“只看 assigned researcher enrollment”的限制；
- 返回字段明确包括 `u.id AS user_id`、nickname、role、各类记录计数。

因此攻击链可以从“取得 admin”继续推进到“取得可操作目标 ID”。

## 3.8 可产生真实高影响副作用：停用目标账号并撤销 Token

`backend/routes/security_controls.py`：

```text
PATCH /api/security/accounts/<user_id>/status
```

只要求：

```python
_actor("admin")
```

而 `backend/services/security_control_service.py::set_account_status()` 在合法 payload 下会：

```sql
UPDATE users
SET status = ?,
    status_reason = ?,
    auth_epoch = auth_epoch + 1
WHERE id = ?
```

允许状态：

- `active`
- `disabled`

当设置为 disabled 时：

- 目标账号被停用；
- `auth_epoch + 1`；
- 现有 Token 被撤销；
- 产生安全事件和审计记录。

这里存在“不能停用自己”的保护，但**没有阻止被 Showcase 提升成 admin 的普通 parent 停用其他账号**，因为服务只看到当前有效角色是 admin。

## 3.9 测试套件明确证明该路径是“被设计为成功”的

`backend/tests/test_showcase_access.py` 当前不是在防止这条链，而是在验证它能够工作。

测试明确包含：

- 普通 parent + workspace header 可以读 researcher dashboard；
- 可以给其他参与者写 researcher note；
- 可以给其他参与者发送 researcher message；
- `effective_role == "admin"`；
- 可以读 participants；
- 可以读 therapeutic assessment work queue；
- 可以命中 AI release transition；
- 可以命中 therapeutic production gate evaluate；
- 可以命中 security account status；
- 可以命中 operations release；
- 可以命中 reliability feature flags；
- 可以命中 content publish；
- 代表性 live write route 的断言是 `response.status_code != 403`。

因此该发现不是静态分析误报。

## 3.10 风险结论

这是典型的：

> **开发便利性后门 + 生产配置打开 + 客户端可控标记 + 服务端角色提升 + 高权限写接口可达**

在正式发布威胁模型下，应当视为认证后权限提升漏洞。

# 7. HIGH-04：Mutation Review 发现测试套件在主动保护开发越权行为

**严重度：HIGH**  
**性质：测试有效性 / Security Regression**

当前后端测试数量很大，但安全价值不能用 `986 passed` 来替代。

## 7.1 关键反例

`backend/tests/test_showcase_access.py` 当前的期望行为就是：

```text
ordinary parent
+ X-SafeHome-Researcher-Workspace: 1
→ effective_role = admin
→ research reads/writes not 403
```

也就是说，如果未来有人正确修复该权限提升，使 parent 获得 `403`，这些测试反而会失败。

## 7.2 Mutation 视角

以下“安全突变”当前会和测试目标产生冲突：

```text
allow_showcase_researcher_platform_full_access: true → false
role = admin → 保持原 participant role
parent research write: allow → 403
```

测试应当保护“安全不变量”，而不是保护“开发后门存在”。

### 建议的安全不变量

正式发布测试应冻结为：

```text
∀ participant_token:
  role(parent|student)
  + 任意自定义 Header
  → 不能成为 researcher/admin
```

以及：

```text
participant
→ /api/security/* write = 403
participant
→ /api/content-review/* publish = 403
participant
→ /api/operations-governance/* release = 403
participant
→ /api/research/* cross-user write = 403
```

开发 Showcase 测试如果必须保留，应与 Release Security Contract 完全分离。

# 8. HIGH-05：账号 Bootstrap 工具的能力边界与冻结测试发生安全契约漂移

**严重度：HIGH / Release Contract Drift**

```python
ALLOWED_BOOTSTRAP_ROLES = {
```

1. 这是 researcher-only 管理工具；还是
2. 正式的 general account bootstrap 工具。

然后统一命名、测试、权限和审计规则。

# 17. Positive Controls：本轮确认值得保留的安全设计

对抗性审查不仅找问题，也要避免误报。以下机制是当前架构中的有效控制。

## PC-01 Actor-first 私有数据归属

`resolve_actor_user_id()` 在已认证 participant 存在时优先使用 actor ID，而不是信任客户端传入 `user_id`。

这对抑制常见 IDOR 很重要。

## PC-02 Token epoch 撤销机制

账号状态变化可以递增 `auth_epoch`，旧 Token 随即失效。

问题不在该机制，而在“谁有权触发它”。

## PC-03 Disabled account 有服务端检查

服务端会拒绝停用账号继续使用现有身份。

## PC-04 Legacy Admin Token 在 production 默认关闭

`legacy_admin_token_enabled()` 默认只在 development/testing 开放；production 需要额外显式配置。

## PC-05 Showcase 没有直接覆盖通用 `/api/auth/admin-create-account`

现有测试也明确验证 researcher workspace 临时权限不直接打开 generic account administration。

这缩小了一部分爆炸半径。

## PC-06 Fault Injection / External Ingest / Production Model Replacement 仍默认关闭

Dockerfile 中：

- `OFFLINE_EXTERNAL_INGEST_ENABLED=0`
- `OFFLINE_PRODUCTION_REPLACEMENT_ALLOWED=0`
- `RELIABILITY_FAULT_INJECTION_ENABLED=0`

说明高危运行能力不是全部打开。

## PC-07 SQL 高影响账户状态修改使用参数化查询

`set_account_status()` 使用绑定参数，不存在显眼 SQL 拼接注入。

## PC-08 本轮未确认真实 Secret 泄露

针对几类常见 key pattern 搜索未确认真实生产凭据。

这只是“未发现”，不是完整 Gitleaks 审计的替代。

# 27. 最终结论

SafeHome 当前并不是“安全机制缺失”的项目。相反，它已经具有：

- Token epoch；
- owner-first identity；
- capability / role；
- audit log；

- idempotency；
- content governance；
- risk gate；
- API contract；
- 大规模测试；
- 多个发布/可靠性开关。

当前主要问题是：

> **开发验证能力、正式运行能力和安全治理事实没有彻底分层。**

最严重后果是一个为了联调方便设计的 Showcase capability，跨越了原有 role/capability 边界，并被当前 production-scope 配置和测试共同保留。

```text

→ 权限不变量冻结
→ 测试从“功能可达”转为“越权不可达”
→ 独立安全门禁
→ 最后再进入真机/正式发布验收
```
