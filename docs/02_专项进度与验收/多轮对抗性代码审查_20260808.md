# 2. 方法：六轮核心审查 + 一轮攻击链交叉验证

## Round A — Semgrep 式语义规则审查

目标：寻找“一旦这种代码模式出现，就应当自动报警”的危险结构。

重点规则模型：

- 生产环境开启 development/showcase bypass
- participant 页面调用 researcher/admin 能力
- 客户端可控 Header 参与服务端角色提升
- 正式 `app.json` 注册 debug / integration-test 页面
- 调试页面执行真实写请求
- hardcoded 心理训练内容绕开受治理内容源
- 生产镜像直接开启高风险 Feature Flags
- 默认生产端点与调试写入入口组合
- `SELECT *` 出现在敏感 HTTP adapter
- 列表接口缺少明确上限
- Shell / eval / 动态执行危险模式
- 私钥 / API Key / Token 硬编码模式

## Round B — CodeQL 式跨文件数据流与权限流审查

目标：不只看函数内部，而是追踪：

```text
用户身份 → Token → Header → actor → role → capability → target object → side effect
```

重点数据流：

1. participant Token 到 researcher/admin 权限的传播；
2. `X-SafeHome-Researcher-Workspace` 从客户端到服务端权限决策；
3. researcher participant matrix 暴露的 `user_id` 到安全管理接口；
4. participant 传入 `user_id` 到对象归属解析；
5. 高风险状态到训练/AI/反馈下游动作；
6. AI participant 请求到真实 Provider；
7. production Feature Flag 到高权限执行面。

## Round C — Trivy / Gitleaks 式供应链、配置与 Secrets 审查

目标：检查 Secret 检测覆盖范围、默认密钥与生产保护、Docker 生产镜像配置、Python/npm 依赖安全证据、明显凭据以及安全扫描器自身漏检范围。

## Round D — Schemathesis 式 API 属性与状态机审查

重点检查角色 × 对象 × 状态 × 输入边界，包括跨用户访问、disabled/expired token、重复提交、高风险下游、异常与空数据区分、分页/长度上限和生产管理操作授权。

## Round E — Mutation Testing 式测试有效性审查

重点检查安全条件翻转后测试是否真的失败，特别是 role、showcase、owner、risk threshold、auth_epoch、AI gate 和 idempotency。

## Round F — CI / PR Gate 审查

重点检查 fail-fast 是否导致独立证据丢失、安全/前端/依赖/小程序门禁是否独立，以及旧冻结测试与当前策略是否冲突。

## Round G — Adversarial Chain Correlation

最终只把能够形成可达路径、权限变化或真实副作用的问题提升为 CRITICAL/HIGH。

# 29. CRITICAL-02：研究者可伪造参与者同意并覆盖撤回，审计主体同时错误归因

**类别：CWE-639 / CWE-862 / Consent Integrity / Audit Integrity**  
**严重度：CRITICAL**  
**置信度：高**  
**发布影响：阻断**

## 29.1 根因

`resolve_actor_user_id()` 对已认证的 `admin/supervisor/researcher` 采用如下语义：

```text
如果请求显式提供 user_id
→ 直接把该 user_id 当作目标对象
```

该 helper 本身没有检查：

- researcher 是否被分配给该参与者；
- 当前 route 是否允许代参与者写；
- 当前 capability 是否允许该操作；
- 当前 consent 是否只能由参与者本人表达。

## 29.2 `/api/consent` 直接继承该语义

`POST /api/consent` 调用：

```python
resolve_actor_user_id(payload=payload, allow_legacy_admin=False, allow_dev_fallback=True)
```

而允许的 consent type 包含：

- `research_authorization`
- `anonymous_research`
- `model_training`
- `ai_assistance`
- `relationship_analysis`
- `secondary_research`
- `contact_permission`
- `service_data`
- `quality_evaluation`

因此一个合法 researcher 账号可以向 participant B 的 `user_id` 写入 `agreed=true` 的研究/模型/AI/二次研究同意记录，而无需 participant B 本人重新确认。

## 29.3 可以逆转参与者撤回

隐私中心的正式撤回流程会追加一条：

```text
consent_type = research_authorization / anonymous_research
agreed = false
```

但当前研究授权判断采用“最新一条记录”为准。研究工作区和 research analysis 也按最新 consent 计算授权状态。

因此攻击/误操作链可以变成：

```text
participant 主动撤回 research_authorization
        ↓
最新记录 agreed=false
        ↓
researcher POST /api/consent
payload.user_id = participant
agreed=true
        ↓
产生更晚的 consent record
        ↓
系统重新认为研究授权有效
```

这突破的是**参与者撤回权的完整性**，不是单纯数据读取权限。

## 29.4 审计证据还会把动作记录成参与者本人

当前 consent route 的审计：

```text
actor_id = user_id
```

这里的 `user_id` 已经是请求指定的目标参与者，而不是实际 Bearer actor。

结果是：

```text
researcher 实际发起
→ participant consent 被修改
→ audit log 看起来像 participant 自己操作
```

这是授权完整性与审计不可抵赖性同时失效。

## 29.5 修复方案

### P0-A：participant consent endpoint 必须 self-only

`/api/consent` 不再调用“可选目标”的通用 helper，而应：

```text
actor = require_login(allow_legacy_admin=False)
actor.role 必须是 parent/student
user_id 永远 = actor.id
```

如果 payload 仍含 `user_id`：

```text
user_id != actor.id → 403
```

更稳妥的方式是直接从 participant consent schema 删除 `user_id` 字段。

### P0-B：后台更正不能复用 participant endpoint

如果存在真实的行政更正需求，应创建独立 endpoint，例如概念上：

```text
/api/admin/consent-corrections
```

但它必须：

- 明确 reason code；
- supervisor/admin 双人批准；
- 保存实际 actor；
- 只做“更正证据”，不能伪造 participant 意愿；
- **不得把 participant 的 revoke 直接改成 agreed**。

### P0-C：撤回应具备单调安全语义

对 `research_authorization / model_training / secondary_research / ai_assistance` 等敏感 consent：

```text
participant revoke
→ 后台 actor 无权自动恢复
→ 只有 participant 新一次认证后的明确 reconfirm 才可恢复
```

建议为重新同意保存：

- `consent_text_hash`
- `consent_version`
- `recorded_by_actor_id`
- `recorded_by_role`
- `source`
- `supersedes_id`
- `reconfirmed_at`

### P0-D：修正审计模型

审计至少分离：

```text
actor_id = 实际认证操作者
target_user_id = 被影响参与者
```

不得再用 target user 代替 actor。

### 必须增加的回归测试

1. researcher 为自己未分配 participant 写 consent → 403；
2. researcher 即使已分配，也不能代 participant 写 `agreed=true`；
3. supervisor 不能伪造 participant consent；
4. participant 只能写自己的 consent；
5. participant revoke 后，后台请求无法恢复；
6. participant 自己重新认证并重新确认后才可恢复；
7. audit actor 必须等于真实操作者；
8. target participant 单独记录；
9. revoke → forged later consent 的 Mutation Test 必须失败。

### 发布验收条件

```text
任何 backend role 都不能通过 participant consent API 重新激活其他人的研究授权。
```

# 30. HIGH-06：关闭 Showcase 后仍存在系统性 researcher 横向对象越权

**置信度：高**

## 30.1 项目其实已经有正确的对象范围模型

`research_access_service.py` 已定义：

```text
has_object_scope()
require_object_scope()
```

researcher 只有满足以下之一才应访问 participant：

- enrollment 的 `assigned_researcher_id == actor.id`；
- 存在 active research scope assignment。

supervisor 也通过 assignment 获取对象范围。

这说明 SafeHome 的目标架构本身不是“researcher 默认看所有人”。

## 30.2 但 participant self-service routes 绕过了这套模型

通用 `resolve_actor_user_id()` 对 researcher/supervisor/admin 直接接受显式 `user_id`，而许多 participant route 仅调用该 helper，没有 `require_object_scope()`。

本轮已逐文件确认：

### Emotion Diaries

`POST /api/diaries`：researcher 可把 payload.user_id 指向任意参与者并代其创建日记。  
`GET /api/diaries?user_id=...`：researcher 可横向读取目标参与者日记。

数据包含 event description、emotion、automatic thought、behavior、raw text 等敏感心理记录。

### Checkins

`POST /api/checkins` 与 `GET /api/checkins?user_id=...` 同样继承任意 target semantics，包含 reflection、emotion before/after、helpfulness、skip reason。

### Assessments

`POST /api/assessment-results` 可在指定 participant 下提交测评；列表、详情、profile-position 同样接受目标 user_id。

这不仅是读取问题，还可能污染：

- score；
- risk result；
- profile position；
- training recommendation；
- longitudinal research data。

### Feedback

`require_admin_or_owner()` 当前把 `researcher/supervisor/admin` 都当作通用 owner-equivalent，因此 researcher 可以对任意 participant diary 生成 feedback，并产生 risk review 等下游副作用。

### Goals

`require_user_id / resolve_user_id_for_query` 最终仍委托给 `resolve_actor_user_id`。匿名 fallback 在 production 会被挡住，因此**本轮没有确认 production 未登录 user_id 冒充**；但 researcher 横向目标语义仍存在。

## 30.3 修复方案：身份解析与对象授权必须拆开

当前最大架构问题是一个 helper 同时承担：

```text
“我是谁？” + “我是否有权访问这个 user_id？”
```

应拆成至少两层。

### P0-A：self-service route 只允许 self

新增/统一概念：

```python
resolve_self_user_id()
```

规则：

- parent/student → actor.id；
- request user_id 不影响 owner；
- researcher/supervisor 不得通过 participant self-service API 进行跨用户操作；
- admin 若需要全局操作，走显式 admin route。

### P0-B：研究跨对象操作必须显式声明 capability + object scope

需要 cross-user 的研究 API 应使用：

```text
require_login
→ assert_capability
→ enrollment lookup
→ require_object_scope
→ target participant
```

不应使用裸 `user_id` 作为授权依据。

优先使用：

```text
enrollment_id / scoped participant reference
```

而不是直接接受任意 participant user_id。

### P0-C：`require_admin_or_owner()` 不得把 researcher 当全局 admin

建议语义调整为：

```text
admin → explicit global route only
owner → actor.id == record.user_id
researcher/supervisor → 必须提供 scope context 并验证 assignment
```

### P1-D：全仓迁移

必须系统审计所有：

- `resolve_actor_user_id`
- `require_user_id`
- `resolve_user_id_for_query`
- `require_admin_or_owner`

本轮已经确认 diaries/checkins/assessments/consent/feedback/goals；搜索还显示 supervision/reports/notifications/progress/programs/emotion thermometer/training plan/general growth 等处复用，不能只修已列出的几个 route。

### 回归测试矩阵

| Actor | Participant X assigned | Participant Y unassigned | Expected |
|---|---|---|---|
| parent X | self | Y | self 200 / Y 403 |
| student X | self | Y | self 200 / Y 403 |
| researcher A | X | Y | policy route X allowed / Y 403 |
| supervisor A | scoped X | Y | scoped only |
| admin | explicit admin endpoint | explicit admin endpoint | 按 admin contract |

必须对 diary/checkin/assessment/feedback/profile/consent/weekly report/message 等重复执行。

### 发布验收条件

```text
researcher 凭据本身不再等价于“可选择任意 user_id”。
```

# 31. HIGH-07：Participant 写接口的幂等设计缺少数据库并发唯一性

**类别：Race Condition / Data Integrity**  
**严重度：HIGH**  
**置信度：高**

## 31.1 当前模式

日记、打卡、目标、测评都采用类似：

```text
SELECT WHERE user_id + client_submission_id
if none:
    INSERT
```

这是典型 check-then-insert。

## 31.2 数据库没有对应唯一约束

当前 schema 中：

- `goals.client_submission_id TEXT`
- `emotion_diaries.client_submission_id TEXT`
- `checkins.client_submission_id TEXT`
- `assessment_results.client_submission_id TEXT`

未发现：

```text
UNIQUE(user_id, client_submission_id)
```

与之相反，新一些的 research/reliability 表已经为 idempotency key 设置数据库 UNIQUE，说明项目知道正确模式，只是 participant 核心表尚未统一。

## 31.3 并发影响

两个并发请求可以：

```text
Request A SELECT → none
Request B SELECT → none
Request A INSERT
Request B INSERT
```

最终同一个 client submission 产生两条记录。

测评链尤其可能重复产生：

- assessment result；
- risk review；
- profile/recommendation 派生；
- 纵向研究记录。

## 31.4 修复方案

### P1-A：数据库唯一约束

对核心幂等写增加：

```text
UNIQUE(user_id, client_submission_id)
```

NULL 可继续允许多个无 key 记录；正式高价值写建议逐步要求 key 非空。

### P1-B：先做历史重复清理再迁移

迁移前：

1. 找重复 `(user_id, client_submission_id)`；
2. 冻结 canonical record 规则；
3. 重连下游引用；
4. 保留脱敏修复审计；
5. 再创建唯一索引。

### P1-C：原子 insert + request hash

不要先查后插。应：

```text
atomic insert
→ duplicate key catch
→ load existing row
→ request_hash 相同：replay
→ request_hash 不同：409 idempotency_conflict
```

SQLite/MySQL 都要有等价实现。

### P1-D：高价值接口要求 Idempotency-Key

优先：

- assessment submission；
- checkin；
- diary；
- consent（若保留可写）；
- privacy actions；
- message/research write。

### 并发回归测试

至少用两个独立 DB connection/线程同时提交：

```text
same actor + same key + same payload
→ DB row = 1
→ responses point to same id
```

以及：

```text
same actor + same key + different payload
→ one canonical success
→ other 409
```

# 32. HIGH-08：家庭绑定码防爆破控制实际无效，并存在并发抢占窗口

**类别：Authentication/Binding Abuse / CWE-330 / Race**  
**严重度：HIGH**

## 32.1 表面控制

代码声明：

```text
MAX_BIND_ATTEMPTS = 5
BIND_CODE_EXPIRES_HOURS = 24
```

并向用户提示“超过 5 次尝试后失效”。

## 32.2 实际错误尝试不计数

`bind-student` 首先按传入 6 位码查 pending link。

如果猜错：

```text
row is None
→ 立即 404
```

没有任何地方增加：

- student attempt counter；
- IP/device counter；
- global abuse counter；
- nonexistent code failure budget。

`attempt_count` 只有在已经猜中某个真实 link 后才有意义，因此“5 次”不能阻止遍历不同 6 位码。

## 32.3 绑定码使用 `random.randint`

6 位码来自 Python `random`，不是 `secrets`。同时空间只有 1,000,000，24 小时有效。

不能仅以“需要 student 登录”作为安全控制，因为任何合法 student 账号都可以成为枚举主体。

## 32.4 并发兑换缺少条件更新

找到 pending row 后最终 UPDATE 只按：

```text
WHERE id = ?
```

没有把 `status='pending' / student_user_id IS NULL / expires_at / version` 一并放进原子条件。

并发两个 student 在读取 pending 后都有机会进入更新路径，存在 last-write-wins 风险。

## 32.5 修复方案

### P0-A：密码学随机生成

至少改用 `secrets`。若仍需要人工输入短码：

- 增加长度/字符空间；
- 配合严格速率限制；
- 短有效期；
- 单次使用。

若可通过扫码/深链，优先高熵随机 token（约 80–128 bit）。

### P0-B：错误码统一 + 多维限速

错误的存在/不存在 code 不应产生可用于枚举的差异。

限制维度至少：

- student account；
- device/session；
- IP / gateway identity；
- bind target；
- 全局异常阈值。

错误 code 不存在也必须消耗 abuse budget。

### P0-C：原子单次兑换

概念 SQL：

```text
UPDATE family_links
SET student_user_id=?, status='active', ...
WHERE id=?
  AND status='pending'
  AND student_user_id IS NULL
  AND expires_at > now
```

然后要求：

```text
rowcount == 1
```

否则返回 409/410。

### P1-D：监护关系建议二阶段确认

对于未成年人敏感数据权限，建议：

```text
student 输入/扫描 bind token
→ pending_confirmation
→ parent 在自己已认证 session 确认
→ guardian link active
```

猜中一个 token 不应单独等价于最终监护授权。

### 回归测试

- 第 6 次错误尝试被阻断；
- 不存在 code 也计入限速；
- 两个 student 并发兑换仅一个成功；
- code 过期不能兑换；
- code 单次使用；
- 生成代码不得依赖 `random`；
- 响应不泄露 code 是否存在。

# 33. HIGH-09：隐私删除“verified”存在白名单覆盖盲区

**类别：Privacy Erasure Completeness / Data Lineage Drift**  
**严重度：HIGH（发布门禁）**  
**当前执行状态：生产策略本身尚未批准，因此属于上线前必须修复的潜伏缺陷**

## 33.1 当前删除执行器是手工白名单

`privacy_request_service.py` 通过：

```text
PRIVACY_HANDLING_SCOPES
SCOPE_TABLES
DIRECT_USER_TABLES
```

决定 preview、delete 和 verification 覆盖哪些表。

其中：

```text
research_outputs = (records, profile_reviews)
```

## 33.2 新研究分析数据不在该范围

但当前数据库已经存在：

- `research_analysis_snapshots`，含 `participant_user_id`；
- `research_analysis_snapshot_links`；
- `research_analysis_jobs`；
- `research_analysis_artifacts`；
- `research_analysis_events`。

`research_analysis_service` 有独立的 consent invalidation/freeze 和 `delete_artifact()`，但本轮没有发现它被 privacy delete executor 纳入统一删除事务。

## 33.3 更严重的是 verification 也只验证同一白名单

`_verify_deleted_scope()` 遍历：

```text
for scope in scopes:
    for table in SCOPE_TABLES[scope]
```

因此如果某张新 participant-linked table 根本没有进入 SCOPE_TABLES：

```text
preview 不会看到它
→ executor 不会删它
→ verifier 也不会检查它
→ status 仍可能是 verified
```

这是典型的**自洽但不完整验证**。

## 33.4 当前有一个重要缓解控制

`privacy_retention_policy.json` 当前仍为：

```text
approval_status = owner_confirmation_required
release_status = not_approved
```

production `_execution_gate()` 要求 policy approved，因此当前不应把该问题描述成“已经发生生产删除欺骗”。

但如果只审批现有 policy 而不修数据血缘覆盖，该缺陷会直接进入正式执行。

## 33.5 修复方案：从数据血缘生成删除矩阵，而不是继续手工补 tuple

### P1-A：建立 Participant Data Registry

每个表/资源必须声明：

```text
participant link column / relation
privacy scope
retention class
delete / anonymize / retain-with-legal-basis
cascade order
verification query
```

例如 research analysis：

```text
snapshot(participant_user_id)
→ links/jobs/artifacts/events
```

### P1-B：CI 做 Schema-to-Privacy Coverage Gate

每次 schema 新增表或 participant identifier 时：

```text
没有 privacy classification
→ CI BLOCKER
```

不能依赖开发者记得手工修改 `SCOPE_TABLES`。

### P1-C：verification 必须从独立事实源生成

当前 executor 与 verifier 共享同一白名单，存在共同模式失效。

应改成：

```text
Data Registry / Schema Lineage
→ expected coverage
Executor uses plan A
Verifier independently scans residual relation
```

至少不能由同一个漏项列表同时决定“要删什么”和“检查什么”。

### P1-D：研究派生数据明确策略

对 research analysis 不能含糊处理：

- 可删除 → transactional delete / tombstone；
- 依法/伦理批准保留 → 不再使用直接 participant ID，做不可逆替换，并记录 legal basis / retention deadline；
- consent revoke → 立即 suspend；
- delete-my-data → 按批准策略 delete/anonymize，而不只是“下次读取时冻结”。

### 回归测试

新增任意 participant-linked table 后，如果未加入 privacy registry：CI 必须失败。

执行删除后：

```text
对 user_id / participant_user_id / enrollment lineage / source links
做全残留扫描
→ 未批准 residual count 必须为 0
```

# 34. MEDIUM-08：密码失败锁号可被用于账户拒绝服务与渐进枚举

**类别：Authentication Abuse / Account Lockout DoS**  
**严重度：MEDIUM**

## 34.1 当前行为

账号密码登录：

```text
MAX_PASSWORD_FAILURES = 5
PASSWORD_LOCK_MINUTES = 15
```

对真实存在账号连续输错密码会累加失败计数，并在达到阈值后返回 `account_locked / 423`。

对不存在用户名则无法对用户记录累加，也不会进入同一 locked 状态。

本轮仓库搜索未发现 Flask-Limiter 或等价独立 login rate-limit 中间件。

## 34.2 风险

攻击者若知道/猜测用户名，可以反复触发：

```text
5 次错误密码
→ 目标账号锁 15 分钟
```

并且多次探测可以利用“最终是否进入 423”作为额外的账号存在信号。

这不是凭据绕过，但会影响研究者/管理员/参与者可用性。

## 34.3 修复方案

- 不以固定少量错误永久承担主要防爆破职责；
- 采用 username hash + IP/device 的多维速率限制；
- progressive delay / exponential backoff；
- 对攻击源限速优先于持续锁死受害账号；
- 登录错误对外保持尽量一致；
- 高权限账号可增加 MFA/step-up；
- 锁定/解锁事件进入安全监控；
- 提供安全的账号恢复流程；
- 对分布式攻击增加 gateway/WAF rate limiting。

### 回归测试

- 同 IP 对多个用户名高速尝试被限速；
- 多 IP 对同用户名异常尝试产生告警而非无限反复锁号；
- unknown/existing username 的外部响应不形成稳定枚举 oracle；
- 正常用户恢复不需要降低密码策略。

# 35. 第二轮架构级解决方案：不要逐 endpoint 打补丁

本轮最重要的修复建议不是增加更多 if，而是重构四个安全边界。

## 35.1 Identity Boundary

只负责回答：

```text
当前真实 actor 是谁？
```

输出：

- actor.id
- actor.role
- actor.auth_epoch
- actor.source

不得在这一层根据 `request.user_id` 自动产生目标授权。

## 35.2 Authorization Boundary

单独回答：

```text
actor 是否有 capability？
actor 是否有 target object scope？
```

研究者必须：

```text
capability AND assignment/scope
```

而不是：

```text
role == researcher → 任意 user_id
```

## 35.3 Consent Boundary

participant 意愿必须是不可冒充的独立事实：

```text
participant self action
≠ researcher/admin correction
```

撤回不得由后台角色隐式逆转。

## 35.4 Data Lifecycle Boundary

每张 participant-linked 表在 schema 创建时就必须同时登记：

```text
ownership
research scope
consent dependency
retention
deletion/anonymization
verification
```

避免功能上线后 privacy whitelist 落后。

# 39. 第二轮最终发布结论

第二轮证明：第一轮的 Showcase 提权并不是唯一的安全阻断项。

即使马上执行：

```text
showcase_access.enabled = false
researcher_platform_full_access = false
```

仍然存在：
