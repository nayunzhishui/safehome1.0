- 非诊断文案模板；

- 小程序画像结果页；

- 没有通过伦理边界检查的内容不得进入用户端。

## 1. 总体结论

0版网页不应作为一个独立页面直接并入安心家，也不应以“旧网页入口”的形式暴露给用户。它应沉淀为安心家的“评估画像与反馈引擎”：

```text
安心家 = 主平台
0版网页 = 评估画像与反馈引擎
GitHub 参考项目 = 可借鉴的产品机制、工程结构和心理学表达方式
```

整合后的主链路建议为：

```text
测评/记录
-> 支持性解释
-> 阶段性画像
-> 推荐一个小任务
-> 训练/打卡
-> 周报/复测
-> 后台导出/人工复核/督导
```

核心原则：

- 安心家继续作为主平台，承载目标设定、情绪事件记录、反馈、训练卡、打卡、周报和人工督导；
- 0版网页只沉淀为测评、画像、解释反馈、任务推荐和研究导出能力；
- 学生端统一称为“支持性测评”“阶段性画像”“压力反应画像”，不出现“0版网页”“人格诊断”等内部或风险表述；
- 技术上采用小步扩展，不做全项目重构；
- 心理学内容采用专家审核规则和模板，不做自由 AI 心理咨询；
- 数据导出默认匿名化、脱敏、受授权控制；
- 高风险文本进入人工复核，不进入普通自动反馈。

### 1.1 对项目计划书的帮助

这一路线能帮助项目计划书把“0版网页”和“安心家”讲清楚：

- 0版网页不是被废弃，而是成为安心家的评估引擎；
- 安心家不是简单套壳，而是形成长期陪伴式支持闭环；
- GitHub 项目不是复制对象，而是为系统结构、用户体验、心理学内容提供参考；
- 后续计划书可按“主平台 + 评估引擎 + 研究导出能力”来组织。

### 1.2 对 safehome1.0 的改进帮助

这一路线对当前项目的直接帮助：

- 明确下一轮重点不是继续堆页面，而是新增“学生画像”能力；
- 把测评结果从“保存分数”升级为“解释、推荐任务、复测追踪”；
- 把训练卡和周报从固定内容升级为基于画像和记录的支持性反馈；
- 把后台导出从普通 CSV 扩展为可研究、可脱敏、可审计的数据入口；
- 把心理学边界从说明文字落实到 API 字段、规则库和导出策略。

## 4. 逐项目细节分析与 safehome 落地

### 4.1 FreeCBT

项目定位：

- 轻量 CBT 思维记录与认知重构工具；
- 围绕“事件、自动想法、情绪、证据、替代想法”组织；
- 适合参考训练卡流程，而不是参考整体产品形态。

对方做法：

- 用户先记录触发事件；
- 写下当时的自动想法；
- 选择可能的认知偏差；
- 填写支持证据和反对证据；
- 形成更平衡的替代解释；
- 复评情绪强度。

可借鉴点：

- 把心理练习拆成稳定步骤，不依赖复杂对话；
- 每一步保存结构化字段，方便后续统计；
- 训练结果可以进入周报；
- 认知偏差用“可能的思考习惯”表达，不做诊断。

对项目计划书的帮助：

- 可以作为 CBT 训练卡设计的开源参考；
- 说明安心家训练卡不是泛泛鼓励，而是有明确心理学机制；
- 可放入“心理干预任务设计依据”。

对 safehome1.0 的改进建议：

- 训练卡增加 CBT 分类；
- 反馈页增加“自动想法 -> 替代解释 -> 一小步行动”结构；
- 情绪记录结果可推荐 CBT 训练卡；
- 周报统计完成了几次认知重构，以及练习前后情绪评分变化。

最小实现：

```json
{
  "id": "cbt_auto_thought_01",
  "category": "cbt",
  "title": "把自动想法写下来",
  "duration_minutes": 5,
  "steps": [
    "写下刚才发生的事",
    "写下脑中最强烈的一句话",
    "给这句话找一个支持证据和一个反对证据",
    "写出一个更平衡的替代解释"
  ],
  "suitable_for": ["test_anxiety", "pressure_alert"],
  "risk_boundary": "high_risk_text_requires_human_review"
}
```

验收标准：

- 至少新增 3 张 CBT 训练卡；
- 训练卡不出现“你有认知错误”等评价性表达；
- 打卡结果能保存练习前后情绪评分；
- 周报能统计 CBT 训练完成次数。

### 4.2 Tempo

项目定位：

- 情绪日记和标签记录工具；
- 重点是低门槛记录、标签、趋势和隐私感。

对方做法：

- 用户写一段日记或事件；
- 选择情绪和标签；
- 后续按标签和时间回看；
- 强调用户对记录的控制感。

可借鉴点：

- 自由文本和标签并存；
- 记录入口短，不像研究问卷；
- 标签让长期记录变得可统计；
- 隐私感能降低用户填写顾虑。

对项目计划书的帮助：

- 可以证明安心家需要“轻量记录 + 标签 + 趋势”，而不是只做一次性测评；
- 可写入用户体验设计依据。

对 safehome1.0 的改进建议：

- 情绪记录增加标签：考试、亲子沟通、同伴关系、睡眠、身体不适；
- `raw_text` 不只是备注，后续用于关键词、压力源、资源线索；
- 周报增加高频标签；
- 导出时默认隐藏自由文本原文。

验收标准：

- 情绪记录支持至少 5 类标签；
- 周报能显示本周高频标签；
- 自由文本导出默认脱敏或不导出；
- 用户可以不写长文本也能完成记录。

### 4.3 Nomie 6 OSS

项目定位：

- 生活、情绪和行为追踪系统；
- 核心思想是“文本即数据”和统一 log。

对方做法：

- 用户输入自然语言记录；
- 系统识别 tracker 或标签；
- 保存成统一日志；
- 后续按指标、标签、时间统计。

可借鉴点：

- 不同模块可以先进入各自业务表，再同步成统一记录；
- `records + data_json` 适合研究导出；
- 文本解析应作为中期能力，第一版先做手动标签更稳。

对项目计划书的帮助：

- 可作为多源异构数据统一建模的参考；
- 支撑夏老师“records 表结构”思维导图。

对 safehome1.0 的改进建议：

- 短期继续保留现有业务表；
- 中期新增 `records` 表；
- `student_profile`、`parent_log`、`sandplay_task`、`checkin` 等关键事件同步到 `records`；
- 后台研究导出优先从 `records` 查询。

验收标准：

- `records` 有数据字典；
- `module_type` 取值受控；
- `data_json` 只保存研究所需摘要，不乱塞敏感原文；
- 不破坏现有业务表查询。

### 4.4 Loop Habit Tracker

项目定位：

- Android 习惯追踪工具；
- 强调离线、趋势、习惯强度和导出。

对方做法：

- 创建习惯；
- 按日或周期打卡；
- 查看习惯强度和历史趋势；
- 支持 CSV/SQLite 导出。

可借鉴点：

- 打卡不是惩罚系统；
- 趋势比单次完成更重要；
- 数据导出是长期产品信任的一部分；
- 打卡记录要成为独立数据，而不是只存在前端。

对项目计划书的帮助：

- 可支撑“训练打卡与周报趋势”设计；
- 说明安心家不是只推任务，还要让用户看到练习积累。

对 safehome1.0 的改进建议：

- 打卡页不显示断签失败；
- 周报展示练习累计、近 7 日完成率、练习前后情绪变化；
- 后台导出增加训练卡完成统计；
- 提醒功能默认弱提醒，不制造压力。

验收标准：

- 打卡文案不出现“失败、断签、落后”等惩罚式表达；
- 周报至少展示一个训练趋势指标；
- 后台能导出训练卡完成次数；
- 用户未完成打卡时仍能获得支持性反馈。

### 4.5 if-me.org

项目定位：

- 心理健康经历分享与可信支持网络；
- 强调支持者、权限、协作和边界。

对方做法：

- 用户记录心理健康经历；
- 选择是否分享给可信联系人；
- 可信支持者查看并回应；
- 用户可管理权限。

可借鉴点：

- 支持网络需要权限模型；
- 用户必须控制谁能看、看什么、何时撤回；
- 支持者不是医生，系统要说明边界；
- 人工支持适合后置，不适合第一版复杂化。

对项目计划书的帮助：

- 可说明安心家后续为什么需要督导和支持网络；
- 可作为伦理边界和权限设计参考。

对 safehome1.0 的改进建议：

- 督导入口增加“非即时危机服务”说明；
- 普通督导和高风险复核分开；
- 后续可增加可信支持者备注；
- 默认不对家长、教师或督导暴露学生自由文本原文。

验收标准：

- 督导页有明确服务边界；
- 高风险提示不承诺即时干预；
- 后台只展示必要摘要；
- 任何支持者共享功能必须有权限和撤回机制。

### 4.6 Journal Tree

项目定位：

对方做法：

- 用户写日记；
- 系统做摘要或主题提取；
- 生成情绪/主题洞察；
- 用户回看趋势。

可借鉴点：

- 文本洞察要短；
- 报告页必须显示边界声明；
- 文本分析只能辅助，不应替代量表或人工判断；
- 第一版可先做关键词和主题标签，不做复杂向量检索。

对项目计划书的帮助：

- 可说明自由文本的价值和风险；
- 支撑“非诊断反馈动态生成”的技术边界。

对 safehome1.0 的改进建议：

- 自由文本只做辅助线索；
- 报告固定展示非诊断边界；
- 周报增加“本周重复主题”；
- 高风险文本进入人工复核，不进入普通洞察。

验收标准：

### 4.7 MoodTracker

项目定位：

- 情绪记录、情绪趋势和短练习类项目集合；
- 常见形态是 PWA、离线记录、情绪图表、呼吸/冥想练习。

对方做法：

- 用户快速选择心情；
- 可选填写备注；
- 可选完成短练习；
- 查看每日或每周趋势。

可借鉴点：

- 情绪记录入口要短；
- 情绪命名本身就是调节；
- 短练习适合高压力时降低启动门槛；
- 图表先做简单折线/柱状即可。

对项目计划书的帮助：

- 可支撑“轻量情绪记录”和“短练习”的产品必要性；

对 safehome1.0 的改进建议：

验收标准：

对 safehome1.0 的改进建议：

### 5.3 P1：学生画像最小 API

规划接口：

| 方法 | 接口 | 用途 | 状态 |
|---|---|---|---|
| `POST` | `/api/profile` | 根据量表分数和自由文本生成学生画像 | 规划 |
| `GET` | `/api/profile/<id>` | 获取单次画像结果 | 规划 |
| `GET` | `/api/profile/history` | 获取画像历史和复测趋势 | 规划 |
| `GET` | `/api/model/info` | 获取当前规则或模型说明 | 规划 |
| `POST` | `/api/risk/check` | 高风险关键词检查 | 规划 |

### 5.5 P3：趋势、周报与人工督导

本节根据以下三个文件补充：

这些内容需要作为后续实现时的硬约束，而不是普通建议。

#### 5.7.1 模型 API 化控制点

夏老师文件强调：0版网页中的画像模型不能继续停留在静态网页内部，而要变成安心家可调用的服务。后续实现 `POST /api/profile` 时，需要同时满足以下要求：

| 控制点 | 具体要求 | 对 safehome1.0 的落地方式 |
|---|---|---|
| 输入输出标准化 | 小程序、网页后台、研究端都使用统一 JSON 字段 | 统一 `scores`、`free_text`、`round`、`source`、`anonymous_id` |
| 模型版本记录 | 模型、规则、推荐任务变更后必须可追溯 | 输出 `model_version`、`rules_version`、`recommended_task_version` |
| 低置信度处理 | 边界样本不能强行输出明确画像 | `confidence < 0.7` 时显示“继续观察”，不显示强标签 |
| 服务响应速度 | 用户端不应长时间等待 | P1 目标：普通请求 2 秒内返回；超时进入兜底 |
| 服务失败兜底 | 接口异常、超时、网络失败时不能中断体验 | 返回温和通用说明：“结果稍后查看”，不显示报错代码 |
| 人工复核入口 | 边界样本、高风险样本、用户质疑结果样本进入复核 | 输出 `requires_review=true`，后台进入复核列表 |
| 热更新与回退 | 模型或规则更新不影响线上服务 | 内容库保留版本号，旧版规则可回退 |

服务失败兜底文案建议：

```text
这次结果暂时没有生成完整报告。你填写的内容已经保存，可以稍后再查看。
在等待期间，可以先做一个 3 分钟情绪命名练习，帮助自己稳定下来。
```

低置信度文案建议：

```text
本次填写显示的信息还不够形成明确画像。你可以先查看各维度提示，或者在一段时间后再次填写。
这不是诊断，也不代表你没有进展。
```

#### 5.7.2 多源数据建模控制点

夏老师文件强调，多源数据不是简单合并，而是要“统一但不混淆”。后续数据库和导出必须处理以下问题：

| 问题 | 风险 | 技术处理 |
|---|---|---|
| 数据语义漂移 | 量表、规则、训练卡版本变化后，同一字段前后含义不同 | 每条记录保存 `version`、`source`、`round` |
| 身份贯通困难 | 学生端、家长端、后台无法追踪同一轮次 | 使用 `anonymous_id` 串联，不用姓名/手机号作主键 |
| 缺失和重复 | 未完成测评、重复提交、打卡中断影响分析 | 增加 `data_quality`：complete / partial / duplicate / corrected |
| 导出不可用 | 没有数据字典会导致后期清洗困难 | 每个导出类型必须附字段说明 |
| 文本和沙盘过度解释 | 可能被误用为诊断依据 | 文本/沙盘只存摘要指标，原文默认不导出 |

建议在后续 `student_profiles` 或 `records` 中增加：

```text
anonymous_id
round
source
rules_version
model_version
data_quality
export_allowed
review_status
```

`data_quality` 建议取值：

| 值 | 含义 |
|---|---|
| `complete` | 完整提交 |
| `partial` | 部分完成 |
| `duplicate` | 疑似重复 |
| `corrected` | 人工修正 |
| `review_required` | 需要人工复核 |

#### 5.7.3 前端融合控制点

夏老师文件强调：整合不是页面拼接，而是体验融合。后续小程序和网页端必须遵守：

- 一页一个主要任务：记录页只负责记录，反馈页只负责理解，训练页只负责练习；
- 角色入口分流：学生、家长、研究人员、督导人员看到的入口和信息不同；
- 用户端只展示简短结论、关键维度和下一步建议；
- 雷达图、PCA 图、关键词云等复杂图表优先放在“查看更多”或研究后台；
- 小程序端报告优先采用“上图下文、卡片分段、短文本”的结构；
- 0版网页功能进入安心家后，视觉上必须像安心家模块，不像外部跳转系统。

用户端图表分级：

| 图表 | 用户端是否展示 | 后台/研究端是否展示 | 说明 |
|---|---|---|---|
| 画像卡 | 是 | 是 | 第一阶段核心展示 |
| 维度条 | 是 | 是 | 比雷达图更适合手机 |
| 雷达图 | 可后置 | 是 | 第二阶段加入 |
| 轮次趋势图 | 是 | 是 | 用于复测动机 |
| PCA 分布图 | 不默认展示 | 是 | 用于模型透明和研究解释，不做诊断 |
| 热力图 | 否 | 是 | 研究后台使用 |

#### 5.7.4 动态反馈生成控制点

夏老师文件提出，反馈要“说话得体又科学”。后续所有反馈模板必须使用固定结构：

```text
状态描述
-> 非评判解释
-> 资源或优势提醒
-> 一个小步建议
-> 非诊断边界
```

每条反馈规则必须标注：

| 字段 | 说明 |
|---|---|
| `id` | 规则 ID |
| `trigger` | 触发条件 |
| `theory_source` | 理论来源，如 CBT / ACT / UP / 沙盘表达 |
| `risk_level` | 风险等级 |
| `recommended_card_ids` | 推荐训练卡 |
| `review_status` | 审核状态 |
| `version` | 规则版本 |
| `boundary_notice` | 非诊断边界 |

禁止：

- 不允许系统自由生成诊断性结论；
- 不允许多人随意修改规则后直接上线；
- 不允许高风险文本继续进入普通训练卡推荐；
- 不允许用户端出现“系统判断你……”。

#### 5.7.5 伦理边界技术化控制点

夏老师文件提出“四层防护机制”：Prevention、Monitoring、Control、Audit。后续落地应按下表执行：

| 防护层 | 目标 | safehome1.0 实现方式 |
|---|---|---|
| 预防层 Prevention | 防止系统默认采集过多敏感数据 | 不采集人脸、音频、视频；自由文本可选；默认匿名 ID |
| 监控层 Monitoring | 发现高风险文本和边界样本 | `risk_keywords.json` + `requires_review` |
| 控制层 Control | 防止未授权导出和误用 | `export_allowed`、默认脱敏、隐藏自由文本原文 |
| 审计层 Audit | 操作可追溯 | 后续新增 `audit_logs`，记录查看、导出、规则修改 |

伦理边界必须变成系统硬约束：

- 如果 `risk_level=high`，系统不允许生成普通画像建议；
- 如果 `export_allowed=false`，导出接口不应导出该记录；
- 如果 `review_status=draft`，用户端不应使用该规则；
- 如果用户未授权研究导出，后台导出不应包含该用户数据；
- 如果请求超出角色权限，后台不显示敏感详情。

#### 5.7.6 五步迁移路线控制点

项目计划书提出五步迁移路线。结合当前项目状态，建议重写为以下执行版本：

| 步骤 | 原计划含义 | safehome 当前执行方式 | 完成标准 |
|---|---|---|---|
| 第 1 步：内容迁移 | 将训练卡、反馈规则、任务脚本导入安心家内容库 | 已开始新增 `student_profile_rules.json`、`risk_keywords.json`、学生端训练卡 | 内容文件合法、无悬空训练卡引用 |
| 第 2 步：模型服务化 | 将 0版网页模型封装为 API | P1 先实现规则版 `POST /api/profile`，后续再接模型参数 | API 可返回画像、置信度、维度、任务 |
| 第 3 步：数据表扩展 | 新增画像和轮次字段 | 短期复用 `assessment_results`，中期新增 `student_profiles` | 数据能保存轮次、版本、风险和导出状态 |
| 第 4 步：页面迁移 | 报告页进入安心家 | 小程序先做画像报告页，网页后台做画像列表 | 用户能测评 -> 画像 -> 训练 |
| 第 5 步：统一后台 | 综合看板和联合导出 | 先做 `type=profile` 导出，后续加审计和看板 | 导出脱敏、字段有数据字典 |

#### 5.7.7 PCA 分布图的定位

项目计划书中强调 PCA 分布图用于降低“黑箱感”。后续应这样定位：

- PCA 不是诊断图；
- PCA 不是给学生贴标签的依据；
- PCA 用于研究后台和人工复核；
- 如果进入用户端，只能作为“可解释辅助图”，并配合通俗说明；
- 第一阶段不应为了 PCA 阻塞画像 API 和训练卡闭环。

推荐顺序：

```text
第一阶段：画像卡 + 维度条
第二阶段：轮次趋势图
第三阶段：雷达图
第四阶段：研究后台 PCA 分布图
```

## 6. 产品体验优化路线

### 6.1 学生端核心路径

```text
测一测
-> 支持性画像测评
-> 阶段性画像报告
-> 推荐一个训练/沙盘任务
-> 完成训练或打卡
-> 周报看到趋势
```

页面原则：

- 入口文案使用“了解近期状态”，不使用“检测你有没有问题”；
- 自由文本可选填；
- 每页信息不要过密；
- 报告只给一个主要解释和 1-3 个建议；
- 用户随时可以退出，不要强制完成长流程。

### 6.2 家长端核心路径

家长端仍以情绪记录和亲子回应为主，不应强迫家长查看学生敏感画像。

建议：

- 家长记录一次事件；
- 系统生成非诊断反馈；
- 推荐亲子回应训练卡；
- 打卡记录练习感受；
- 周报展示家长练习积累。

边界：

- 学生自由文本默认不向家长展示；
- 如果后续开放共享，需要学生/监护规则和伦理审核；
- 家长端文案避免“你做错了”。

### 6.3 教师/督导端核心路径

```text
后台登录
-> 查看画像列表
-> 筛选风险等级/画像类型/时间
-> 查看详情
-> 添加人工备注
-> 导出匿名数据
```

后台优先能力：

- 匿名 ID；
- 画像类型；
- 置信度；
- 风险等级；
- 推荐任务；
- 复测趋势；
- 导出状态。

后台不应默认展示：

- 学生联系方式；
- 自由文本原文；
- 家庭隐私；
- 没有授权的详细个人信息。

### 6.4 研究人员路径

```text
选择导出类型
-> 设置时间范围
-> 选择是否包含文本摘要
-> 确认脱敏策略
-> 导出 CSV/Excel
-> 查看数据字典
```

研究导出要求：

- 默认匿名化；
- 字段解释完整；
- 量表分、画像、训练完成、复测轮次能关联；
- 高风险文本和自由文本原文默认不导出；
- 导出操作后续进入审计日志。

### 6.5 用户研究方法

| 研究环节 | 建议方法 | 观察指标 | 参考项目 |
|---|---|---|---|
| 测评填写 | 5-8 名学生/家长可用性测试 | 完成时间、放弃点、隐私说明理解 | WeUI、mindLAMP |
| 画像报告理解 | 让用户复述报告含义 | 是否误解为诊断、是否知道下一步 | Journal Tree、FreeCBT |
| 训练卡使用 | 任务完成后访谈 | 启动难度、完成率、情绪前后评分 | FreeCBT、MoodTracker |
| 打卡周报 | 连续 7 天试用 | 打卡压力感、周报回访率、趋势理解度 | Loop、Tempo |
| 后台导出 | 教师/研究人员任务走查 | 筛选成功率、字段理解、脱敏确认 | mindLAMP、Loop |

## 7. 心理学内容优化路线

### 7.1 非诊断表达

允许使用：

- “可能”；
- “看起来”；
- “阶段性画像”；
- “支持性观察”；
- “可以尝试”；
- “这不是诊断”；
- “本次填写显示”。

避免使用：

- “人格”；
- “障碍”；
- “异常”；
- “病态”；
- “你就是……”；
- “系统判断你……”；
- “必须治疗”；
- “严重问题”。

### 7.2 画像表达规范

推荐表达：

```text
压力警觉型画像
近期压力反应画像
阶段性支持画像
考试压力敏感画像
自我支持发展中画像
```

避免表达：

```text
压力警觉型人格
焦虑人格
回避型人格
异常压力反应
心理问题类型
```

每个画像报告必须包含：

- 画像名称；
- 置信度；
- 维度说明；
- 优势提示；
- 推荐任务；
- 非诊断边界；
- 必要时的人工复核提示。

### 7.3 CBT 内容转化

| CBT 环节 | FreeCBT 做法 | safehome 训练卡改造 | 验收标准 |
|---|---|---|---|
| 情境 | 记录触发事件 | 情绪记录中增加“发生了什么” | 用户能用一句话描述事件 |
| 自动想法 | 写下当时想法 | 反馈页提示“当时脑中冒出的想法可能是……” | 不把系统猜测写成确定判断 |
| 认知偏差 | 选择可能偏差 | 用“可能的思考习惯”替代“认知错误” | 用户可跳过或自行确认 |
| 证据检验 | 支持/反对证据 | 训练卡分两栏填写证据 | 完成后有替代解释 |
| 行动计划 | 形成新想法 | 推荐一个小步行动 | 行动可在 5 分钟内启动 |

### 7.4 量表维度与推荐任务映射

| 维度 | 可能含义 | 推荐任务 | 边界 |
|---|---|---|---|
| 考试焦虑高 | 对考试结果和评价更敏感 | 考前身体放松、自动想法记录、考后复盘 | 不能据此判断焦虑障碍 |
| IU 偏高 | 对不确定情境较难忍受 | 不确定性暴露小练习、可控/不可控清单 | 不把分数写成人格缺陷 |
| 恐惧倾向高 | 对威胁线索更警觉 | 安全感资源清单、情绪命名、沙盘表达 | 高风险内容需人工介入 |
| 自我同情低 | 自我支持语言不足 | 给朋友的建议、自我支持句改写 | 避免鸡汤式鼓励 |
| 自由文本压力源集中 | 近期重复压力场景 | 场景复盘、求助资源、下周小目标 | 文本只作为辅助线索 |

### 7.5 非诊断文案模板

```text
建议标题：近期压力警觉画像

推荐表达：
你近期可能更容易注意到压力信号，这说明你对环境变化较敏感。

优势提示：
这种敏感有时能帮助你提前发现问题，也说明你在认真对待重要事情。

行动建议：
今天先完成一个 3 分钟情绪命名练习，或者写下“我现在最担心的是什么”。

边界声明：
这不是诊断，也不代表你一直都会这样；它只是基于本次填写形成的支持性反馈。

避免表达：
你是压力警觉型人格 / 你存在异常焦虑 / 你需要治疗。
```

## 12. 总体验收标准

进入实现前，至少确认：

1. 画像接口字段已写入 API 文档；
2. 画像结果表或复用表策略已写入数据库文档；
3. 画像文案通过非诊断检查；
4. 高风险文本进入人工复核；
5. 导出默认匿名化；
6. 小程序和网页后台使用同一套画像数据结构；
7. 用户能从测评结果进入一个小任务，而不是停留在“被评价”的感觉中；
8. 训练卡至少包含 CBT、情绪调节、行为替代三类；
9. 打卡不显示断签失败；
10. 周报至少展示一个趋势指标；
11. 后台导出隐藏联系方式和自由文本原文；
12. 内容规则包含版本号和审核状态；
13. 后续若新增 records，不能破坏现有业务表；
14. 所有报告页固定显示非诊断边界；
15. 项目计划书能清楚说明：安心家是主平台，0版网页是评估画像与反馈引擎。

## 14. 模块级详细优化清单

本节用于把前文路线拆成后续可以直接执行的模块任务。每个模块都按“当前问题 -> 参考项目 -> 对方做法 -> safehome 修改 -> 交付物 -> 验收标准”整理。

### 14.1 测一测与学生画像模块

当前问题：

- 当前“测一测”更接近量表/工作表结果保存；
- 结果页主要展示分数和说明，还没有形成学生画像；
- 测评结果和训练任务之间的连接不够强；
- 0版网页的评估反馈能力还没有 API 化。

参考项目：

- mindLAMP：测评和活动配置化，后台可追踪和导出；
- Journal Tree：文本洞察必须带免责声明；
- FreeCBT：测评或记录之后应进入可执行练习。

对方做法：

- mindLAMP 把测评作为可配置活动，用户端只完成任务，后台负责数据查看；
- Journal Tree 用文本生成洞察，但强调边界声明；
- FreeCBT 不停留在“解释”，而是让用户进入结构化练习。

safehome 修改建议：

- 在 `content/assessment_worksheets.json` 增加 `student_profile_v1` 条目；
- 在小程序“测一测”入口中展示为“学生支持性画像测评”；
- 提交后调用 `POST /api/profile`，而不是只保存普通测评结果；
- 结果页展示“画像 + 维度 + 优势 + 推荐任务 + 非诊断声明”；
- 后台可查询画像结果和复测历史。

建议交付物：

| 交付物 | 类型 | 说明 |
|---|---|---|
| `student_profile_v1` | 内容配置 | 学生画像测评条目 |
| `student_profile_rules.json` | 内容规则 | 画像触发、解释、推荐任务 |
| `POST /api/profile` | 后端 API | 生成画像结果 |
| 画像结果页 | 小程序页面 | 展示支持性画像 |
| 画像列表页 | 网页后台 | 查看、筛选、导出 |

验收标准：

- 用户能从“测一测”进入画像测评；
- 提交后能得到非诊断画像；
- 画像结果必须推荐至少一个任务；
- 高风险文本不生成普通画像建议；
- 后台能看到画像记录。

### 14.2 情绪记录模块

当前问题：

- 当前记录已经能保存事件和情绪，但长期趋势价值还可以增强；
- `raw_text` 目前更像备注，尚未进入关键词和压力源分析；
- 记录字段和周报之间的连接还不够强。

参考项目：

- Tempo：自由文本、标签、趋势；
- Nomie：文本即数据，统一记录；
- MoodTracker：快速情绪记录和短练习。

对方做法：

- Tempo 允许用户写日记并添加标签，后续按标签回看；
- Nomie 把自然语言记录解析为可统计数据；
- MoodTracker 保持入口很短，先让用户记录下来。

safehome 修改建议：

- 情绪记录保留短表单，不扩成复杂问卷；
- 增加可选标签：考试、亲子沟通、同伴关系、睡眠、身体不适、学习压力；
- `raw_text` 后续可做关键词、压力源、资源词提取；
- 周报统计高频标签和重复压力场景；
- 导出时自由文本原文默认隐藏。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `emotion_tags` | array/string | 用户选择的场景标签 |
| `body_sensation` | string | 身体感受，可选 |
| `action_urge` | string | 当下想做的反应，可选 |
| `text_keywords` | array/string | 后端抽取的关键词，后续规划 |
| `resource_words` | array/string | 文本中出现的支持资源词，后续规划 |

验收标准：

- 用户不填写长文本也能提交；
- 至少支持 5 个场景标签；
- 周报可以统计标签频次；
- 自由文本不会默认出现在后台导出中。

### 14.3 反馈结果模块

当前问题：

- 当前反馈偏即时解释，还需要增强“行动转化”；
- 部分反馈如果过度解释，容易让用户感觉被评价；
- 学生画像反馈需要和家长情绪反馈区分。

参考项目：

- FreeCBT：反馈后进入认知重构；
- Journal Tree：洞察要有免责声明；
- WeUI Miniprogram：结果页表达要克制、清楚。

safehome 修改建议：

- 反馈页固定使用四段结构：

```text
我观察到...
这可能说明...
你可以先尝试...
这不是诊断...
```

- 家长情绪反馈：重点是亲子回应和自我调节；
- 学生画像反馈：重点是阶段性状态、优势提示、推荐任务；
- 高风险反馈：不输出普通建议，提示现实支持和人工复核。

验收标准：

- 每条反馈都有一个可执行任务；
- 反馈文案不使用“你就是”“系统判断你”；
- 结果页显示边界声明；
- 高风险场景不会输出常规训练建议。

### 14.4 训练卡模块

当前问题：

- 当前训练卡已有基础，但分类和心理机制还可以更清晰；
- 训练卡和画像结果的匹配关系需要明确；
- 打卡结果应反向进入周报。

参考项目：

- FreeCBT：CBT 结构化练习；
- MoodTracker：短练习降低启动门槛；
- Loop Habit Tracker：练习积累和趋势。

建议分类：

| 分类 | 适用场景 | 示例训练卡 | 参考项目 |
|---|---|---|---|
| CBT | 自动想法、考试焦虑、过度担心 | 自动想法记录、证据检验、替代解释 | FreeCBT |
| 情绪调节 | 情绪强烈、身体紧张 | 三秒暂停、3 分钟呼吸、身体扫描 | MoodTracker |
| 行为替代 | 冲突后想逃避或爆发 | 延迟反应、换一种表达、小步行动 | FreeCBT |
| 自我支持 | 自责、自我批评 | 给朋友的建议、自我支持句改写 | Journal Tree |
| 沙盘表达 | 难以语言表达、压力警觉 | 选择一个象征物、描述场景、说出感受 | 夏老师沙盘任务 |

训练卡字段建议：

```json
{
  "id": "emotion_naming_01",
  "category": "emotion_regulation",
  "title": "给现在的情绪取个名字",
  "duration_minutes": 3,
  "suitable_for": ["pressure_alert", "test_anxiety"],
  "steps": [
    "停下来感受身体最明显的位置",
    "从担心、紧张、委屈、生气、害怕中选一个最接近的词",
    "对自己说：我现在注意到这个情绪了",
    "做一次慢呼吸，再决定下一步"
  ],
  "boundary_notice": "这是情绪调节练习，不用于判断心理问题。"
}
```

验收标准：

- 每类至少 1-2 张训练卡；
- 每张训练卡有适用场景；
- 每张训练卡能在 3-8 分钟内完成；
- 每张训练卡都有边界说明；
- 训练完成结果能进入打卡和周报。

### 14.5 打卡与周报模块

当前问题：

- 打卡已有基础，但需要避免“签到失败”的压力；
- 周报应从数据汇总升级为支持性复盘；
- 周报需要连接记录、训练、画像和复测。

参考项目：

- Loop Habit Tracker：打卡趋势、习惯强度、导出；
- Tempo：标签频次和趋势；
- mindLAMP：研究数据追踪。

safehome 修改建议：

- 打卡文案统一为“练习积累”；
- 不展示断签、失败、排名；
- 周报展示 4 个核心块：
  - 本周情绪高频标签；
  - 本周重复模式；
  - 本周练习积累；
  - 下周一个建议。

周报数据来源：

| 周报块 | 数据来源 | 说明 |
|---|---|---|
| 高频标签 | `emotion_diaries` | 统计本周情绪记录标签 |
| 重复模式 | `raw_text` 摘要 / 标签 | 先手动标签，后续可关键词辅助 |
| 练习积累 | `checkins` | 训练卡完成次数、前后评分 |
| 画像变化 | `student_profiles` 或 `assessment_results` | 多轮测评趋势 |
| 下周建议 | 规则库 | 根据高频标签和画像推荐一个任务 |

验收标准：

- 周报不评价用户好坏；
- 周报至少展示一个趋势；
- 周报必须给出一个可执行建议；
- 用户没有打卡时，周报也能给温和提示。

### 14.6 后台导出与研究数据模块

当前问题：

- 当前已有 CSV 导出基础，但对学生画像、脱敏和数据字典支持不足；
- 自由文本、高风险文本、联系方式需要分级处理；
- 研究导出需要可追溯字段。

参考项目：

- Loop Habit Tracker：CSV/SQLite 导出；
- mindLAMP：数据门户；
- Nomie：统一记录和长期追踪。

导出类型建议：

| `type` | 含义 | 默认是否匿名 | 是否包含自由文本原文 |
|---|---|---|---|
| `diary` | 情绪记录 | 是 | 否 |
| `feedback` | 反馈结果 | 是 | 否 |
| `training` | 训练卡和打卡 | 是 | 不涉及 |
| `assessment` | 普通测评/工作表 | 是 | 否 |
| `profile` | 学生画像结果 | 是 | 否 |
| `weekly_report` | 周报摘要 | 是 | 否 |

导出策略：

- 默认导出 `anonymous_id`；
- 默认不导出 `user_id`、手机号、微信标识、联系方式；
- 默认不导出自由文本原文；
- 可导出文本摘要、标签、关键词；
- 高风险文本导出需要管理员确认；
- 后续所有导出写入 `audit_logs`。

验收标准：

- 后台导出 `profile` 类型可用；
- 导出文件包含数据字典；
- 敏感字段默认不出现；
- 导出操作有明确权限说明。

## 15. API 详细设计草案

本节用于后续更新 `docs/03_技术真相/API接口文档.md` 时参考。实现前需根据后端实际路由风格再确认命名。

### 15.1 `POST /api/profile`

用途：

- 根据学生测评分数、自由文本和规则库生成阶段性画像；
- 输出非诊断解释、推荐任务和风险处理结果。

请求体：

```json
{
  "user_id": "demo-student",
  "anonymous_id": "anon_20260601_001",
  "round": 1,
  "source": "miniprogram_assessment",
  "scores": {
    "test_anxiety": 3.8,
    "iu_score": 4.2,
    "fear_score": 2.9,
    "self_compassion": 3.1
  },
  "free_text": "最近总担心考不好，爸妈会失望...",
  "consent": {
    "profile_feedback": true,
    "research_export": false
  }
}
```

响应体：

```json
{
  "success": true,
  "data": {
    "id": "profile_001",
    "profile_name": "压力警觉型画像",
    "profile_code": "pressure_alert",
    "confidence": 0.76,
    "confidence_label": "中等偏高",
    "dimensions": [
      {
        "key": "anxiety_sensitivity",
        "label": "压力信号敏感度",
        "level": "high",
        "summary": "你可能更容易注意到压力和评价相关线索。"
      },
      {
        "key": "emotion_regulation",
        "label": "情绪调节资源",
        "level": "medium_low",
        "summary": "情绪强烈时，你可能还需要更多可操作的调节方法。"
      }
    ],
    "strength_note": "敏感也可能帮助你提前发现问题。",
    "suggested_task": "emotion_naming_01",
    "recommended_card_ids": ["emotion_naming_01", "cbt_auto_thought_01"],
    "risk_level": "low",
    "requires_review": false,
    "rules_version": "2026-06-01",
    "boundary_notice": "本结果不是临床诊断，仅用于自我理解和练习参考。"
  }
}
```

错误响应：

| 场景 | HTTP 状态 | 响应策略 |
|---|---|---|
| 缺少必要分数 | `400` | 返回字段错误，不生成画像 |
| 自由文本触发高风险 | `200` 或 `202` | 返回 `requires_review=true`，不返回普通建议 |
| 规则库不存在 | `500` | 返回系统错误，提示稍后重试 |
| 低置信度 | `200` | 返回维度说明，不显示强画像标签 |

## 16. 数据库和内容库详细方案

### 16.1 短期策略：复用现有表

短期为了降低风险，可以继续复用 `assessment_results` 保存画像测评结果。

优点：

- 不需要第一步改数据库；
- 可以快速打通小程序测评 -> 画像结果 -> 训练卡推荐；
- 适合 P0/P1 试做。

风险：

- 普通量表、工作表和画像结果混在一起；
- 后续查询和导出会变复杂；
- 画像复测和风险复核字段不够清晰。

适用阶段：

- P1 原型；
- 小样本试用；
- 还没有后台筛选和研究导出需求时。

### 16.2 中期策略：新增 `student_profiles`

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PRIMARY KEY | 画像结果 ID |
| `user_id` | TEXT | 用户 ID，内部使用 |
| `anonymous_id` | TEXT | 匿名 ID，导出使用 |
| `round` | INTEGER | 第几轮测评 |
| `source` | TEXT | 来源，如 `miniprogram_assessment` |
| `scores_json` | TEXT | 量表分数 |
| `text_features_json` | TEXT | 关键词、标签、资源线索 |
| `profile_code` | TEXT | 画像编码 |
| `profile_name` | TEXT | 展示名称 |
| `confidence` | REAL | 置信度 |
| `dimensions_json` | TEXT | 维度说明 |
| `recommended_task_ids_json` | TEXT | 推荐任务 |
| `risk_level` | TEXT | 风险等级 |
| `requires_review` | INTEGER | 是否需人工复核 |
| `boundary_notice` | TEXT | 非诊断声明 |
| `rules_version` | TEXT | 规则版本 |
| `export_allowed` | INTEGER | 是否允许导出 |
| `created_at` | TEXT | 创建时间 |
| `updated_at` | TEXT | 更新时间 |

### 16.3 长期策略：新增 `records`

`records` 不替代业务表，只做研究导出统一入口。

写入规则：

- 新增画像结果时，同步一条 `module_type=student_profile`；
- 新增家长情绪记录时，同步一条 `module_type=parent_log`；
- 新增沙盘任务时，同步一条 `module_type=sandplay_task`；
- 新增打卡时，同步一条 `module_type=checkin`；
- `data_json` 只写研究摘要，不写完整隐私原文。

`records.data_json` 示例：

```json
{
  "profile_code": "pressure_alert",
  "confidence": 0.76,
  "risk_level": "low",
  "dimension_levels": {
    "anxiety_sensitivity": "high",
    "emotion_regulation": "medium_low"
  },
  "recommended_task_count": 2,
  "export_note": "free_text_raw_excluded"
}
```

### 16.4 内容库版本管理

每个内容库文件建议包含：

- `version`；
- `updated_at`；
- `review_status`；
- `reviewer_role`；
- `items`；
- `change_note`。

示例：

```json
{
  "version": "2026-06-01",
  "updated_at": "2026-06-01",
  "review_status": "draft",
  "reviewer_role": "psychology_content_reviewer",
  "change_note": "学生画像规则初稿",
  "items": []
}
```

## 17. 页面级详细规格

### 17.1 小程序：学生画像结果页

页面目标：

- 让学生或家长理解“当前状态画像”；
- 给出一个可执行任务；
- 明确非诊断边界；
- 避免被评价感。

页面结构：

```text
顶部说明：
这是根据本次填写生成的阶段性支持画像，不是诊断。

画像卡：
压力警觉型画像
置信度：中等偏高

维度条：
压力信号敏感度：较高
情绪调节资源：发展中
自我支持：发展中

优势提示：
你对变化比较敏感，这有时能帮助你提前发现问题。

推荐任务：
3 分钟情绪命名
按钮：开始练习

边界说明：
如果你正在经历强烈危险，请联系现实中的可信成年人或当地紧急服务。
```

交互要求：

- 用户可以跳过推荐任务；
- 用户可以保存结果；
- 用户可以稍后再练习；
- 高风险时不展示普通画像卡，展示安全提示和人工支持入口；
- 结果页不显示复杂研究图表。

### 17.2 小程序：训练卡页

页面目标：

- 把画像建议转成短练习；
- 降低启动门槛；
- 练习完成后能进入打卡。

页面结构：

```text
训练卡标题
适合场景
预计时长
步骤 1
步骤 2
步骤 3
完成后感受评分
保存练习
```

文案要求：

- 使用“可以试试”；
- 不使用“必须完成”；
- 不使用“你做错了”；
- 不承诺“做完就会好”。

### 17.3 网页后台：画像列表页

页面目标：

- 给教师、督导或研究人员查看画像数据；
- 支持筛选和导出；
- 控制敏感信息。

筛选项：

- 时间范围；
- 画像类型；
- 风险等级；
- 是否需要复核；
- 规则版本；
- 是否允许导出。

表格字段：

- 匿名 ID；
- 画像名称；
- 置信度；
- 风险等级；
- 推荐任务；
- 是否需复核；
- 创建时间；
- 操作：查看详情。

默认不显示：

- 真实姓名；
- 联系方式；
- 自由文本原文；
- 家庭详细隐私。

### 17.4 网页后台：画像详情页

页面结构：

```text
基础信息：匿名 ID、提交时间、轮次、规则版本
画像结果：画像名称、置信度、风险等级
维度说明：压力敏感、情绪调节、自我支持
推荐任务：训练卡或沙盘任务
文本摘要：关键词、标签、压力源摘要
复核状态：无需复核/待复核/已复核
人工备注：仅后台可见
导出状态：是否允许导出
```

伦理要求：

- 自由文本原文默认折叠或不展示；
- 查看敏感文本应记录审计；
- 人工备注不自动同步到学生端；
- 任何诊断性措辞都不得出现在系统生成区域。

## 18. 心理内容审核流程

### 18.1 内容进入系统前的审核

每条画像规则、训练卡、风险关键词都要经过以下检查：

| 检查项 | 通过标准 |
|---|---|
| 非诊断 | 不使用疾病、障碍、人格定性 |
| 支持性 | 包含优势提示或正常化说明 |
| 可执行 | 至少有一个小任务 |
| 边界清楚 | 写明不是诊断或危机服务 |
| 风险处理 | 高风险场景转人工复核 |
| 版本明确 | 有 `version` 和 `review_status` |

### 18.2 禁用词和替代表达

| 禁用/慎用表达 | 推荐替代表达 |
|---|---|
| 人格 | 阶段性画像 / 当前状态画像 |
| 异常 | 近期反应较明显 |
| 障碍 | 困扰 / 压力反应 |
| 病态 | 需要更多支持 |
| 系统判断你 | 本次填写显示 / 可能提示 |
| 你必须 | 可以先尝试 |
| 治疗 | 支持 / 练习 / 咨询资源 |

### 18.3 高风险内容处理

高风险类别：

- 自伤/自杀；
- 伤害他人；
- 被侵害或严重安全威胁；
- 严重失眠或极端痛苦表达；
- 明确危机场景。

处理原则：

- 不生成普通训练建议；
- 不输出“你会没事的”这类空泛安慰；
- 不承诺平台能即时处理；
- 提示联系现实可信成年人、学校老师、专业机构或当地紧急服务；
- 后台标记 `requires_review=true`。

## 19. 用户研究与试用方案

### 19.1 小样本试用目标

试用目标不是证明系统有效治疗，而是验证：

- 用户是否愿意填写；
- 用户是否能理解画像不是诊断；
- 用户是否知道下一步做什么；
- 推荐任务是否能启动；
- 打卡和周报是否造成压力；
- 后台导出字段是否够用。

### 19.2 试用对象

建议第一轮：

- 3-5 名学生或模拟学生；
- 3-5 名家长；
- 1-2 名教师/督导；
- 1 名心理学内容审核者；
- 1 名开发人员观察记录。

### 19.3 试用任务

| 角色 | 任务 | 观察点 |
|---|---|---|
| 学生 | 完成一次支持性画像测评 | 是否卡在题目、是否担心隐私 |
| 学生 | 阅读画像报告 | 是否误解为诊断、是否感到被贴标签 |
| 学生 | 完成一个推荐训练卡 | 是否知道怎么做、是否觉得太长 |
| 家长 | 完成一次情绪记录 | 表单是否过长、反馈是否温和 |
| 家长 | 查看周报 | 是否能理解趋势、是否增加压力 |
| 督导 | 查看后台画像列表 | 筛选是否够用、信息是否过度暴露 |
| 研究人员 | 导出 profile 数据 | 字段是否清楚、是否默认脱敏 |

### 19.4 访谈问题

学生：

- 你觉得这个结果是在帮助你理解自己，还是在评价你？
- 哪一句话让你觉得舒服或不舒服？
- 你能说出下一步可以做什么吗？
- 你是否担心别人看到你的填写内容？

家长：

- 这个反馈是否让你更理解孩子？
- 有没有哪句话让你感到被指责？
- 训练卡是否容易开始？
- 周报是否让你感到压力？

教师/督导：

- 后台信息是否足够支持后续跟进？
- 哪些字段不应该默认展示？
- 哪些情况需要人工复核？
- 导出数据是否满足研究分析需要？

### 19.5 试用指标

| 指标 | 目标 |
|---|---|
| 测评完成率 | 第一轮大于 70% |
| 报告误解率 | 明显误解为诊断的比例低于 10% |
| 推荐任务启动率 | 大于 50% |
| 打卡压力感 | 访谈中不出现普遍“被惩罚”感 |
| 后台筛选成功率 | 督导能在 2 分钟内找到需复核个案 |
| 导出脱敏通过率 | 默认导出不含联系方式和自由文本原文 |

## 23. 最高标准执行版

本节用于回答“这是否是一个可以直接执行的方案”。结论是：可以执行，但必须按阶段执行，不允许跳过 P0 直接写 API 或页面。

执行优先级：

```text
先内容和边界
-> 再画像 API
-> 再用户端报告页
-> 再后台列表和导出
-> 再周报趋势
-> 最后研究平台化
```

### 23.1 执行总原则

后续任何开发都必须遵守：

1. 不先实现页面，必须先有内容规则和边界声明；
2. 不先做复杂模型，先用可解释规则引擎；
3. 不把画像称为人格；
4. 不把自由文本直接交给自动反馈；
5. 不默认导出自由文本原文；
6. 不让小程序端承载研究后台复杂图表；
7. 不把高风险用户引导到普通训练卡；
8. 不让周报变成评分或排名系统；
9. 不复制第三方 GitHub 项目源码；
10. 不在未同步文档的情况下合并实现。

### 23.2 阶段准入与退出标准

| 阶段 | 准入条件 | 退出标准 | 是否我可以直接执行 |
|---|---|---|---|
| P0 内容与边界 | 当前文档已完成 | 内容库初稿、伦理清单、量表方案已同步 | 可以 |
| P1 画像 API | P0 文件存在且通过文案检查 | `POST /api/profile` 可用，高风险可拦截 | 可以，但先读后端代码 |
| P2 小程序报告页 | P1 API 可本地返回结果 | 用户能测评 -> 看画像 -> 进训练卡 | 可以，但先读小程序页面结构 |
| P2 后台导出 | P1 数据可保存 | 后台可筛选和导出匿名数据 | 可以，但先读 web/API client |
| P3 周报督导 | P2 数据稳定 | 周报有趋势，后台有复核入口 | 可以，但需先确认真实数据结构 |
| P4 研究平台化 | P1-P3 已试用 | `records`、审计、数据字典稳定 | 可以，但不建议提前做 |

### 23.4 P1 最高标准任务包

P1 的目标是最小画像 API，不追求复杂模型。

必须新增或修改：

| 文件/模块 | 操作 | 目标 |
|---|---|---|
| `backend/routes/profile.py` | 新增 | 画像 API 路由 |
| `backend/services/profile_service.py` | 新增 | 画像规则匹配和结果生成 |
| `backend/services/risk_service.py` | 新增 | 高风险关键词检查 |
| `backend/services/content_loader.py` 或现有内容加载工具 | 新增/复用 | 读取 JSON 规则 |
| `backend/app.py` 或路由注册文件 | 修改 | 注册 profile route |
| `shared/types/api.ts` | 修改 | 增加画像响应类型 |
| `docs/03_技术真相/API接口文档.md` | 修改 | 写入真实接口 |
| `docs/03_技术真相/数据库字段说明.md` | 修改 | 说明短期保存策略 |

P1 最小服务逻辑：

```text
读取请求体
-> 校验 scores
-> risk_service 检查 free_text
-> 如果 high risk：返回 requires_review=true，不生成普通建议
-> profile_service 根据分数生成 profile_code 和 confidence
-> 从 student_profile_rules.json 匹配反馈内容
-> 返回画像、维度、推荐任务、边界声明
-> 保存结果
```

P1 保存策略：

P1 必须测试：
