# 四种上线方案实施教程

更新时间：2026-08-23

本文档根据当前项目代码整理四种上线方式：云服务器加域名、微信云托管、Caddy 加 Cloudflare Tunnel、GPT 站点或 ChatGPT App。每套教程包含准备、配置、验证和回滚。正式执行前，重新核对对应平台的官方要求。

当前事实统一以 `docs/00_当前事实基准/项目进度统一口径.md` 和 `docs/00_当前事实基准/当前进度交接.md` 为准。本教程不表示项目已经完成公网部署、备案或正式发布。

## 1. 选型前检查

### 1.1 当前代码部署基线

- 根目录已有生产 `Dockerfile`，使用 `gunicorn -c gunicorn.conf.py wsgi:app` 启动 Flask
- 后端默认监听 `0.0.0.0:5050`，健康检查为 `/healthz`，就绪检查为 `/readyz`
- 生产环境必须显式使用 MySQL；当前代码禁止 production SQLite，也不支持直接切换 PostgreSQL
- 除至少 32 字符的 `SECRET_KEY` 和非默认 `ADMIN_EXPORT_TOKEN` 外，生产启动还要求数据库批准摘要、MySQL TLS CA 和 `OPERATIONS_HEALTH_TOKEN`
- Web 使用 React/Vite，构建产物为 `apps/web/dist`
- Web 生产 API 变量为 `VITE_SAFEHOME_API_BASE_URL`；同域部署时设置为空字符串
- 小程序已使用 `wx.cloud.callContainer`，环境为 `prod-d3gl35otiaa7c8d24`，服务为 `flask-gh3l`
- 仓库已有受控外部访问脚本和 Cloudflare Tunnel 配置模板

### 1.2 共用上线门槛

四种方案都不能绕过以下要求：

1. 完成目标环境的 `/healthz`、`/readyz` 和核心链路验证
2. 备份数据库，并实际完成一次恢复演练
3. 为后台启用登录、角色权限、导出控制和审计
4. 只收集实现功能所需的数据，并明确保存期限和删除方式
5. 未成年人数据、心理文本、画像和风险记录不得出现在公开页面或演示数据中
6. 高风险内容只进入人工处理流程，不生成普通自动训练建议
7. 生产 Secret 只能存放在服务器或云平台环境变量中
8. 没有备案、隐私政策、负责人或回滚方案时，不发布正式公网版本

当前 `production_gate_eligible=false`，且真实 MySQL 迁移、恢复演练、供应链和外部负责人证据尚未齐全。因此本教程当前只允许准备候选包、零流量构建和只读核对；不得切入生产流量或把项目写成“已正式上线”。

## 2. 选择方案

| 方案 | 适用场景 | 电脑是否持续开机 | 当前建议 |
|---|---|---:|---|
| 云服务器 + 域名 | 稳定 Web、后台和多端统一入口 | 否 | 中长期正式路线 |
| 微信云托管 | 小程序主链路和微信生态试点 | 否 | 当前优先 |
| Caddy + Cloudflare Tunnel | 临时演示、受邀研究协作 | 是 | 仅使用合成或脱敏数据 |
| GPT 站点或 ChatGPT App | 公开介绍、已审核知识或外围工具 | 取决于后端 | 不替代现有 Flask 和数据库 |

执行顺序建议：

1. 小程序试点先使用微信云托管
2. 临时远程查看后台时使用受控 Tunnel
3. 需要稳定 Web 和多端访问时部署云服务器
4. GPT 站点只做公开介绍或窄范围只读工具

## 3. 云服务器加域名

本教程以“Ubuntu 服务器 + 当前 Dockerfile + Caddy + 单域名同源部署”为例。Caddy 自动申请和续签 HTTPS，`/api/*`、健康检查转发给 Flask，其余路径提供 Web 静态页面。

### 3.1 第 0 步：确认适用边界

适用：

- 需要稳定运行，不希望依赖办公室电脑开机；
- Web 后台和 API 需要固定地址；
- 已有明确管理员、备份负责人和外部试用范围。

暂不执行：

- 没有管理后台访问控制；
- 计划直接公开真实未成年人心理文本；
- 尚未确定主体、隐私政策、备案和数据保存责任人。

### 3.2 第 1 步：购买服务器和域名

1. 选择中国大陆服务器时，先确认云资源是否满足备案条件，再购买域名并做实名认证。
2. 备案主体应与域名实名认证信息保持一致。中国大陆服务器对外提供网站或 APP 服务前，应按当前接入商和主管部门要求完成 ICP 备案；是否还需公安联网备案、APP/小程序备案，以实施当日平台要求为准。
3. 测试期建议 2 核 4 GB、Ubuntu LTS、40 GB 以上系统盘；真实数据试点优先使用同地域托管 MySQL。
4. 云安全组只开放：

```text
22/tcp    SSH，只允许负责人固定 IP 时更好
80/tcp    Caddy 申请证书和 HTTP 跳转
443/tcp   HTTPS
```

不要开放 `5050`、`5173`、MySQL `3306` 到公网。

### 3.3 第 2 步：配置 DNS

假设使用一个域名：

```text
safehome.example.com
```

在域名 DNS 控制台添加：

```text
记录类型：A
主机记录：safehome
记录值：云服务器公网 IPv4
```

等待解析生效后，在本机检查：

```powershell
Resolve-DnsName safehome.example.com
```

返回的 IP 必须是刚购买的服务器公网 IP，才能继续配置自动 HTTPS。

### 3.4 第 3 步：初始化 Ubuntu

使用云厂商控制台给出的 SSH 用户登录。以下命令在服务器上执行：

```bash
sudo apt update
sudo apt upgrade -y
sudo apt install -y git curl ca-certificates gnupg
sudo timedatectl set-timezone Asia/Shanghai
```

Docker 应按 [Docker 官方 Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/) 安装并验证：

```bash
sudo systemctl enable --now docker
sudo docker run --rm hello-world
```

不要使用来源不明的“一键部署脚本”，也不要把 GitHub 个人访问令牌直接写进命令历史。

### 3.5 第 4 步：取得代码

公开仓库可执行：

```bash
sudo mkdir -p /srv/safehome
sudo chown "$USER":"$USER" /srv/safehome
git clone https://github.com/nayunzhishui/safehome1.0.git /srv/safehome
cd /srv/safehome
git status --short
```

如果仓库以后转为私有仓库，应使用只读 Deploy Key；不要把账号密码或 token 保存到仓库文件。

### 3.6 第 5 步：生成生产环境配置

先生成两个不同的随机值：

```bash
openssl rand -hex 32
openssl rand -hex 32
```

第一个用于 `SECRET_KEY`，第二个用于 `ADMIN_EXPORT_TOKEN`。在服务器创建仅管理员可读的 `/etc/safehome/backend.env`：

```bash
sudo install -d -m 700 /etc/safehome
sudoedit /etc/safehome/backend.env
```

当前生产镜像只允许 MySQL。生产环境示例：

```dotenv
APP_ENV=production
PORT=5050
DB_PROVIDER=mysql
MYSQL_HOST=<已批准的数据库主机名>
MYSQL_PORT=3306
MYSQL_USER=<最小权限业务账号>
MYSQL_PASSWORD=<数据库密码>
MYSQL_DATABASE=<数据库名>
MYSQL_SSL_CA=<镜像内已审核的 CA PEM 路径>
MYSQL_SSL_VERIFY_IDENTITY=1
MYSQL_TLS_MIN_VERSION=TLSv1.2
DATABASE_DATA_WATERMARK=participant_production
DB_PROFILE_APPROVAL_ID=<批准记录编号>
DB_APPROVED_HOST_SHA256=<规范化 MYSQL_HOST 的 SHA-256>
DB_APPROVED_DATABASE=<与 MYSQL_DATABASE 完全一致>
DB_APPROVED_PORT=3306
DB_APPROVED_MIGRATION_HEAD=2026_08_24_063+2026_08_25_076
CONTENT_DIR=/app/content
SECRET_KEY=<至少32字符的随机值>
ADMIN_EXPORT_TOKEN=<另一组高强度随机值>
OPERATIONS_HEALTH_TOKEN=<独立的高强度运维令牌>
ALLOWED_ORIGINS=https://safehome.example.com
TRUST_CLOUDBASE_IDENTITY_HEADERS=0
LOG_LEVEL=INFO
PRODUCTION_FEATURES_UNLOCKED=0
AI_QA_ENABLED=0
AI_QA_REAL_PROVIDER_ENABLED=0
RESEARCH_OPERATIONS_WRITE_ENABLED=0
```

保存后执行：

```bash
sudo chmod 600 /etc/safehome/backend.env
```

MySQL 安全组只允许该服务器或同一私有网络访问。TLS 必须先在数据库侧开启并下载对应 CA；迁移前按 `docs/04_部署联调/数据库备份与恢复说明.md` 完成备份和恢复演练。未经批准不得自行填写批准摘要或执行真实迁移。

### 3.7 第 6 步：构建后端镜像并本机验收

在项目根目录执行：

```bash
cd /srv/safehome
sudo docker build -t safehome-backend:20260823 .
sudo docker volume create safehome-data
sudo docker run -d \
  --name safehome-backend \
  --restart unless-stopped \
  --env-file /etc/safehome/backend.env \
  -p 127.0.0.1:5050:5050 \
  -v safehome-data:/app/data \
  safehome-backend:20260823
```

检查容器和健康状态：

```bash
sudo docker ps --filter name=safehome-backend
sudo docker logs --tail 100 safehome-backend
curl -fsS http://127.0.0.1:5050/healthz
curl -fsS http://127.0.0.1:5050/readyz
```

`/healthz` 和 `/readyz` 都成功后才能继续。若 `/readyz` 返回 503，应先读取响应中的数据库、内容库和部署一致性信息，不要先改反向代理。

### 3.8 第 7 步：构建 Web

服务器需安装符合当前 Vite 要求的 Node.js 22。进入 Web 目录并创建只在服务器使用的 `apps/web/.env.production.local`：

```dotenv
VITE_SAFEHOME_API_BASE_URL=
VITE_SAFEHOME_CLIENT_VERSION=web-20260823
```

然后执行：

```bash
cd /srv/safehome/apps/web
npm ci
npm run typecheck
npm run build
test -f dist/index.html
sudo chmod -R a+rX /srv/safehome/apps/web/dist
```

API 地址留空表示浏览器使用同域 `/api`。不要把 `ADMIN_EXPORT_TOKEN`、数据库密码或 OpenAI key 写成 `VITE_*`，因为 Vite 会把这些值打包进浏览器文件。

### 3.9 第 8 步：安装和配置 Caddy

按 [Caddy 官方安装页](https://caddyserver.com/docs/install#debian-ubuntu-raspbian)安装稳定版。官方 Debian/Ubuntu 命令为：

```bash
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy
```

编辑 `/etc/caddy/Caddyfile`：

```caddyfile
safehome.example.com {
    encode zstd gzip

    @backend path /api/* /healthz /healthz/* /readyz
    handle @backend {
        reverse_proxy 127.0.0.1:5050
    }

    handle {
        root * /srv/safehome/apps/web/dist
        try_files {path} /index.html
        file_server
    }
}
```

验证并加载：

```bash
sudo caddy fmt --overwrite /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
sudo systemctl status caddy --no-pager
```

Caddy 会在 DNS 正确且 80/443 可达时自动申请和续签证书。

### 3.10 第 9 步：公网验收

```bash
curl -fsS https://safehome.example.com/healthz
curl -fsS https://safehome.example.com/readyz
curl -I https://safehome.example.com/
```

浏览器至少检查：

1. 首页可打开，地址栏证书正常；
2. 深层路由刷新不会 404；
3. 登录、退出和权限边界正常；
4. 浏览器控制台没有 CORS、混合内容或 `127.0.0.1` 请求；
5. 未登录用户不能看到研究者后台数据；
6. 导出、角色和敏感操作仍由服务端鉴权和审计。

### 3.11 第 10 步：备份、更新和回滚

SQLite 每次更新前至少备份 Docker volume 中的数据库，并执行恢复演练；MySQL 使用云数据库备份和独立 dump。不要只验证“备份文件存在”。

更新前：

```bash
cd /srv/safehome
git status --short
git pull --ff-only
sudo docker build -t safehome-backend:<新版本号> .
```

SQLite 只能安排短暂停机切换，不能让新旧容器同时写同一个数据库。MySQL 可以让新容器先绑定 `127.0.0.1:5051` 完成健康检查，再修改 Caddy upstream 并 reload。回滚时恢复旧镜像、旧 Caddy upstream；若迁移改变了数据库，必须按对应迁移回滚方案处理，不能只回滚容器。

## 4. 微信云托管

本方案与当前小程序代码最一致。它不需要自管 Linux 服务器；小程序通过 `wx.cloud.callContainer` 访问容器服务。当前配置已经登记云环境和服务，但“配置存在”不等于“本轮代码已发布”。

### 4.1 第 0 步：决定入口模式

二选一：

1. 小程序私有链路专用：关闭服务公网入口，可在重新完成身份头负向验证后评估是否信任 CloudBase 注入身份。
2. 小程序 + Web 共用服务：保留公网 HTTPS，必须保持 `TRUST_CLOUDBASE_IDENTITY_HEADERS=0`，微信登录使用服务端 `jscode2session` 或已验证的专门路径。

当前项目属于第 2 类，不应只因 `callContainer` 可用就把信任开关改成 `1`。

### 4.2 第 1 步：准备云环境

1. 使用项目小程序 AppID 登录微信云托管/CloudBase 控制台。
2. 核对环境 ID：`prod-d3gl35otiaa7c8d24`。
3. 核对服务名：`flask-gh3l`。
4. 确认服务具备标准输出日志、版本管理和回滚能力。
5. 生产数据使用 CloudBase MySQL 或同地域 MySQL；不要依赖容器本地 SQLite，因为容器扩缩容和重建后本地文件不应被视为持久数据库。

### 4.3 第 2 步：准备发布代码

云托管上传的构建目录必须是项目根目录，因为根 `Dockerfile` 需要同时复制：

```text
backend/
content/
shared/
config/rc0810/database_profiles.json
deploy/verify_rc0810_f03_images.py
```

不要只上传 `backend` 目录。上传前检查：

```powershell
git status --short
docker build -t safehome-cloudbase-check .
```

如果本地没有 Docker，可以由云托管从代码构建，但构建失败时仍应先检查 Dockerfile 的 COPY 路径和 `.dockerignore`。

### 4.4 第 3 步：新建云托管版本

控制台操作：

1. 进入“云托管 -> `flask-gh3l` -> 新建版本”。
2. 上传方式选择“代码包/代码库拉取”。
3. 构建目录选择项目根目录。
4. Dockerfile 填 `Dockerfile`。
5. 监听端口填 `5050`。
6. 日志采集路径留空，使用标准输出。
7. 第一轮先不给新版本 100% 流量。

### 4.5 第 4 步：配置环境变量

最小生产变量：

```dotenv
APP_ENV=production
PORT=5050
DB_PROVIDER=mysql
MYSQL_HOST=<CloudBase MySQL 内网地址>
MYSQL_PORT=3306
MYSQL_USER=<业务账号>
MYSQL_PASSWORD=<密码>
MYSQL_DATABASE=<数据库名>
MYSQL_SSL_CA=<镜像内已审核的 CA PEM 路径>
MYSQL_SSL_VERIFY_IDENTITY=1
MYSQL_TLS_MIN_VERSION=TLSv1.2
DATABASE_DATA_WATERMARK=participant_production
DB_PROFILE_APPROVAL_ID=<批准记录编号>
DB_APPROVED_HOST_SHA256=<规范化 MYSQL_HOST 的 SHA-256>
DB_APPROVED_DATABASE=<与 MYSQL_DATABASE 完全一致>
DB_APPROVED_PORT=3306
DB_APPROVED_MIGRATION_HEAD=2026_08_24_063+2026_08_25_076
CONTENT_DIR=/app/content
SECRET_KEY=<至少32字符随机值>
ADMIN_EXPORT_TOKEN=<高强度随机值>
OPERATIONS_HEALTH_TOKEN=<独立的高强度运维令牌>
ALLOWED_ORIGINS=https://<批准的Web域名>
TRUST_CLOUDBASE_IDENTITY_HEADERS=0
LOG_LEVEL=INFO
PRODUCTION_FEATURES_UNLOCKED=0
AI_QA_ENABLED=0
AI_QA_REAL_PROVIDER_ENABLED=0
RESEARCH_OPERATIONS_WRITE_ENABLED=0
```

微信登录、手机号和订阅消息若启用，再按 `docs/04_部署联调/小程序云托管调试说明.md` 添加对应变量。密钥只放云托管环境变量，不写入 `cloudConfig.js`、截图或 Git。

### 4.6 第 5 步：无流量/灰度验收

新版本构建完成后先检查：

1. 容器日志没有配置校验错误；
2. `/healthz` 返回 200；
3. `/readyz` 返回 200；
4. `/healthz/deep` 中数据库、内容库和部署一致性均正常；
5. 数据库迁移完成且旧数据仍可读取。

然后按 5% -> 20% -> 100% 逐步切流。每一步都观察错误率、延迟、登录和关键链路，不要构建成功后立即全量。

### 4.7 第 6 步：核对小程序调用

当前代码已经执行：

```javascript
wx.cloud.init({ env: "prod-d3gl35otiaa7c8d24" })
```

请求时服务名必须保持：

```text
X-WX-SERVICE: flask-gh3l
```

在微信开发者工具打开 `pages/debug/index`，依次测试：

```text
healthz -> readyz -> assessments -> risk/check -> profile
```

随后在真机体验版回测：登录、测评、画像、训练卡、打卡、周报、消息和退出。

### 4.8 第 7 步：身份与公网负向验证

只要服务公网域名仍开启，就从公网域名发送伪造 `X-WX-OPENID`、`X-WX-APPID` 等请求头。预期必须是缺少真实凭证或未授权，绝不能创建用户或返回登录 token。

如果伪造请求可以登录：

1. 立即停止验收；
2. 保持 `TRUST_CLOUDBASE_IDENTITY_HEADERS=0`；
3. 将流量切回旧版本；
4. 检查审计日志和已创建账号；
5. 修复后重新做负向验证。

### 4.9 第 8 步：Web 公网与自定义域名

- 只有小程序通过 `callContainer` 使用时，可以关闭公网入口，私有链路不受影响。
- Web 后台调用同一服务时，需要公网 HTTPS 或同环境的受控代理。
- 云托管本身就是后端服务器；只需要 API 时无需另购 VPS。可规划 `api.wefamily.chat -> flask-gh3l`，小程序继续使用 `callContainer`。
- 按 CloudBase 当前官方规则，自定义域名需先完成 ICP 备案并准备 SSL 证书；首次接入还要添加 TXT 做归属校验，平台生成 CNAME 后再到 DNS 控制台解析。
- 默认 `sh.run.tcloudbase.com` 地址只用于技术联调。需要完整 Web 前台时，可由 VPS 或静态托管承载 `www.wefamily.chat`，API 仍指向云托管。

### 4.10 第 9 步：回滚

1. 在版本流量配置中把流量切回上一稳定版本；
2. 不立即删除失败版本，先保留日志和 request_id；
3. 数据库迁移若不可向后兼容，执行已审核的数据库回滚或恢复；
4. 小程序若同时改了环境或服务名，恢复 `cloudConfig.js` 对应配置并重新上传体验版；
5. 完成一次完整核心链路回测。

## 5. Windows 本机 Caddy 加 Cloudflare Tunnel

Cloudflare Tunnel 通过本机向 Cloudflare 发起出站连接，不要求家庭/办公室拥有公网 IP，也不需要在路由器开放 80/443。Caddy 只在本机 loopback 提供同源静态站和 API 代理。

本方案只用于受控演示和受邀研究协作。电脑关机、休眠、断网或进程退出，站点会立即不可用。

### 5.1 第 0 步：选择项目内置代理或 Caddy

项目已提供 `scripts/researcher_access_proxy.py`。如果按现有门禁脚本运行，就不需要 Caddy。用户明确需要 Caddy 时，才采用本节配置。

二者都默认使用 `127.0.0.1:8787`，不能同时启动。正式外部访问仍应遵守 `docs/04_部署运维/Web研究者后台受控外部访问与内网穿透实施计划_20260722.md`。

### 5.2 第 1 步：准备域名和 Cloudflare

1. 注册一个正式域名。
2. 在 Cloudflare 添加该域名，并把域名注册商的 nameserver 改为 Cloudflare 给出的值。
3. 等待 Cloudflare 显示域名为 Active。
4. 规划专用子域名，例如：

```text
research.safehome.example.com
```

不要使用主站同一个 hostname 做临时演示，避免误伤正式 DNS 和 Cookie。

### 5.3 第 2 步：构建 Web 同源版本

在 `apps/web/.env.production.local` 写入：

```dotenv
VITE_SAFEHOME_API_BASE_URL=
VITE_SAFEHOME_CLIENT_VERSION=web-tunnel-20260823
```

执行：

```powershell
Set-Location D:\codex\workspace\safehome1.0\apps\web
npm ci
npm run typecheck
npm run build
Test-Path .\dist\index.html
```

最后一条必须返回 `True`。

### 5.4 第 3 步：启动 Flask，且只暴露给本机

推荐用根 `Dockerfile`，端口只绑定 loopback。把生产/演示环境变量放在仓库外，例如 `C:\safehome-secrets\backend.env`：

```powershell
Set-Location D:\codex\workspace\safehome1.0
docker build -t safehome-backend:tunnel .
docker volume create safehome-tunnel-data
docker run -d --name safehome-backend-tunnel --restart unless-stopped `
  --env-file C:\safehome-secrets\backend.env `
  -p 127.0.0.1:5050:5050 `
  -v safehome-tunnel-data:/app/data `
  safehome-backend:tunnel
curl.exe -f http://127.0.0.1:5050/healthz
curl.exe -f http://127.0.0.1:5050/readyz
```

演示环境必须使用合成或完全脱敏数据，关闭导出、账号管理、规则发布、生产开关和真实 AI 供应商。

### 5.5 第 4 步：安装 Caddy 和 cloudflared

从官方渠道安装：

- [Caddy 安装说明](https://caddyserver.com/docs/install)
- [cloudflared 下载与安装](https://developers.cloudflare.com/tunnel/downloads/)

安装后检查：

```powershell
caddy version
cloudflared --version
```

不要下载第三方网盘里的可执行文件。

### 5.6 第 5 步：创建本地 Caddyfile

在仓库外创建 `C:\safehome-deploy\Caddyfile`：

```caddyfile
{
    auto_https off
}

http://127.0.0.1:8787 {
    encode zstd gzip

    @backend path /api/* /healthz /healthz/* /readyz
    handle @backend {
        reverse_proxy 127.0.0.1:5050
    }

    handle {
        root * D:/codex/workspace/safehome1.0/apps/web/dist
        try_files {path} /index.html
        file_server
    }
}
```

这里关闭本地自动 HTTPS，是因为公网 TLS 由 Cloudflare 终止，Cloudflare 到本机通过 Tunnel 访问 loopback HTTP；本机没有开放公网入站端口。

验证和启动：

```powershell
caddy fmt --overwrite C:\safehome-deploy\Caddyfile
caddy validate --config C:\safehome-deploy\Caddyfile
caddy run --config C:\safehome-deploy\Caddyfile
```

另开一个 PowerShell 检查：

```powershell
curl.exe -f http://127.0.0.1:8787/healthz
curl.exe -I http://127.0.0.1:8787/
```

### 5.7 第 6 步：创建命名 Tunnel

项目当前模板采用 locally-managed named tunnel，因此以下步骤与现有 `config/cloudflared.safehome.example.yml` 一致。Cloudflare 对普通新项目更推荐 Dashboard 管理的 remotely-managed tunnel；如果要继续复用项目的人工门禁脚本，则保持本地管理模式。

```powershell
cloudflared tunnel login
cloudflared tunnel create safehome-research-web
cloudflared tunnel list
```

记下 Tunnel UUID。`cloudflared tunnel login` 会在用户目录生成账号证书，`tunnel create` 会生成 Tunnel 凭据 JSON；两者都不得加入 Git、截图或聊天记录。

在 `%USERPROFILE%\.cloudflared\config.yml` 写入：

```yaml
tunnel: <TUNNEL_UUID>
credentials-file: C:\Users\<你的Windows用户名>\.cloudflared\<TUNNEL_UUID>.json
ingress:
  - hostname: research.safehome.example.com
    service: http://127.0.0.1:8787
  - service: http_status:404
```

创建 DNS 路由并验证规则：

```powershell
cloudflared tunnel route dns safehome-research-web research.safehome.example.com
cloudflared tunnel ingress validate
cloudflared tunnel ingress rule https://research.safehome.example.com/healthz
```

启动 Tunnel：

```powershell
cloudflared tunnel run safehome-research-web
```

### 5.8 第 7 步：先配置 Cloudflare Access，再邀请用户

在 Cloudflare Zero Trust 控制台：

1. 进入 `Access controls -> Applications`；
2. 创建 `Self-hosted and private` 应用；
3. Hostname 选择 `research.safehome.example.com`；
4. 新建 `Allow` 策略，只允许负责人批准的具体邮箱或身份组；
5. 会话时间建议 30 分钟；
6. 不创建 `Bypass Everyone`；
7. 保存后用未邀请邮箱验证默认拒绝；
8. 通过 Access 后，仍必须再登录 SafeHome 应用账号。

Cloudflare Access 默认拒绝没有匹配 Allow 策略的用户，但仍要实际做未授权负向测试，不能只看控制台配置。

### 5.9 第 8 步：外部验收

至少验证：

1. 未邀请用户不能到达 SafeHome 登录页；
2. 邀请用户未登录 SafeHome 时不能读取后台数据；
3. 普通角色不能执行研究者、导出、角色和生产操作；
4. 深层路由刷新可恢复；
5. 浏览器没有 `127.0.0.1`、CORS 和混合内容错误；
6. Tunnel 停止后外部域名不可达；
7. 日志不记录 token、Cookie、手机号或参与者原文。

### 5.10 第 9 步：停止和回滚

手工运行时，在 Tunnel 和 Caddy 窗口按 `Ctrl+C`，然后停止后端容器：

```powershell
docker stop safehome-backend-tunnel
```

如果 `cloudflared` 已安装为 Windows 服务：

```powershell
Stop-Service cloudflared
```

演示结束还应撤销 Access 邀请、临时账号和临时 CORS 域名。不要删除业务数据库作为回滚手段。

## 6. GPT 站点、ChatGPT Sites 与 ChatGPT App

“GPT 站点”常被用来指三件不同的事，必须先区分：

| 名称 | 实际能力 | 能否替代 Flask/数据库 |
|---|---|---:|
| ChatGPT Sites 生成并托管网页 | 适合公开说明页、原型、内部轻应用 | 否，动态 API 仍需方案 1/2/3 |
| ChatGPT Plugin/App（MCP） | 在 ChatGPT 内调用你提供的工具和可选组件 | 否，需要独立 HTTPS MCP 服务和现有 API |
| 自建 GPT API 网站 | 自己开发聊天页面并调用 OpenAI API | 否，本质仍需服务器/云托管和服务端密钥管理 |

本项目不应把“GPT 站点”作为跳过身份、数据库、备案、隐私和危机边界的捷径。

### 6.1 路线 A：用 ChatGPT Sites 做公开介绍站

适合展示：项目介绍、使用边界、试点招募说明、公开训练理念和联系入口。

不适合展示：研究者后台、用户画像、风险记录、自由文本原文、导出、账号管理。

步骤：

1. 准备一份已脱敏的公开素材，只包含 `README.md`、产品介绍、隐私/非诊断边界和公开图片。
2. 不上传 `.env`、数据库、日志、CloudBase 凭据、真实 AppSecret、管理员 token 和参与者文本。
3. 在 ChatGPT Work 中启用 Sites，创建一个新的公开说明站。
4. 给出明确页面范围：`首页`、`项目如何使用`、`非诊断与危机边界`、`隐私说明`、`联系与试点申请`。
5. 要求不生成登录、测评、风险评估或管理后台的假功能。
6. 先发布预览地址，逐页检查移动端、链接、隐私文字和无障碍。
7. 需要正式域名时，再按 Sites 当前托管能力绑定；账号可用性、套餐、域名支持以实施当日界面为准。
8. 如需读取真实 SafeHome 数据，不在 Sites 中直接塞密钥；改为由方案 1/2 提供受控 API，并重新做权限和隐私设计。

可复制给 ChatGPT Sites 的需求摘要：

```text
基于提供的公开、已脱敏资料创建“安心陪伴”项目说明站。只做公开信息展示，不创建登录、测评、画像、聊天、风险判断、导出或管理后台。页面包含：首页、如何使用、非诊断与危机边界、隐私说明、联系与试点申请。使用支持性、非评判措辞；明确系统不能替代诊断、治疗或危机干预。先返回预览，不直接发布正式域名。
```

### 6.2 路线 B：把 SafeHome 做成 ChatGPT Plugin/App

当前官方路线是 MCP 服务 + 可选 Web 组件。ChatGPT 负责判断何时调用工具；MCP 服务负责执行、鉴权和返回结构化数据。现有 Flask REST API 不能直接当 MCP 地址使用，需要新增一个窄适配层。

第一版只建议三个只读工具：

| 工具 | 输入 | 输出 | 数据边界 |
|---|---|---|---|
| `list_training_cards` | 主题、受众 | 已审核训练卡摘要 | 只读公开内容库 |
| `get_training_card` | 训练卡 ID | 一张训练卡详情 | 不返回用户记录 |
| `get_service_boundary` | 无 | 非诊断、隐私、危机边界 | 固定已审核文本 |

第一版禁止：

- 上传或分析真实未成年人心理文本；
- 通过 ChatGPT 读取研究者后台、画像、风险记录或导出；
- 提供诊断、危机判断或自动训练处方；
- 暴露管理员 token、数据库或内部审计接口。

逐步实施：

1. 从 [OpenAI Apps SDK 官方示例](https://github.com/openai/openai-apps-sdk-examples) 选择最小 Node 或 Python MCP 示例，不在现有 Flask 路由上直接猜协议。
2. 新建独立 MCP 适配服务，工具只读取经过版本治理的 `content/training_cards.json` 和边界文本。
3. 为每个工具定义严格输入/输出 schema，并标记只读；未知训练卡 ID 返回明确错误，不让模型猜测。
4. 本地启动 MCP，例如 `http://127.0.0.1:8000/mcp`，先用 MCP Inspector 验证列出工具和调用结果。
5. 开发阶段用命名 Tunnel 暴露为 `https://gpt.safehome.example.com/mcp`；真实数据仍禁止进入。
6. 在 ChatGPT 中打开 `Settings -> Security and login -> Developer mode`。
7. 进入 Plugins，点击加号，填写公网 HTTPS MCP URL。
8. 安装个人 Plugin，在 Work 对话中用 `@` 选择它，测试正常、无效和“不应调用工具”的请求。
9. 增加身份数据前必须实现用户级 OAuth、最小权限、审计、删除和隐私政策；不能共用一个管理员 token。
10. 对外发布前按 OpenAI 当前提交指引检查工具描述、认证、隐私、安全、稳定性和公开域名。

回滚很简单：先在 ChatGPT 停用 Plugin，再停止 MCP Tunnel/服务；这不会回滚或删除现有 SafeHome 数据。

### 6.3 路线 C：自建 GPT API 网站

如果目标是自己的聊天网页，而不是 ChatGPT 内 Plugin：

1. 前端只发送用户输入给 SafeHome 后端；
2. OpenAI API key 只放 Flask 服务端环境变量，绝不能放 `VITE_*` 或小程序代码；
3. 后端调用模型前先执行现有风险边界、数据最小化、限速、预算和审计；
4. 生产环境继续默认 `AI_QA_ENABLED=0`，只有评审、合成测试和供应商证据通过后才打开；
5. 站点仍必须选择方案 1、2 或 3 承载后端，因此它不是独立部署替代项。

## 7. 故障定位顺序

所有方案统一按“由内到外”排查：

1. Flask 是否启动：`http://127.0.0.1:5050/healthz`；
2. 就绪状态是否成功：`/readyz`；
3. Caddy 或本地同源代理是否能访问；
4. Web 是否错误打包了 `127.0.0.1`；
5. Tunnel/云托管版本是否运行；
6. DNS 是否指向正确目标；
7. HTTPS 证书是否匹配域名；
8. Cloudflare Access、应用登录和角色权限是否按层生效；
9. 小程序环境 ID、服务名和调用路径是否一致；
10. 最后才检查浏览器缓存和前端页面。

典型错误：

| 现象 | 先检查 |
|---|---|
| Caddy 502 | `127.0.0.1:5050/readyz` 和容器日志 |
| 页面能开但 API 失败 | `VITE_SAFEHOME_API_BASE_URL`、Caddy `/api/*` 路由、CORS |
| Cloudflare 502/1033 | cloudflared 是否在线、ingress 是否指向 8787 |
| 未授权用户直接看到登录页 | Cloudflare Access 应用和 Allow 策略是否覆盖正确 hostname |
| `callContainer 102002` | 环境 ID、服务名、版本流量和服务运行状态 |
| `/readyz` 503 | 响应中的数据库、内容库、构建一致性，不要先改 DNS |
| ChatGPT 找不到工具 | MCP URL 是否为 HTTPS `/mcp`、Developer mode、工具元数据 |
