## 6.6-FIX-P0-01：反馈生成接口补 diary 所有者校验

### 状态

已完成。

### 已完成证据

```text
代码位置：backend/routes/feedback.py 第 54-61 行
  diary = conn.execute("SELECT * FROM emotion_diaries WHERE id = ?", (diary_id,)).fetchone()
  if diary is None:
      return fail("not_found", ...)
  try:
      require_admin_or_owner(diary["user_id"])
  except ValueError as exc:
      return auth_error_response(exc)

测试覆盖：backend/tests/test_sensitive_owner_auth.py、test_admin_auth.py
```

### 问题

`POST /api/feedback/generate` 传入 `diary_id` 时，接口会直接读取对应 `emotion_diaries` 记录并生成反馈。

### 发生原因

早期 MVP 阶段默认前端只会处理当前匿名用户自己的记录，后端没有在 `diary_id` 路径上补充“请求 user_id 必须等于记录 user_id”的校验。6.5 后已为画像、家长测评等敏感接口补了 `require_admin_or_owner()`，但反馈生成接口遗漏。

### 位置

```text
backend/routes/feedback.py
第 54-59 行：根据 diary_id 查询 emotion_diaries
第 68-72 行：后续才 require_user_id(source_payload)
```

### 修改内容

```text
1. 在读取 diary 后立即校验权限。
2. 如果请求头有 X-Admin-Token，必须通过 require_admin_token()。
3. 如果没有管理员令牌，请求 payload 中的 user_id 必须等于 diary.user_id。
4. 校验失败返回 401 unauthorized。
5. 新增测试：用户 A 不能用用户 B 的 diary_id 生成反馈；管理员 token 可以。
```

### 修改结果

预期完成后：

```text
1. 小程序和 Web 当前用户仍能生成自己的反馈。
2. 其他匿名用户不能通过猜测 diary_id 读取或生成反馈。
3. 管理后台仍可通过有效 X-Admin-Token 生成反馈。
```

### 修改约束条件

```text
1. 不改变 POST /api/feedback/generate 的返回字段。
2. 不改变 high 风险阻断逻辑。
3. 不删除匿名 user_id 试用模式。
```

## 6.6-FIX-P0-05：导出转换函数 NULL user_id 崩溃防护

### 状态

已完成。

### 问题

2026-06-06 全工作区审查发现：在 `backend/routes/admin.py` 中，`EXPORT_ROW_TRANSFORMS` 下的 9 个导出转换函数直接调用 `_anonymous_id(row["user_id"])` 而**未使用 `or ""` 回退**。如果数据库中某行的 `user_id` 为 NULL，`row["user_id"]` 返回 `None`，调用 `None.encode("utf-8")` 会引发 `AttributeError`，导致整个导出请求崩溃并返回 500。

新增导出转换函数时参考了部分已有代码，但未统一 NULL 防护模式。`_feedback_export_rows` 和 `_record_export_rows` 已正确使用 `or ""`，其他函数遗漏。

### 位置

```text
backend/routes/admin.py
_goal_export_rows         → _anonymous_id(row["user_id"])        ← 缺少 or ""
_diary_export_rows        → _anonymous_id(row["user_id"])        ← 缺少 or ""
_checkin_export_rows      → _anonymous_id(row["user_id"])        ← 缺少 or ""
_assessment_export_rows   → _anonymous_id(row["user_id"])        ← 缺少 or ""
_weekly_report_export_rows→ _anonymous_id(row["user_id"])        ← 缺少 or ""
_supervision_export_rows  → _anonymous_id(row["user_id"])        ← 缺少 or ""
_cards_export_rows        → _anonymous_id(row["user_id"])        ← 缺少 or ""
_student_followup_rows    → _anonymous_id(row["user_id"])        ← 缺少 or ""
_sandplay_rows            → _anonymous_id(row["user_id"])        ← 缺少 or ""
```

### 修改内容

```text
1. 所有 9 个函数中的 _anonymous_id(row["user_id"]) 改为 _anonymous_id(row["user_id"] or "")。
2. 同步修复 export_csv 中未通过 EXPORT_ROW_TRANSFORMS 的其他导出路径（如 records）确保一致性。
3. 新增测试：模拟 user_id=NULL 的行，验证导出不崩溃并返回 anonymous_id 不为空。
```

### 修改结果

预期完成后：


## 6.6-FIX-P0-06：ContentLoadError 异常处理加固

### 状态

已完成。

### 问题

2026-06-06 审查发现三处 `check_text_risk()` 调用未捕获 `ContentLoadError`：

1. `backend/routes/profile.py` `_save_profile_result` 第 277 行：`check_text_risk` 在 `with get_connection() as conn:` 代码块内、`conn.commit()` 之前被调用。若抛出 `ContentLoadError`，整个事务回滚，所有评估数据永久丢失。

2. `backend/routes/profile.py` `create_profile_followup` / `create_profile_sandplay`：调用 `check_text_risk` 但未捕获 `ContentLoadError`，导致用户收到 500 而非友好的错误提示。

3. `backend/routes/parent_assessments.py` `create_parent_assessment` 第 120 行：`check_text_risk` 在 try/except 块**之后**被调用，异常不受保护。

### 发生原因

`check_text_risk` 内部调用 `load_risk_keywords()` → `load_required_content("risk_keywords.json")`，当内容文件缺失或解析失败时抛出 `ContentLoadError`。相关端点未统一处理此异常。

### 位置

```text
backend/routes/profile.py 第 277 行（_save_profile_result）
backend/routes/profile.py 第 475 行（create_profile_followup）
backend/routes/profile.py 第 588 行（create_profile_sandplay）
backend/routes/parent_assessments.py 第 120 行（create_parent_assessment）
```

### 修改内容

```text
1. _save_profile_result：将 check_text_risk 调用移到 conn.commit() 之后，或将整个风险检查包裹在 try/except ContentLoadError 中。
2. create_profile_followup / create_profile_sandplay / create_parent_assessment：在 check_text_risk 调用处增加 try/except ContentLoadError，失败时返回 fail("content_load_error", ...) 而非 500。
3. 新增测试：模拟 risk_keywords.json 缺失时端点不崩溃。
```

### 修改结果

预期完成后：

```text
1. 内容文件异常时用户收到明确错误提示而非 500。
2. _save_profile_result 不会因风险检查失败而丢失已计算数据。
3. 所有文本风险检查入口有统一的异常处理。
```

### 修改约束条件

```text
1. 不改变 risk_keywords.json 结构。
2. 不改变风险阻断逻辑。
3. 不新增数据库表。
```

## 6.6-FIX-P1-01：Web 云端后台令牌体验修正

### 状态

未完成。

### 问题

本地 Web 指向云端 API 时，后台页面仍默认使用 `safehome-local-admin-token`。云端 production 使用的是 CloudBase 环境变量 `ADMIN_EXPORT_TOKEN`，导致页面初始加载容易显示“后台令牌缺失或无效”。

### 发生原因

`getStoredAdminToken()` 为了方便本地开发，在 Vite dev 环境自动返回本地默认 token。但现在本地 Web 经常连接云端 API，默认 token 反而干扰验收。

### 位置

```text
apps/web/src/services/adminToken.ts 第 3-12 行
apps/web/src/pages/AdminDashboard.tsx 第 92-110 行、第 318-337 行
```

### 修改内容

```text
1. 当 VITE_SAFEHOME_API_BASE_URL 指向 tcloudbase.com 或非 localhost 时，不再默认返回 safehome-local-admin-token。
2. AdminDashboard 顶部增加后台令牌输入区，刷新记录前提示先填写令牌。
3. token 保存仍使用 localStorage 的 safehome_admin_token。
4. 错 token 时提示“请填写云托管 ADMIN_EXPORT_TOKEN，而不是本地默认令牌”。
```

### 修改结果

预期完成后：

```text
1. 云端验收时不会自动带错 token。
2. 用户能在页面顶部先填 token 再刷新数据。
3. 小程序写入云端后，Web 后台能按管理员视角读取。
```

### 修改约束条件

## 6.6-FIX-P1-04：React useEffect adminToken 依赖修复

### 状态

已完成。

### 问题

2026-06-06 审查发现三个 React 页面存在 adminToken 依赖错误：

1. **ResearchDashboard.tsx**：`useEffect(() => { void loadOverview(); }, []);` 依赖数组为空，但 `loadOverview()` 内部将 `adminToken` 传递给 `listRiskReviews` 和 `listProfileResults`。用户输入令牌后不会自动重新获取数据。

2. **ReviewManagement.tsx**：同一模式，且该页面**无手动刷新按钮**，用户输入令牌后永远无法触发重新加载（只能刷新整个页面）。

3. **ProfilesManagement.tsx**：两个 useEffect 将 `adminToken` 放入依赖数组 `[pathProfileId, adminToken]` 和 `[selectedId, adminToken]`。由于 `adminToken` 是受控输入，每次按键都触发两次网络请求（loadProfiles + loadDetail），一个 20 字符的令牌会产生约 40 个 HTTP 请求。

### 位置

```text
apps/web/src/pages/ResearchDashboard.tsx 第 215-217 行
apps/web/src/pages/ReviewManagement.tsx 第 79-81 行
apps/web/src/pages/ProfilesManagement.tsx 第 77、94 行
```

### 修改内容

```text
1. ResearchDashboard：useEffect 依赖数组添加 adminToken，使令牌变更时自动重新获取。
2. ReviewManagement：useEffect 依赖数组添加 adminToken，同时可考虑增加手动刷新按钮作为备选。
3. ProfilesManagement：从 useEffect 依赖数组中移除 adminToken，改为将 adminToken 通过 ref 传递，或在 loadProfiles/loadDetail 调用时从 localStorage 直接读取最新 token。
   推荐方案：使用 useRef 存储 adminToken，避免每次按键触发网络请求；增加"刷新"按钮用于应用令牌。
```
