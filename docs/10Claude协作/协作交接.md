## 一、当前项目定位

SafeHome 已不再是 2026 年 6 月阶段的单一亲子支持 MVP。当前代码实际包含：

1. 家长/学生参与者端：情绪记录、支持性反馈、训练、课程、测评、家庭绑定、隐私中心等。
2. 研究者/督导/管理员平台：研究参与者、复核、研究范围、交付、数据分析等。
3. 心理测量与画像：量表目录、worksheet、结果、聚类画像、模型准入与解释门禁。
4. 治疗性评估原型：能力授权、生命周期、未成年人保护、多方协作、安全、质量监督、停止恢复等。
5. AI 研究沙盒：合成数据、供应商治理、输入输出安全、质量门禁；参与者入口默认硬关闭。
6. 系统治理：安全隐私、可靠性、UX、运营发布、证据包等。

因此下一阶段的主目标不是继续扩大功能，而是：

> **SafeHome 1.0 收敛、P0 安全封口、真实试点边界冻结。**

### CI 事实修正

仓库已经有 GitHub Actions。`check.yml` 当前覆盖：

- 内容校验
- API contract drift
- API query boundaries
- API compatibility replay
- backend pytest
- AI quality gate
- Web typecheck/build
- design token / 小程序 UI / 结构 / JS / JSON 审计

不要再写“项目没有 CI”。后续需确认的是：**main branch protection 是否把该 workflow 设为 required check**，以及是否需要补 MySQL/Playwright/dependency 安全矩阵。

## 三、必须先处理的 P0

完整证据和验收条件见 `代码审查.md`。这里只保留执行顺序。

### P0-01 Showcase production 提权

涉及：

- `content/showcase_access.json`
- `backend/services/showcase_access_service.py`
- `backend/routes/auth_utils.py`
- `backend/tests/test_showcase_access.py`
- `backend/config.py`

当前仓库中的 showcase 是开启状态，并且现有测试明确允许 production 下打开。正式发布必须改成 production hard-off / fail-fast。

### P0-02 风险复核审计身份

涉及：

- `backend/routes/risk_review.py`
- `backend/services/risk_review_service.py`

客户端当前可传 `reviewer_id`，服务端又用该值写 `audit_logs.actor_id`。实际操作者必须只取认证 actor。

### P0-03 普通 student 年龄/监护范围

需要注意：项目**不是没有儿童保护代码**。治疗性评估已有：

- guardian consent
- child assent/refusal
- child refusal 优先
- 外部门禁
- 默认 entry disabled

对应 `backend/services/therapeutic_assessment_child_service.py`。

真正未闭环的是普通 student 注册/测评/记录主链路没有统一年龄字段和 <14 岁门禁。首轮试点可优先选择“仅 >=14 岁 + 服务端硬门禁”，避免先扩展复杂儿童身份系统。

### P0-04 PRFQ 准入状态冲突

`content/scales_catalog.json` 的 PRFQ 同时是 `pilot_approved/enabled=true`，又是 `draft_extracted`、`draft_from_syntax_pending_review`。

production `assessments.py` 会把 `pilot_approved` 当作用户端合格状态。闭环前必须降级，或把准入改成多字段联合判断。

### P0-05 风险关键词仍为 draft

`content/risk_keywords.json` 是运行时资源，但仍 `review_status=draft`。正式试点前需要人工冻结版本和处置边界。

## 四、当前应保留的设计

以下不是本轮重构对象，不要重复开发或随意删掉：

1. 高风险时禁止普通反馈/普通训练建议的安全边界。
2. 风险关键词明确声明“只作分流，不构成诊断或危机评估”。
3. 家长默认只查看学生授权摘要，不自动看到自由文本原文。
4. 画像 artifact hash、admission status、低置信/离群拒绝、解释批准门禁。
5. AI participant hard-off、synthetic-only sandbox。
6. 治疗性评估儿童 safeguard 的 guardian/child 双主体设计。
7. production 内容治理强制开启的总体方向。
8. GitHub Actions `SafeHome Checks`。
9. Task 37–38 中“engineering complete 不等于伦理/人工/生产批准”的边界。
10. UI 文案“非诊断、非评判、低压力”的设计系统。

## 五、下一阶段不要做什么

1. 不继续新增 Task 39/40 式大模块，除非 P0 已关闭且用户重新冻结需求。
2. 不做大爆炸式微服务化。
3. 不一次性重写数据库。
4. 不把关键词规则包装成自杀风险预测模型。
5. 不把聚类结果写成人格类型。
6. 不把 development 环境当真实试点环境。
7. 不把本地/自动工程验收写成真实试点、伦理批准或正式上线。
8. 不因“代码很多”直接删除 Task 37–38 的安全与治理模块；先做依赖与运行路径核验。

## 六、推荐执行顺序

### 第一轮：只修 P0-01

目标：showcase 在 production 彻底 fail-closed。

完成后必须跑：

- showcase 单元/路由测试
- backend 全量 pytest
- content validation
- API contract/boundary checks

### 第二轮：只修 P0-02

目标：风险复核 audit actor 不可由客户端冒充。

需要新增伪造 `reviewer_id` 的回归测试。

### 第三轮：只修 P0-04

目标：量表准入从“单字段状态”变成“证据成熟度联合门禁”，至少先关闭 PRFQ 当前矛盾状态。

### 第四轮：冻结试点人口与安全政策

由用户/导师确认：

- 试点是否只纳入 >=14 岁
- 哪些量表真正允许进入试点
- `risk_keywords` 人工审核版本
- 人工复核 SLA / 值班责任
- 真实试点数据库与 CloudBase 环境

之后再决定 P0-03/P0-05 的最终实现。

## 九、AI 协作操作边界

- 默认先审查、再修改。
- 每轮只处理一个 P0/P1，避免跨领域大改。
- 修改业务代码前先读现有测试，优先补回归测试。
- 不操作真实参与者数据。
- 不直接执行生产数据库迁移。
- 不修改 CloudBase 生产配置或部署，除非用户明确批准。
- 不记录密码、Token、密钥、验证码。
- 发现旧文档与代码冲突时，以当前代码和 `00_当前事实基准` 为优先，并把冲突记录下来。
