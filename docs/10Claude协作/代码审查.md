## 一、结论

SafeHome 已从早期亲子支持 MVP 扩展为“参与者端 + 研究平台 + 心理测量/画像 + 治疗性评估 + AI 研究沙盒 + 安全/可靠性/运营治理”的模块化单体。当前不建议继续新增大模块，下一阶段应进入 **SafeHome 1.0 收敛与真实试点准备**。

当前最需要处理的不是功能缺失，而是生产旁路、审计身份、量表准入状态、未成年人一般流程边界和架构收敛。

### 本轮对上一版审查的两项修正

1. **CI 已存在，不应再列为“没有 GitHub CI”**。`.github/workflows/check.yml` 已在 `push` / `pull_request` 上运行内容校验、API 契约检查、pytest、Web typecheck/build、小程序审计等。后续只需确认 GitHub branch protection 是否把该 workflow 设为必需检查。
2. **未成年人保护并非完全缺失**。`therapeutic_assessment_child_service.py` 已实现监护人同意、儿童 assent/refusal、外部证据门禁且默认关闭；真正缺口是**普通 student 注册/测评/家庭绑定主链路没有年龄识别和 <14 岁一般门禁**。

# 二、P0：上线/真实试点阻断项

## P0-01｜Showcase 在 production 可形成临时 admin 提权

### 证据

- `content/showcase_access.json`
  - `enabled=true`
  - `researcher_platform_full_access=true`
  - `allow_program_participation=true`
- `backend/services/showcase_access_service.py`
  - 所有 gate 只读取 JSON，没有 `APP_ENV` 的 production 拒绝条件。
- `backend/routes/auth_utils.py`
  - `elevate_actor_for_showcase_researcher_platform()` 在指定路径上直接返回 `role="admin"`。
- `backend/tests/test_showcase_access.py`
  - 当前测试明确验证 `APP_ENV=production` 时 showcase 可打开；普通 parent 可临时读写研究者平台。

### 风险

这是生产权限边界问题。当前安全依赖“发布前人工记得关闭 JSON”，不是 fail-closed。

### 必改

1. `Config.validate()`：`APP_ENV=production` 且 showcase 任一权限开启时直接启动失败。
2. `showcase_access_service.py`：production 一律返回关闭，不能只依赖配置文件。
3. `content/showcase_access.json`：仓库默认值全部改为 false。
4. `test_showcase_access.py`：删除/改写“production 打开 showcase”的正向测试，新增 production 必须拒绝的测试。
5. 最好把 showcase 归入 `devtools`/`internal-rd`，不要继续作为正式 RBAC 的分支逻辑长期存在。

### 验收条件

- production + showcase JSON=true → 应用启动失败或所有 showcase gate 恒为 false。
- parent/student 在 production 永远不能因 showcase 获得 researcher/admin capability。
- CI 有反向回归测试。

## P0-02｜风险复核审计 actor 可由客户端 `reviewer_id` 冒充

### 证据

`backend/routes/risk_review.py`：

```python
reviewer_id = str(payload.get("reviewer_id") or actor["id"])
```

`backend/services/risk_review_service.py`：

- 把传入的 `reviewer_id` 写入 `risk_review_records.reviewer_id`
- 同一个 `reviewer_id` 又被写入 `audit_logs.actor_id`

### 风险

A 实际完成复核，但请求体写 B 的 ID 时，最终审计会记录为 B。对自伤/自杀/他伤等安全复核，这会破坏不可抵赖性。

### 必改

```text
actor_id = 认证令牌中的 actor.id       # 永远由服务端决定
assigned_reviewer_id = 原分配负责人      # 如有
reviewed_by = 实际复核人                 # actor.id
delegated_by / delegation_id = 代办链路  # 如有
```

客户端不允许提交会改变审计 actor 的字段。

### 验收条件

- 请求体伪造 `reviewer_id` 不会改变 audit actor。
- 新增测试：supervisor A 请求中携带 B ID，最终 `audit_logs.actor_id` 必须仍为 A。

## P0-03｜普通 student 主链路没有年龄识别；<14 岁边界未闭环

### 已有优点

`backend/services/therapeutic_assessment_child_service.py` 已有较强的儿童保护设计：

- guardian consent 与 child assent 分离
- child refusal 优先，监护人不能覆盖
- T3/伦理/试点外部门禁
- `entry_enabled=false`
- `production_release_approved=false`
- showcase 不计作权限

这个模块应保留。

### 一般链路缺口

- `backend/models.py -> users` 没有 `birth_date`、年龄段、`is_under_14` 等通用身份字段。
- `backend/routes/auth.py -> register()` 公开允许 `student` 注册，但不收集/校验年龄。
- `backend/routes/family.py -> bind_student()` 写入的是学生同意家长查看摘要，不等价于 <14 岁数据处理的监护人同意。
- 普通测评/日记/反馈链路因此无法从服务端判断是否应进入儿童专门政策。

### 必须二选一

**方案 A（首轮试点推荐）**：明确仅招募/允许 `>=14` 岁参与者，并把年龄资格做成服务端硬门禁和审计字段。  
**方案 B**：把现有 therapeutic child safeguard 的 guardian/child 双主体思想上移到统一 participant identity / consent 层，再允许 <14 岁进入普通心理数据链路。

### 验收条件

- 系统能在服务端判断参与者是否处于受限制年龄范围。
- 未满足对应 consent/assent 的账号不能提交敏感心理数据。
- 不能只靠招募说明或前端提示约束。

## P0-04｜PRFQ 的准入状态与证据成熟度矛盾

### 证据

`content/scales_catalog.json` 中 `parent_reflective_functioning_prfq` 同时为：

```text
review_status = pilot_approved
enabled = true
item_status = draft_extracted
scoring_status = draft_from_syntax_pending_review
```

notes/review_note 又明确写着“正式试点前仍需人工复核来源、计分和边界”。

`backend/routes/assessments.py` 把 `pilot_approved` 列入 `APPROVED_REVIEW_STATUSES`，production 内容治理开启时会允许该 worksheet 对用户开放。

### 风险

状态机把“负责人原则批准”误当成“题项、计分、权利与伦理证据均成熟”。

### 必改

准入不能只看单一 `review_status`。建议至少同时满足：

```text
enabled_for_user = true
review_status in approved statuses
item_status in verified statuses
scoring_status in verified statuses
rights/licence status = approved
ethics/boundary status = approved
```

在闭环前，PRFQ 应降级到 `pilot_review_required` 或 `enabled=false`。

### 验收条件

任何 `draft_*` / `pending_review` 的题项或计分状态不得通过 production participant gate。

## P0-05｜风险关键词运行时资源仍标记为 draft

### 证据

- `content/risk_keywords.json`：`review_status="draft"`
- `backend/services/risk_service.py`：运行时 `check_text_risk()` 直接加载该配置，并用 `keyword in combined_text` 做子串匹配。

### 判断

当前实现适合作为**透明的安全分流器**，不适合称为临床风险评估。代码中的非诊断边界是正确的，应保留。

### 必改

1. 正式试点前由心理学/伦理负责人冻结关键词版本和处置说明。
2. 运行时资源必须具有明确 `pilot_approved`/版本/审核人/证据引用。
3. UI/API 更推荐使用 `safety_route`（standard / human_review / urgent_human_review）而不是让用户或开发者误读为真实风险等级。
4. 保留人工复核，不允许关键词结果独立决定临床处置。

# 三、P1：试点扩量前整改

## P1-01｜账号密码最低仅 8 位

`backend/routes/auth.py -> register()` 当前：

```python
if len(password) < 8:
```

建议统一建立 `password_policy`，至少加入更长口令策略和常见/泄露口令 blocklist；如果正式用户完全迁移到可信微信身份/多因素路径，可降低该项优先级。

---

## P1-02｜Web Bearer token 存在 `localStorage`

`apps/web/src/services/authState.ts` 直接把 `safehome_auth_token` 写入 `window.localStorage`。

建议评估：

- Web 使用 HttpOnly/Secure/SameSite session cookie；或
- 短期 access token + 严格 CSP + 刷新机制。

后台 legacy admin token 当前仅在内存保存，反而更不容易被持久化脚本直接读取。

---

## P1-03｜缺少“pilot”这一独立运行环境语义

`backend/config.py` 目前主要区分 development/testing/production。`CONTENT_GOVERNANCE_ENFORCED` 在 production 强制开启，而 development/testing 的多项研发能力默认开启。

真实参与者试点不应直接使用 development 配置。

建议增加 `APP_ENV=pilot` 或等价部署 profile：

- 强制内容治理
- showcase=false
- AI participant=false
- debug/integration test 不暴露
- 独立试点数据库
- 完整审计
- 只允许 pilot-approved 内容/模型
- 保持 production 的大多数安全限制，但允许尚未正式生产发布的受控试点能力

---

## P1-04｜数据库关系越来越复杂，但核心关系主要靠应用代码保持一致

`backend/models.py` 已承载大量 `user_id`、`enrollment_id`、`workflow_id`、`assessment_result_id` 等跨表关系。当前主 schema 中没有形成系统性的 FK 约束体系。

不要一次性重写数据库，先给高价值关系补完整性：

1. assessment_result → users/worksheet
2. family_links → users
3. risk_review → user/source
4. relationship enrollment → users/result
5. research workflow → enrollment

MySQL/SQLite 迁移要分别验证。

## P1-05｜前端领域边界应开始拆分

重点文件：

- `apps/web/src/main.tsx`
- `apps/web/src/services/safehomeApi.ts`

它们已同时承载参与者、内容、研究、隐私、安全、可靠性、运营、治疗性评估等领域，继续增长会成为 God Module。

建议先做模块化单体前端，不需要微前端：

```text
features/participant
features/assessment
features/research
features/safety
features/privacy
features/therapeutic-assessment
features/system-governance
```

API client 按领域拆文件，保留统一底层 request client。
