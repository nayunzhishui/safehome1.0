# SafeHome 工程技术增强方案

更新时间：2026-08-07  
适用仓库：`nayunzhishui/safehome1.0`  
审计基线：`main@1fc556da9c12948132e8e77c0f14bd7776d53d4b`  
修复分支：`codex/safehome-security-enhancement-20260807`  
性质：**工程技术审计与后续增强路线，不代表这些基础设施已经部署。**

---

## 0. 先给结论

SafeHome 当前最适合继续维持 **模块化单体 + MySQL + CloudBase 网关 + 原生微信小程序 + React 研究后台**，暂时不应为了“技术先进”改造成微服务。

对本项目，各技术的建议优先级如下：

| 技术 | 当前实际状态 | 是否现在就需要 | 结论 |
|---|---|---:|---|
| MySQL | 已是生产主数据层 | 是 | **重点增强**：连接池、超时、索引、慢查询、备份、迁移、完整性 |
| Nginx | 仓库内未发现配置；当前主要依赖 CloudBase/平台入口 | 否/条件式 | CloudBase 已满足入口时不要重复堆一层；自托管时再加入 |
| Redis | 当前未发现正式实现 | 条件式 | 先用于限流/缓存/幂等/任务状态；绝不能做心理数据事实源 |
| Flask | 2.2.2，代码组织已明显超过早期 MVP | 是 | 升级版本并做领域拆分、输入契约、观测性和服务边界 |
| Gunicorn | 2 workers，配置极简 | 是 | 增加线程/超时/回收/日志/健康管理，AI长任务异步化 |
| React | React 19 + Vite，后台功能很大 | 是 | 按领域拆 main/API，统一鉴权/查询/错误边界 |
| 微信小程序 | 原生 JS + CloudBase callContainer | 是 | 分包、请求治理、真机性能、无障碍、隐私与保护门禁 |
| UI/UX | 已有较成熟设计系统 | 是 | 从“页面数量”转向“任务完成率、认知负荷、安全理解” |
| RAG | 已有 SQL LIKE 词法检索 + 知识治理 | 条件式增强 | 先保留治理，再升级 hybrid retrieval，不要先上大模型 |
| Agent | 未发现真正自治 Agent runtime | 暂不全面开放 | 先做单编排器 + 只读工具 + 人工批准，不做自治临床 Agent |

### 核心架构判断

SafeHome 的技术复杂度主要来自 **权限、心理内容治理、研究数据、未成年人、危机安全、审计和多端一致性**，而不是 QPS。因此优化目标应是：

1. 可验证；
2. 可追溯；
3. 可回滚；
4. 权限最小化；
5. 心理内容不越界；
6. 真机和真实试点稳定；
7. 只有在出现真实容量瓶颈时再水平拆分。

# 2. MySQL：本项目最值得优先增强的基础设施

## 2.1 当前实现优点

现有 `backend/database.py` 已有：

- SQLite/MySQL 双 provider；
- 显式事务；
- 异常回滚；
- `utf8mb4`；
- MySQL `DictCursor`；
- 只读快照事务；
- schema/index 元数据抽象；
- readiness 检查；
- 本分支新增独立 `explicit_schema_migrations`，不污染旧 readiness schema marker。

这意味着**不需要推翻重写数据库层**。

## 2.2 当前最明显缺口：没有连接池

当前每次：

```python
pymysql.connect(...)
```

然后请求结束关闭。

低并发试点可以运行，但会产生：

- TCP/MySQL握手成本；
- 短连接抖动；
- 高并发时连接数峰值；
- CloudBase 容器扩缩容时连接风暴。

### 建议方案 A：最小变更连接池

不要为了连接池立刻引入 ORM。

可选：

- DBUtils `PooledDB`；或
- SQLAlchemy `QueuePool` 仅作为连接管理层，业务 SQL 保持原样。

起始参数示例（不是固定最优值）：

```text
每个 Gunicorn 实例：
workers = 2
threads = 4
pool_size = 5
max_overflow = 2
pool_recycle = 1800s
pre_ping = true
```

容量公式必须检查：

```text
最大数据库连接预算
>= 容器最大实例数 × 每实例连接池上限 + 运维连接 + 迁移连接
```

并建议只使用数据库 `max_connections` 的约 60%-70% 作为应用正常预算，保留故障恢复空间。

### 推荐连接参数

```python
pymysql.connect(
    ...,
    charset="utf8mb4",
    autocommit=False,
    connect_timeout=5,
    read_timeout=10,
    write_timeout=10,
)
```

参数需要根据腾讯云同地域网络实测调整。

AI 外部调用绝不能占着数据库事务等待 20-60 秒。

错误模式：

```text
BEGIN
SELECT ... FOR UPDATE
调用 LLM 30 秒
UPDATE
COMMIT
```

正确模式：

```text
短事务读取最小数据 -> COMMIT
调用外部 AI
新短事务写入经过验证的结果/草稿
```

## 2.3 TLS

应确认 CloudBase -> TencentDB 的链路模式。

若数据库支持 TLS：

- 开启服务端证书验证；
- 不接受 `ssl_disabled` 式快速绕过；
- CA 文件走部署秘密/可信镜像，不进仓库；
- 数据库密码只由 Secrets/环境注入。

## 2.4 数据库账号最小权限

不要让 Web 应用账号拥有：

```text
CREATE USER
GRANT
SUPER
DROP DATABASE
```

建议至少拆：

```text
safehome_app_rw     正常业务读写
safehome_migration  发布时迁移
safehome_readonly   BI/只读审计
```

研究导出权限不应等于 MySQL 用户权限；仍必须经过应用层 RBAC + 审计。

## 2.5 索引治理

不要按“看到 WHERE 就加索引”。

流程：

```text
慢 SQL / 高频 SQL
  -> EXPLAIN ANALYZE
  -> 判断选择性和排序
  -> 加联合索引
  -> 回归写性能
  -> 观察 7-14 天
```

本项目优先检查的查询形态：

```sql
risk_review_records(review_status, due_at, risk_level)
supervision_requests(status, due_at, priority)
family_links(parent_user_id, status)
family_links(student_user_id, status)
assessment_results(user_id, created_at)
consent_records(user_id, consent_type, created_at)
messages(user_id, created_at)
emotion_diaries(user_id, created_at)
relationship_pilot_enrollments(user_id, status)
audit_logs(actor_id, created_at)
```

本分支已经为风险、督导、未成年人保护新增若干关键索引；其余应先 `EXPLAIN`，不要盲加。

## 2.6 外键

SafeHome 当前大量 `*_id` 关系由应用维护。

建议分阶段加入 FK，优先关系：

```text
assessment_results.user_id -> users.id
family_links.parent_user_id -> users.id
family_links.student_user_id -> users.id
participant_minor_safeguards.user_id -> users.id
risk_review_records.user_id -> users.id
relationship_pilot_enrollments.user_id -> users.id
```

但不要一次对全库强加：

1. 先查孤儿记录；
2. 修数据；
3. 给新表加；
4. 再处理历史表。

审计日志通常不建议级联删除。

## 2.7 隔离级别

当前项目已有 MySQL `REPEATABLE READ + READ ONLY WITH CONSISTENT SNAPSHOT` 的读取能力。

建议：

- 普通单请求 CRUD：保持数据库默认或评估 `READ COMMITTED`；
- 研究导出/一致快照：显式只读 `REPEATABLE READ`；
- 高冲突工作流：使用 version 字段做乐观锁，优先于大范围 `FOR UPDATE`。

本分支风险复核已经使用 `review_version`。

## 2.8 大表治理

未来最先膨胀的通常不是 users，而是：

- audit_logs；
- observability_events；
- agent/tool traces；
- product events；
- messages；
- longitudinal/research events。

建议在 >100万级记录前准备：

- retention；
- 冷热分层；
- 按时间归档；
- 导出到对象存储/日志平台；
- 不要把无限 tracing 永久放 MySQL。

## 2.9 备份

真实试点前必须能回答：

```text
RPO 是多少？
RTO 是多少？
能否点时间恢复？
误删后如何恢复？
恢复是否演练过？
```

建议试点目标示例：

```text
RPO <= 15 min
RTO <= 2 h
```

但最终值取决于腾讯云能力和项目实际责任。

至少每季度做恢复演练，而不是只看“备份成功”。

# 3. Nginx：当前不要为了“标准架构”强行加入

## 3.1 当前事实

仓库当前 Docker 直接运行 Gunicorn，未发现正式 Nginx 配置。

CloudBase/云托管本身通常已经提供入口代理、TLS和流量接入，因此：

> 如果平台已经处理 TLS、入口路由、健康检查和基础限流，再在同容器内加 Nginx 只会增加一层配置和故障点。

## 3.2 什么时候应该加入

只有出现以下需求时再引入自管 Nginx：

- 自建 VM/Kubernetes；
- 需要细粒度 upstream；
- SSE/长连接需要平台无法满足的控制；
- 特殊 header/rate-limit；
- 静态 Web 与 API 同域反代；
- 多后端服务路由。

## 3.3 如果未来使用，建议起点

```nginx
server {
    listen 443 ssl http2;
    server_name safehome.example.com;

    client_max_body_size 1m;

    location /api/ {
        proxy_pass http://safehome_backend;
        proxy_connect_timeout 5s;
        proxy_send_timeout 30s;
        proxy_read_timeout 30s;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID $request_id;
    }
}
```

AI SSE 若启用：

```nginx
proxy_buffering off;
proxy_read_timeout 120s;
```

但不要把普通 API 全部调成 120 秒。

## 3.4 安全注意

`X-WX-OPENID` 等 CloudBase 身份头只能由可信网关注入。

如果自加 Nginx：

- 外部请求进入时清除伪造身份头；
- 再由受信链路注入；
- Flask 的 `ProxyFix` 只能按真实代理层数配置，不能无条件信任任意 `X-Forwarded-*`。

# 4. Redis：适合做辅助层，不适合做心理数据事实源

## 4.1 当前事实

仓库当前没有正式 Redis 实现。

## 4.2 推荐引入时机

当以下至少两项出现真实需求时引入：

1. 多实例限流；
2. 幂等请求跨实例去重；
3. 高频不可变内容缓存；
4. AI job 状态；
5. 异步任务队列；
6. 短期 nonce/challenge；
7. 分布式 scheduler 选主。

## 4.3 绝不能放什么

不要把这些只存在 Redis：

- 监护人同意；
- 儿童 assent/refusal；
- 风险复核最终记录；
- 心理测评正式结果；
- 研究授权；
- 审计日志唯一副本。

这些必须进入 MySQL/正式审计层。

## 4.4 推荐 key 设计

```text
rl:login:ip:{hash}                 TTL 15m
rl:login:user:{user_id}            TTL 15m
idem:{actor_id}:{idempotency_key}  TTL 24h
content:{version}:{resource}:{id}  TTL 1h-24h
agent:run:{run_id}:status           TTL 1h
agent:approval:{run_id}             TTL 15m-1h
embedding:q:{model}:{query_hash}    TTL 24h
```

避免把原始心理文本写进 key 名。

## 4.5 限流示例

登录：

```text
IP: 10 次 / 15 分钟
账号: 5 次失败 -> 已有数据库锁定机制继续保留
```

AI：

```text
普通参与者: AI 默认不开
研究者: 10-30 次 / min / actor，视模型成本调整
全局: 设置并发上限
```

危险文本接口不能因为限流让用户只看到“429”而失去安全提示；用户端应有静态紧急帮助边界。

## 4.6 eviction

若 Redis 只做缓存：

```text
allkeys-lfu
```

若同时做队列/重要 job 状态，不要与可随意淘汰的缓存共用同一实例；至少拆实例或使用 `noeviction` 的独立队列实例。

# 5. Flask：从“大型 MVP”向稳定模块化单体收敛

## 5.1 版本

当前 Flask/Werkzeug 较旧。

建议不要直接跨版本上线：

```text
分支升级
 -> pytest
 -> API契约
 -> MySQL集成测试
 -> Web E2E
 -> 微信开发者工具
 -> 体验版
 -> pilot
```

目标可升级到当前维护中的 Flask 3.x / Werkzeug 3.x 系列，但以实际兼容测试为准。

## 5.2 Blueprint 拆分原则

不要继续按任务号：

```text
task37_xxx
task38_xxx
```

建议长期领域：

```text
backend/domains/
  participant/
  assessment/
  safety/
  supervision/
  minor_safeguards/
  research/
  privacy/
  identity/
  content_governance/
  operations/
  ai/
```

Task 编号只保留：

- migration 名；
- acceptance evidence；
- 历史 docs。

## 5.3 输入验证

本分支新增了中央 bounded validation。

长期建议向 schema 化发展：

```python
class DiaryCreate(BaseModel):
    scene: constr(min_length=1, max_length=120)
    event_description: constr(min_length=1, max_length=4000)
    parent_emotion_intensity: conint(ge=0, le=10)
```

项目已经有 Pydantic，可先统一请求 DTO，不要求切 ORM。

## 5.4 错误模型

统一：

```json
{
  "ok": false,
  "error": {
    "code": "guardian_consent_required",
    "message": "...",
    "details": {}
  },
  "request_id": "..."
}
```

原则：

- code 稳定；
- message 可本地化；
- details 不返回内部 SQL/trace；
- 5xx 带 request_id。

## 5.5 外部服务隔离

微信、AI、未来向量库调用都必须：

```text
connect timeout
read timeout
bounded retry
circuit breaker / fallback
request id
metrics
```

不可：

```python
requests.post(url)  # 无 timeout
```

## 5.6 retry

只有幂等操作自动重试。

可安全重试：

- GET；
- 已有 Idempotency-Key 的 POST；
- 明确定义 request token 的 provider request。

不应直接重试：

- 未带幂等键的创建；
- 发送消息；
- 监护人同意；
- 发布内容。

# 6. Gunicorn：当前 2 worker 需要按 I/O 模型调优

## 6.1 推荐起点

当前 SafeHome 是 DB + HTTP I/O 较多的应用，可先试：

```bash
gunicorn app:app \
  --bind 0.0.0.0:80 \
  --workers 2 \
  --worker-class gthread \
  --threads 4 \
  --timeout 30 \
  --graceful-timeout 30 \
  --keep-alive 5 \
  --max-requests 1000 \
  --max-requests-jitter 100 \
  --access-logfile - \
  --error-logfile -
```

真实参数必须结合：

- CloudBase CPU/内存；
- DB连接池；
- P95/P99 latency；
- 并发用户；
- AI调用是否异步。

## 6.2 AI 长任务不要靠 `timeout=120` 硬扛

推荐：

```text
POST /ai/jobs -> 202 + job_id
worker 执行
GET /ai/jobs/{id}
或 SSE 只推状态
```

而不是让 Gunicorn worker 同步等待一分钟。

# 7. React/Vite Web 研究后台

## 7.1 当前优点

- React 19；
- TypeScript；
- Vite；
- React Router；
- Zod；
- Playwright；
- lazy pages；
- 本分支将 bearer token 从 localStorage 收敛为 sessionStorage。

## 7.2 当前结构问题

`main.tsx` 和 `safehomeApi.ts` 过大。

长期拆分：

```text
src/
  app/
    router/
    auth/
    errors/
  features/
    assessment/
    research/
    safety/
    supervision/
    privacy/
    therapeutic-assessment/
    operations/
    ai/
  shared/
    api/
    ui/
    schemas/
```

API：

```text
services/safehomeApi.ts
```

逐步变成：

```text
features/safety/api.ts
features/research/api.ts
features/assessment/api.ts
```

## 7.3 Zod 真正用起来

服务端契约有 TypeScript 类型不代表运行时安全。

例：

```ts
const RiskReviewSchema = z.object({
  id: z.string(),
  safety_route: z.enum(["standard", "human_review", "urgent_human_review"]),
  review_status: z.string(),
  due_at: z.string().nullable(),
});
```

对安全/研究/隐私高价值接口优先 runtime parse。

## 7.4 Web 会话最终形态

`sessionStorage` 比长期 localStorage 降低了持久化风险，但**仍会被同源 XSS 读取**。

如果 Web 与 API 能同域，长期更推荐：

```text
HttpOnly
Secure
SameSite=Lax/Strict
短会话 Cookie
CSRF 防护
```

微信小程序仍可使用 bearer token。

这不是重新制造“双身份系统”：

> 身份主体和 RBAC 统一；只是 Web 和小程序的凭证传输载体不同。

## 7.5 前端权限原则

前端路由隐藏只用于 UX：

```text
隐藏按钮 != 权限控制
```

所有真正权限仍由 Flask `require_role/require_capability` 决定。

前端应有单一权限注册：

```ts
route -> allowed roles -> required capabilities
```

避免每个页面自己写 `if role === ...`。

## 7.6 Server state

当同一数据在多个页面反复读取时，可以引入 TanStack Query 一类 server-state 层，但不要为了“现代 React”立即重写全部页面。

优先对象：

- current user；
- content registry；
- review queues；
- dashboard；
- feature gates。

# 8. 微信小程序 + CloudBase

## 8.1 当前架构

- 原生微信小程序 JS；
- `wx.cloud.callContainer`；
- local HTTP / cloud container 双传输；
- Bearer token；
- 微信登录；
- 手机号授权；
- 本分支新增年龄/监护人保护前端闭环。

## 8.2 请求治理

建议统一网络层包含：

```text
request_id
Idempotency-Key
timeout
retry policy
auth refresh/logout
error mapping
network/offline state
```

不要每个 service 再复制一套 transport；本分支新 minor client 后续应并回统一 API transport。

## 8.3 分包

页面数量已多，建议根据真机包体检查拆：

主包只保留：

```text
home
login
profile
training core
emergency
```

分包示例：

```text
subpackages/assessment/
subpackages/research/
subpackages/therapeutic-assessment/
subpackages/internal-debug/
```

实际分包前必须检查微信当前包体限制与预加载策略。

## 8.4 setData

避免：

```js
this.setData({ giantObject: hugeData })
```

优先：

- 小字段 diff；
- 列表分页；
- 不把后台大 JSON 全塞页面 data；
- 大文本不重复 setData。

## 8.5 登录/年龄门禁

当前正确原则：

```text
前端引导
+
后端强制
```

不能只在小程序页面隐藏按钮。

本分支 `<14` 门禁后端会再次检查，因此抓包绕过页面仍应被拒绝。

## 8.6 真机专项

体验版必须覆盖：

- iPhone 小屏；
- Android 中低端；
- 深色/字体放大（即使设计不完全支持，也要检查崩坏）；
- 网络从 Wi-Fi -> 4G；
- 弱网；
- 页面被系统回收；
- 授权取消；
- 微信登录 code 失效；
- 手机号授权拒绝；
- 草稿恢复；
- 重复点击提交。

# 9. UI/UX：从“设计完整”转向“任务安全完成”

## 9.1 已有优势

SafeHome 设计系统方向是对的：

- 安静；
- 低刺激；
- 非评判；
- 少渐变/少装饰；
- 非 AI 感；
- 一页一个主要焦点；
- “今天的一小步”。

## 9.2 首页

首页不要继续变成“所有功能导航页”。

推荐信息层级：

```text
1 今天的一小步（Hero）
2 紧急帮助固定可达
3 当前记录/进度
4 次级功能
```

## 9.3 危机 UX

不要显示：

```text
“你的风险为高”
“AI判断你很危险”
“系统评估安全”
```

显示：

```text
“这段内容触发了人工安全复核。”
“如果你此刻担心会伤害自己/他人，请优先联系现实中的可靠人员或当地紧急服务。”
```

人工队列内部可显示 `urgent_human_review`，用户端不需要看到技术标签。

## 9.4 未成年人 UX

年龄门禁应做到：

- 不询问精确生日；
- 不使用“儿童账户受限”式惩罚语言；
- 解释为什么需要家长；
- 明确家长同意不能替代本人意愿；
- 拒绝按钮不能藏在弱视觉角落；
- 撤回路径与同意路径同等可达。

## 9.5 无障碍

目标升级为 WCAG 2.2 AA 的关键原则，尤其：

- 文本对比度；
- 焦点可见；
- 点击目标；
- 键盘 Web；
- 状态不能只靠颜色；
- 错误提示与字段关联；
- 认证不要依赖认知谜题。

## 9.6 真实用户研究指标

不要只做“好不好看”。

建议测：

```text
任务完成率
完成时间
错误率
放弃率
重复提交率
错误恢复率
关键边界理解率
未成年人流程理解率
紧急帮助发现时间
SUS / UMUX-Lite
单题认知负荷
```

例：

> 给家长一个“未满14周岁学生需要绑定和同意”的任务，看他能否在无指导情况下完成，并让其复述“绑定是否等于同意”。

这比主观设计评分更重要。

# 10. CI/CD 增强

## 10.1 当前已经有的好基础

SafeHome Checks 已包含：

- content validation；
- API contract drift；
- API query boundary；
- API compatibility snapshot；
- pytest；
- AI quality gate；
- TypeScript；
- Vite build；
- 小程序设计治理；
- 小程序 JS/JSON 静态校验。

## 10.2 建议矩阵化

当前数据库测试主要偏 SQLite。

建议增加：

```yaml
matrix:
  db: [sqlite, mysql]
```

MySQL CI 用临时 service container，至少跑：

- schema init；
- explicit migration；
- auth；
- minor safeguards；
- risk review；
- supervision；
- assessment submission。

## 10.3 依赖安全

增加：

```text
pip-audit
npm audit（作为信号而非机械阻塞）
Dependabot/Renovate
SBOM
container image scan
```

安全更新不应“一键全升级”；先分 PR。

## 10.4 branch protection

main 至少：

- PR required；
- SafeHome Checks required；
- 禁止直接 force push；
- 关键 CODEOWNERS 可后续配置；
- 不自动合并本安全收敛分支。

# 13. 不建议做的技术改造

当前阶段明确不建议：

- 微服务化；
- Kubernetes 只为“专业”；
- 把所有 SQL 改 ORM；
- 把 Redis 当正式数据源；
- 为了 Nginx 而 Nginx；
- 把全部自由文本送入向量库；
- 参与者端开放自治 Agent；
- AI 自动发布心理反馈；
- AI 自动关闭危机事件；
- AI 自动批准研究导出；
- 一次性重写 React 后台；
- 一次性替换原生小程序框架。

SafeHome 当前最需要的是 **更可靠的边界，而不是更多技术名词**。
